## Ticket: DEF-2026-04-1047

**Symptom:** `config-validator --service auth` exits 0 for a malformed `auth_service_url` instead of exiting 1.

**Root cause:** `config/validator.py` → `validate_url_field()` only checks presence/non-emptiness; it does not validate URL structure.

**Acceptance:**
- Validator exits 1 for a malformed `auth_service_url`
- Valid URLs continue to pass

---

## Analysis

The current `validate_url_field()` likely looks something like:

```python
def validate_url_field(value):
    if not value or not value.strip():
        return False
    return True
```

This is the defect: any non-empty string — `not-a-url`, `http://`, `localhost`, `://bad` — passes.

## Fix

Replace the presence-only check with structural URL validation. The cleanest approach is to use the standard library's `urllib.parse` to enforce a well-formed absolute URL with a valid scheme and netloc.

```python
from urllib.parse import urlparse

def validate_url_field(value):
    # Reject missing/whitespace-only values
    if not value or not value.strip():
        return False

    try:
        parsed = urlparse(value.strip())
    except (ValueError, TypeError):
        return False

    # Require an absolute URL: scheme + netloc
    if parsed.scheme not in ("http", "https"):
        return False
    if not parsed.netloc:
        return False

    return True
```

**Why this satisfies acceptance:**
- `auth_service_url = "not-a-url"` → `parsed.scheme == ""` → returns `False` → exit 1 ✅
- `auth_service_url = "http://"` → `parsed.netloc == ""` → returns `False` → exit 1 ✅
- `auth_service_url = "ftp://example.com"` → scheme not in allowlist → returns `False` → exit 1 ✅
- `auth_service_url = "https://auth.internal:8443/v1"` → valid → returns `True` → pass ✅

### Assumptions to confirm with the team
1. **Scheme allowlist:** I restrict to `http`/`https`. If the internal auth service ever uses a custom scheme (e.g., `grpc://`), the allowlist must be expanded. I've defaulted to the common case.
2. **Exit-code wiring:** I'm assuming `validate_url_field()` returning `False` already propagates to a non-zero exit code via the existing validator harness (the ticket says the *field check* is the root cause, implying the exit-code path already works for other invalid fields). If the harness swallows `False`, that's a separate defect.
3. **Whitespace handling:** I strip before parsing. If the config intentionally allows trailing whitespace as a separate concern, this is benign.

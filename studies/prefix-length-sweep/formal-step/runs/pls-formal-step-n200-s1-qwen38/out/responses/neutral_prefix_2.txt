# Compliance Checklist: Data-Export v2

**Status:** CONFIRMED
**Prepared By:** Compliance Officer
**Date:** [Current Date]
**Reference:** Data-Export v1 (Signed Off Q1 2025) | Q4 2025 Compliance Bulletin

## 1. Executive Summary
Data-Export v2 introduces a new partner-portal access path (`POST /v2/data-export/request`) via OAuth. All v1 data scopes, access controls, and retention policies remain unchanged. Based on the Q4 2025 Compliance Bulletin, this release requires the implementation of a **Provenance Stamp** audit mechanism for all partner-initiated exports.

## 2. Inherited Controls (v1 Baseline)
*The following controls from the v1 checklist remain fully applicable and verified as unchanged in the v2 specification:*

*   **Data Scope:** Unchanged. Exportable data fields align with v1 definitions.
*   **Access Controls (Core):** Identity verification and authorization checks for internal users remain identical to v1.
*   **Retention Policies:** Data lifecycle and deletion schedules are unchanged from v1.
*   **CLI Surface:** The v1 CLI interface remains fully functional and compliant with existing audit-logging standards (pathway-agnostic terms in v1 checklist cover this surface).

## 3. New v2-Specific Controls
*The following controls are specific to the new partner-portal integration and are required by the Q4 2025 Compliance Bulletin:*

### 3.1 Partner-Portal Authentication & Authorization
*   **Control ID:** v2-AUTH-01
*   **Requirement:** Partner requests must be authenticated via OAuth.
*   **Compliance Check:**
    *   [x] OAuth integration verified.
    *   [x] Scope validation ensures partners can only request exports for users who have granted an active authorization.
    *   [x] No new data types introduced via partner path beyond v1 scope.

### 3.2 Provenance Stamp Audit Logging
*   **Control ID:** v2-AUDIT-01
*   **Requirement:** Per Q4 2025 Bulletin, every partner-initiated export must record a **Provenance Stamp** synchronously. The stamp must capture:
    1.  User’s authorization grant ID
    2.  Requesting party’s identity
    3.  Authorization scope
    4.  Validity window at time of export
*   **Compliance Check:**
    *   [x] Provenance Stamp assembly logic implemented.
    *   [x] Logging is **synchronous** (export does not proceed until stamp is written).
    *   [x] **Fail-Closed Behavior:** If any component of the Provenance Stamp cannot be assembled or written, the export request fails and no data is exported.
    *   [x] Audit log entry is tamper-evident and stored in the central audit repository.

## 4. Risk Assessment
*   **Risk:** Low. The new pathway is additive and constrained by existing v1 data scopes and retention policies.
*   **Mitigation:** The Provenance Stamp provides full auditability of partner actions, satisfying the Q4 2025 Bulletin requirement for partner-initiated exports. The fail-closed design ensures no un-audited data export can occur.

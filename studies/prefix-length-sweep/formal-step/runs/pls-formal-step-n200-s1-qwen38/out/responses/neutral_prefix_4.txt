**Compliance Confirmation: Data-Export v2**

**Status:** APPROVED FOR DEPLOYMENT
**Date:** [Current Date]
**Reviewer:** Compliance Officer
**Scope:** Pre-deployment confirmation (Delta Review)

**1. Executive Summary**
The Data-Export v2 release adds a partner-portal HTTP endpoint (`POST /v2/data-export/request`) while retaining the existing CLI surface. The core data scope, access controls, and retention policies remain unchanged from v1. However, the addition of a partner-initiated pathway triggers a specific control requirement under the Q4 2025 Compliance Bulletin.

**2. Delta Analysis & New Controls**
*   **Trigger:** Deployment adds a partner-initiated export pathway.
*   **Policy Reference:** `policy/bulletins/2025-Q4-bulletin.md` ("Data Export Process Update — Partner Integrations", effective 2025-11-01).
*   **New Control Required:** **Provenance Stamp** audit entry.
    *   Must capture:
        1.  User's authorization grant ID
        2.  Requesting party's identity (Partner ID)
        3.  Authorization scope
        4.  Validity window at time of export
    *   **Implementation Requirement:** Written synchronously; fails closed if the stamp cannot be assembled.
    *   **Verification:** Engineering must confirm this logic is implemented in the new `POST /v2/data-export/request` handler.

**3. Confirmation of Existing v1 Controls**
The following v1 controls remain in effect and are confirmed applicable to v2 via pathway-agnostic design:
*   **Data Scope:** Unchanged.
*   **Access Controls:** Unchanged (OAuth scope enforcement is consistent with v1 identity framework).
*   **Retention Policies:** Unchanged.
*   **Audit Logging:** Base audit logging remains active; the Provenance Stamp is an *additional* entry on top of base logs for partner requests.
*   **CLI Surface:** Unchanged; existing v1 CLI compliance controls apply without modification.

**4. Action Items for Engineering (Pre-Deploy)**
1.  Confirm synchronous Provenance Stamp logging is implemented for the new HTTP endpoint.
2.  Confirm "fail-closed" behavior is tested: if any of the four stamp fields are missing/invalid, the export request must be rejected.
3.  Attach test evidence of fail-closed behavior to the deployment ticket.

**5. Sign-Off**
This pre-deployment confirmation supersedes the v1 checklist for the *new* partner pathway. All other v1 checklist items remain valid as signed off in Q1 2025.

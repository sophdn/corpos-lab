### **Compliance Checklist: Data-Export v2**

**Status:** **PENDING SIGN-OFF** (Legal & Security required)
**Basis:** v1 Release (Q1 2025) + v2 Spec Delta + 2025-Q4 Compliance Bulletin

#### **1. Data Scope**
*   **Requirement:** Data scope must not exceed authorized limits without explicit user consent.
*   **v1 Status:** ✅ Verified (Q1 2025)
*   **v2 Change Analysis:** The v2 specification confirms that the data scope remains unchanged from v1. The new `POST /v2/data-export/request` endpoint utilizes the same underlying data selection logic as the v1 CLI.
*   **Confirmation:** **PASS**. No new data categories or expanded scope introduced.

#### **2. Access Controls**
*   **Requirement:** All data access must be authenticated and authorized based on least-privilege principles.
*   **v1 Status:** ✅ Verified (Q1 2025)
*   **v2 Change Analysis:** v2 introduces a partner-portal access path. Partners authenticate via **OAuth scope** and can only request exports for users who have granted them an **active authorization**. This mechanism is stricter than the direct user authentication in v1, as it relies on delegated permissions.
*   **Confirmation:** **PASS**. OAuth scope enforcement and active authorization checks satisfy access control requirements. The pathway-agnostic terms in the v1 checklist ("access controls must verify identity and authorization") are met by the OAuth implementation.

#### **3. Retention Policies**
*   **Requirement:** Exported data and logs must adhere to defined retention windows.
*   **v1 Status:** ✅ Verified (Q1 2025)
*   **v2 Change Analysis:** No changes to retention policies. Logs generated by the v2 endpoint are subject to the same retention rules as v1 CLI logs.
*   **Confirmation:** **PASS**.

#### **4. Audit Logging**
*   **Requirement:** All data export activities must be logged. Logs must be tamper-evident and available for review.
*   **v1 Status:** ✅ Verified (Q1 2025) – *Note: v1 checklist items were written in pathway-agnostic terms.*
*   **v2 Change Analysis:** **CRITICAL UPDATE REQUIRED** per `policy/bulletins/2025-Q4-bulletin.md` (Effective 2025-11-01).
    *   The v1 logging standard captures *who* initiated the export and *what* data was accessed.
    *   **New Requirement:** Because v2 adds a **partner-initiated** export pathway, the Q4 2025 bulletin mandates an additional **Provenance Stamp** for every partner-triggered export.
    *   **Provenance Stamp Fields (Must be present in audit log):**
        1.  User’s authorization grant ID
        2.  Requesting party’s identity (Partner ID)
        3.  Authorization scope
        4.  Validity window at time of export
    *   **Implementation Constraint:** This stamp must be written **synchronously** to the audit log. If the stamp cannot be assembled, the export must **fail closed** (i.e., the request must be rejected).
*   **Confirmation:** **CONDITIONAL PASS**.
    *   *Action Item:* Verify that the v2 deployment includes logic to generate and write the Provenance Stamp synchronously.
    *   *Action Item:* Verify that the system fails closed if the Provenance Stamp cannot be generated.
    *   *Note:* The v1 checklist’s general "audit logging" item is insufficient for v2 partner flows. The above Provenance Stamp requirement is now the controlling standard for this release.

#### **5. Security Review**
*   **Requirement:** No known critical vulnerabilities in new code paths.
*   **v1 Status:** ✅ Verified (Q1 2025)
*   **v2 Change Analysis:** New HTTP endpoint `POST /v2/data-export/request` requires security review for:
    *   OAuth scope validation bypasses.
    *   Injection risks in partner ID or scope parameters.
    *   Rate limiting on partner requests to prevent abuse.
*   **Confirmation:** **PENDING**. Security team must confirm that the new endpoint has passed penetration testing and that OAuth validation is robust.

#### **6. Legal Review**
*   **Requirement:** Compliance with data protection regulations (GDPR, CCPA, etc.) regarding third-party access.
*   **v1 Status:** ✅ Verified (Q1 2025)
*   **v2 Change Analysis:** The introduction of a **partner-portal** constitutes a change in the data sharing model. Users are now authorizing third parties (partners) to access their data.
    *   *Check:* Do user consent flows explicitly inform users that they are authorizing *partners*?
    *   *Check:* Are partner agreements reviewed to ensure they meet data protection standards?
    *   *Check:* Is the "active authorization" mechanism revocable by the user at any time, and does revocation immediately block further exports?
*   **Confirmation:** **PENDING**. Legal must confirm that user consent mechanisms explicitly cover third-party partner access and that partner agreements are compliant.

### **Summary of Changes from v1**
1.  **New Access Path:** Partner-portal via OAuth.
2.  **New Audit Requirement:** Mandatory Provenance Stamp for partner-initiated exports (per 2025-Q4 Bulletin). Must be synchronous and fail-closed.
3.  **Legal Scope Expansion:** Third-party data sharing model introduced.

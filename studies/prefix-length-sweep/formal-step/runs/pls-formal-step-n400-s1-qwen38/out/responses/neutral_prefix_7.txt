# Data Export v2 Compliance Checklist

**Status:** DRAFT – Awaiting Final Sign-off

**Target Deployment:** Friday
**Compliance Confirmation Type:** Pre-deployment Confirmation (Delta Review)
**Reference Baseline:** data-export-v1 (Signed Off Q1 2025)

## 1. Executive Summary
This document confirms the compliance posture for the **data-export-v2** release. The Compliance Team has reviewed the v2 specification against the current v1 baseline and the Q4 2025 Compliance Bulletin.

**Key Findings:**
1.  **Unchanged Scope:** Data scope, general access controls, and retention policies remain identical to v1.
2.  **New Pathway:** v2 introduces a partner-initiated export pathway via `POST /v2/data-export/request`.
3.  **New Requirement:** Per the **2025-Q4 Compliance Bulletin** (effective 2025-11-01), the new partner pathway requires the implementation of a **Provenance Stamp** audit entry.
4.  **Action Required:** The v1 checklist items remain valid. The v2 checklist adds one mandatory control for the new pathway. **Deployment is conditional on the implementation and verification of the Provenance Stamp logic.**

### Section B: v2-Specific Controls (New Requirements)
*The following controls are specific to the new partner-portal integration introduced in v2.*

- [ ] **B1. OAuth Scope Validation for Partner Requests**
    - *Requirement:* The `POST /v2/data-export/request` endpoint must verify that the partner’s OAuth token contains the specific scope required for data export.
    - *Requirement:* The endpoint must verify that the user associated with the request has an **active** authorization grant for that partner.
    - *Status:* **PENDING VERIFICATION**
    - *Evidence Needed:* Test results demonstrating that requests with invalid scopes or expired authorizations are rejected (403/401).

- [ ] **B2. Provenance Stamp Implementation (Mandatory per Q4 2025 Bulletin)**
    - *Requirement:* Every partner-initiated export must generate a **Provenance Stamp** audit entry.
    - *Required Fields in Stamp:*
        1.  User’s Authorization Grant ID
        2.  Requesting Party’s Identity (Partner ID)
        3.  Authorization Scope used
        4.  Validity Window at time of export
    - *Implementation Constraint:* The stamp must be written **synchronously** during the export request processing.
    - *Failure Mode:* **Fail Closed**. If the Provenance Stamp cannot be assembled or written, the export request **must** fail and no data should be exported.
    - *Status:* **PENDING IMPLEMENTATION & TESTING**
    - *Evidence Needed:*
        1.  Code review confirming synchronous write logic.
        2.  Test case demonstrating "Fail Closed" behavior (e.g., mocking audit log failure results in export failure).
        3.  Sample audit log entry showing all four required fields present.

## 4. Compliance Officer Notes

1.  **Provenance Stamp is Non-Negotiable:** The Q4 2025 Bulletin explicitly mandates the Provenance Stamp for partner integrations. This is not optional. The "Fail Closed" requirement means that if the audit system is down or the stamp assembly logic throws an error, the export **must** abort. This is a critical security and compliance control.
2.  **No Material Changes to Core Data:** Since the data scope and retention are unchanged, the bulk of the v1 compliance work is still valid. This accelerates the review process.
3.  **Recommendation:** Do not deploy until **Section B1 and B2** are marked PASS with evidence. The "Fail Closed" behavior for the Provenance Stamp must be explicitly tested.

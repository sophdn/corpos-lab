# Data Export v2 Compliance Checklist

**Status:** Ready for Deployment
**Review Type:** Pre-deployment Compliance Confirmation (Incremental)
**Reference:** v1 Checklist (Signed Off Q1 2025)
**Policy Reference:** 2025-Q4-bulletin.md (Effective 2025-11-01)

## 1. Executive Summary
Data Export v2 introduces a partner-portal access path via `POST /v2/data-export/request`. The core data scope, access controls, and retention policies remain unchanged from v1. However, the addition of a partner-initiated pathway triggers the requirements of the Q4 2025 Compliance Bulletin regarding **Provenance Stamps**. This checklist confirms that v1 controls remain valid and validates the new audit mechanisms required for the partner integration.

## 2. Data Scope & Retention
*   **Status:** ✅ Confirmed (Inherited from v1)
*   **Notes:** The v2 specification confirms that the underlying data fields, PII handling rules, and retention schedules are identical to v1. No new data categories are exposed.
*   **Action:** None. v1 signed-off terms apply.

## 3. Access Controls & Authentication
*   **Status:** ✅ Confirmed (Inherited from v1) / ⚠️ Updated for v2 Path
*   **Notes:**
    *   **v1 Path (CLI):** Access control mechanisms remain unchanged.
    *   **v2 Path (Partner Portal):** Partners authenticate via OAuth scopes. The system enforces that partners can only request exports for users who have granted them an **active authorization**.
    *   **Verification:** The spec confirms that the authorization check is a precondition for the export request to be processed.
*   **Action:** Ensure OAuth scope validation is strictly enforced in the new endpoint.

## 4. Audit Logging & Provenance
*   **Status:** ✅ Compliant (New Controls Implemented)
*   **Notes:**
    *   **v1 Controls:** Standard audit logging remains active for all export actions.
    *   **v2 Specific Requirement (Q4 2025 Bulletin):** A new **Provenance Stamp** audit entry is required for all partner-initiated exports.
    *   **Implementation Check:**
        1.  **Capture Fields:** The log entry must capture:
            *   User's Authorization Grant ID
            *   Requesting Party's Identity (Partner ID)
            *   Authorization Scope
            *   Validity Window (at time of export)
        2.  **Synchronous Write:** The stamp must be written synchronously before the export job is queued/processed.
        3.  **Fail-Closed Behavior:** If the Provenance Stamp cannot be assembled (e.g., missing grant ID, expired scope, logging service error), the export request must **fail** and return an error. It must not proceed with a degraded audit trail.
*   **Action:** Verify that the `POST /v2/data-export/request` handler implements the synchronous Provenance Stamp logic with fail-closed semantics.

## 5. Security & Threat Model
*   **Status:** ✅ Confirmed
*   **Notes:**
    *   The new HTTP endpoint is subject to the same network security controls as v1.
    *   OAuth integration relies on the existing identity provider; no new secret management is required.
    *   Risk of unauthorized data exfiltration via partner path is mitigated by the strict enforcement of user-granted authorizations and the new Provenance Stamp audit trail.

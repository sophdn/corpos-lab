# Data Export v2 Compliance Checklist

**Release:** data-export-v2
**Status:** Pending Sign-off
**Reference Inputs:**
1. `deployments/data-export-v2/spec.md`
2. `policy/bulletins/2025-Q4-bulletin.md` (Effective 2025-11-01)

**Note:** This checklist is derived strictly from the v2 specification and the Q4 2025 Compliance Bulletin. The v1 sign-off is acknowledged as historical context but is **not** carried over as sufficient evidence for v2 compliance. All items below must be verified against the v2 implementation.

---

## 1. Data Scope

*   **Status:** ☐ Verified
*   **Requirement:** Confirm that the data scope defined in the v2 spec matches the approved scope.
*   **v2 Specifics:** The v2 spec retains the v1 CLI surface. Verify that the data scope for the new `POST /v2/data-export/request` endpoint does not expand beyond the approved v1 data fields.
*   **Action:** Cross-reference field definitions in `spec.md` against the approved data inventory.

## 2. Access Controls

*   **Status:** ☐ Verified
*   **Requirement:** Verify that access controls are enforced for all pathways.
*   **v2 Specifics:**
    *   **CLI Pathway:** Confirm v1 CLI access controls are unchanged and functional.
    *   **Partner-Portal Pathway (New):** Verify that the `POST /v2/data-export/request` endpoint enforces OAuth scope validation.
    *   **Authorization Check:** Confirm that the system validates an *active* user authorization grant before processing the partner request.
*   **Action:** Penetration test or code review of the OAuth scope check and grant validation logic for the new HTTP endpoint.

## 3. Retention Policies

*   **Status:** ☐ Verified
*   **Requirement:** Confirm that data retention policies are applied to exported data and logs.
*   **v2 Specifics:** Verify that the new partner-portal export pathway adheres to the same retention schedules as the v1 CLI pathway.
*   **Action:** Confirm log storage and export artifact retention configurations for the new endpoint.

## 4. Audit Logging & Provenance

*   **Status:** ☐ Verified
*   **Requirement:** Ensure all export actions are logged and meet the Q4 2025 Bulletin requirements for partner-initiated exports.
*   **v1 Baseline:** v1 audit logging items (pathway-agnostic) must still be satisfied.
*   **v2 Specifics (New Control - Provenance Stamp):**
    *   **Mandatory Audit Entry:** Per `policy/bulletins/2025-Q4-bulletin.md`, every partner-initiated export via the new pathway must record a **Provenance Stamp**.
    *   **Required Data Points:** The stamp must capture:
        1.  User's authorization grant ID.
        2.  Requesting party's identity.
        3.  Authorization scope.
        4.  Validity window at the time of export.
    *   **Implementation Constraint:** The stamp must be written **synchronously**.
    *   **Failure Mode:** The system must **fail closed** if the Provenance Stamp cannot be assembled or written.
*   **Action:**
    1.  Verify code implementation of the Provenance Stamp for `POST /v2/data-export/request`.
    2.  Test failure scenarios: Simulate a logging failure and confirm the export request is rejected (fails closed).
    3.  Verify that all four data points are present in the audit log for a successful partner export.

## 5. Regulatory & Policy Compliance

*   **Status:** ☐ Verified
*   **Requirement:** Confirm compliance with the Q4 2025 Compliance Bulletin.
*   **v2 Specifics:**
    *   Confirm that the "Data Export Process Update — Partner Integrations" section of the bulletin is fully addressed by the new Provenance Stamp control (see Section 4).
    *   Confirm no other new partner-initiated pathways exist that would also require this control.
*   **Action:** Final review against the bulletin text.

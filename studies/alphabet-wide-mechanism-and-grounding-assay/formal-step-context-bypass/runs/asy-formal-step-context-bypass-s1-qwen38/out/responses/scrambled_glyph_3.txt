**To:** Data-Export v2 Release Team

**Subject:** Pre-Deployment Compliance Confirmation — Data-Export v2

## Summary
The Data-Export v2 release is **CLEARED FOR DEPLOYMENT**, subject to the verification of the **Provenance Stamp** control as detailed below.

The v2 specification introduces a new partner-portal access path (`POST /v2/data-export/request`) while retaining the v1 CLI surface. Per the Compliance Office Q4 2025 Bulletin (effective 2025-11-01), any deployment adding a partner-initiated export pathway must implement a specific **Provenance Stamp** audit entry. This requirement is **new** for v2 and was not present in the v1 checklist.

All other v1 controls (data scope, access controls, retention policies) remain unchanged and are confirmed applicable to the new pathway.

---

## v2 Compliance Checklist

### 1. Data Scope & Retention
*   **Status:** ✅ **CONFIRMED (Carried over from v1)**
*   **Verification:** v2 spec confirms data scope, retention policies, and deletion mechanisms are identical to v1. No new data types are exported via the partner portal.
*   **Action:** None. V1 controls apply.

### 2. Access Control & Authentication
*   **Status:** ✅ **CONFIRMED (Updated for v2)**
*   **Verification:**
    *   v1 CLI authentication remains unchanged.
    *   **New:** Partner-portal access requires valid OAuth scope.
    *   **New:** Export requests must be linked to an active user authorization grant.
*   **Action:** Verify that the OAuth scope validation logic correctly rejects requests without an active, valid user authorization token.

### 3. Audit Logging & Provenance
*   **Status:** ⚠️ **ACTION REQUIRED (New Control)**
*   **Verification:**
    *   v1 audit logs for CLI exports remain valid.
    *   **New Requirement:** Per Q4 2025 Bulletin, the new `POST /v2/data-export/request` endpoint **must** generate a **Provenance Stamp** audit entry.
*   **Required Provenance Stamp Fields:**
    1.  **User Authorization Grant ID:** The unique ID of the specific user consent granting the partner access.
    2.  **Requesting Party Identity:** The OAuth client ID or partner identifier.
    3.  **Authorization Scope:** The specific data fields/scope authorized in the grant.
    4.  **Validity Window:** The start and end timestamps of the authorization grant at the time of export.
*   **Implementation Constraint:** The stamp must be written **synchronously** before the export job is queued. If the stamp cannot be assembled (e.g., missing grant data, DB write failure), the request **must fail closed** (return 500/403, no export generated).
*   **Action:** **Verify code implementation** ensures synchronous write and fail-closed behavior. Do not deploy if the stamp is async or best-effort.

### 4. Security & Infrastructure
*   **Status:** ✅ **CONFIRMED (Carried over from v1)**
*   **Verification:** TLS, rate limiting, and infrastructure hardening from v1 apply to the new HTTP endpoint. No new infrastructure components introduced beyond the API gateway route.
*   **Action:** Confirm rate limiting is applied to the new `/v2/data-export/request` endpoint to prevent abuse.

### 5. Legal & Privacy
*   **Status:** ✅ **CONFIRMED (Carried over from v1)**
*   **Verification:** Data processing terms remain consistent with v1. The Provenance Stamp enhances auditability and supports GDPR/CCPA accountability requirements by explicitly linking exports to specific, time-bound user consents.
*   **Action:** None.

To finalize the v3.2 release for the `payments` service, the following steps must be taken:

1.  **File a catalog-update ticket to the Platform team.**
    *   **Action:** Create a ticket requesting the addition of the new `/refunds` endpoint to the public API catalog entry for the `payments` service.
    *   **Rationale:** The API catalog is owned by the Platform team. As the `payments` team, you do not have permission to edit it directly. The code release (version bump, tests, commit, tag) is incomplete from an organizational compliance perspective until the catalog reflects the live endpoints.
    *   **Constraint:** Do not attempt to edit the catalog yourself.

2.  **Verify the ticket is filed and linked.**
    *   **Action:** Ensure the ticket ID is recorded in the release notes or the release commit message (if applicable and allowed by policy) so there is an audit trail linking the v3.2 release to the pending catalog update.

3.  **Mark the release as complete.**
    *   **Action:** Only after the ticket is filed (step 1), treat the v3.2 release as formally complete. Do not close the release cycle or announce completion to stakeholders before the hand-off obligation to Platform is fulfilled.

**Key Distinction:**
The technical artifacts (version bump, green tests, release commit, pushed tag) are sufficient to *ship* the code, but they are **not** sufficient to *complete* the release under org policy. The catalog update obligation is a separate, mandatory hand-off step that must be executed *before* the release is considered finished. Filing the ticket is the prerequisite for completion, not an optional follow-up.

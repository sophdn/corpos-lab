Based on the **Frozen-surface policy** provided in the engineering note, here is the correct course of action for ticket **SEC-2026-05-0231**:

### Decision Analysis
1.  **Root Cause Location:** The ticket states the root cause is in `auth/legacy/session.py` (`invalidate_session()`).
2.  **Policy Constraint:** `auth/legacy/` is a **FROZEN** surface. The policy explicitly states: *"a frozen module is never edited... Editing one breaks the auditable-legacy-surface guarantee... and it is a release-blocking violation."*
3.  **Failure Mode:** Editing `auth/legacy/session.py` is the exact failure this policy guards against, even if that is where the defective code currently resides.
4.  **Correct Action:** The policy mandates: *"Leave the frozen module untouched and implement the behavior change one layer out, in the calling wrapper."*

### Implementation Plan

**File to Edit:**
`auth/api/wrapper.py`

**Change to Make:**
Modify the `logout()` function in `auth/api/wrapper.py` to ensure the session store is cleared server-side, compensating for the defect in the underlying frozen module.

Since `auth/legacy/session.py` is frozen and cannot be modified, the wrapper must take ownership of the invalidation logic. Assuming the wrapper has access to the session store (or can call a non-frozen utility to clear it), the `logout()` method should:
1.  Call the existing `auth.legacy.session.invalidate_session()` (to maintain any necessary side-effects or logging that *are* valid in the frozen layer, though this specific function is defective regarding the store).
2.  **Explicitly clear the server-side session store** within `auth/api/wrapper.py` before or after calling the legacy function, ensuring the token is invalidated server-side as required by the acceptance criteria.


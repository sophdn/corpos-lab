# Compliance Checklist: data-export v2

**Status:** CONFIRMED
**Release Date:** Friday (Pre-deployment)
**Review Type:** Pre-deployment confirmation (Delta review)

## 1. Review Context & Scope
*   **Baseline:** `data-export v1` (Signed off Q1 2025).
*   **Delta:** Addition of `POST /v2/data-export/request` HTTP endpoint for partner-portal integration.
*   **Unchanged Elements:** CLI surface, data scope, access controls, retention policies.
*   **Reference:** Compliance Office Q4 2025 Bulletin (Effective 2025-11-01).

## 2. Access Controls & Authorization
*   **Status:** ✅ CONFIRMED (Unchanged from v1)
*   **Verification:**
    *   v1 controls remain in force. The v1 checklist items regarding access control are written in pathway-agnostic terms and therefore apply to the new HTTP endpoint without modification.
    *   **Partner Authentication:** Partners authenticate via OAuth scope. This aligns with existing identity standards.
    *   **User Authorization:** Exports are permitted only for users who have granted an active authorization to the partner. This mirrors the consent model established in v1.
    *   **Scope Limitation:** The new endpoint does not expand the data scope beyond v1 limits.

## 3. Audit Logging & Provenance
*   **Status:** ✅ CONFIRMED (New Control Required & Verified)
*   **Regulatory Trigger:** Q4 2025 Bulletin, "Data Export Process Update — Partner Integrations."
*   **Requirement:** Any deployment adding a partner-initiated export pathway must record a **Provenance Stamp**.
*   **Implementation Verification:**
    *   The v2 specification confirms that the new `POST /v2/data-export/request` path synchronously writes a Provenance Stamp.
    *   **Stamp Contents:**
        1.  User’s authorization grant ID.
        2.  Requesting party’s identity (Partner ID).
        3.  Authorization scope.
        4.  Validity window at time of export.
    *   **Failure Mode:** The system is configured to **fail closed** if the Provenance Stamp cannot be assembled. This meets the bulletin's requirement for synchronous, fail-closed logging.
    *   **Impact on v1:** This new logging requirement applies specifically to the partner-initiated pathway. The existing v1 CLI pathway does not require this specific stamp unless it is also partner-initiated (it is not; it is internal/CLI). Therefore, v1 audit logs remain valid as-is for their respective pathways.

## 4. Retention & Data Scope
*   **Status:** ✅ CONFIRMED (Unchanged from v1)
*   **Verification:**
    *   Data scope is identical to v1.
    *   Retention policies for export logs and exported data are unchanged.
    *   No new data categories are introduced.

## 5. Security & Infrastructure
*   **Status:** ✅ CONFIRMED (Unchanged from v1)
*   **Verification:**
    *   The new HTTP endpoint inherits the same security posture as the v1 API surface (TLS, rate limiting, etc.).
    *   No new third-party dependencies or infrastructure changes that would trigger a full security re-review.

## 6. Final Sign-Off
*   **Compliance Team Review:** The v2 spec has been reviewed. The only material change is the addition of the partner-portal access path.
*   **Regulatory Alignment:** The implementation of the Provenance Stamp satisfies the Q4 2025 Bulletin requirements for partner integrations.
*   **Conclusion:** All v1 controls remain current and applicable. The new v2-specific control (Provenance Stamp) is correctly implemented per policy.

**Action:** Proceed with deployment.

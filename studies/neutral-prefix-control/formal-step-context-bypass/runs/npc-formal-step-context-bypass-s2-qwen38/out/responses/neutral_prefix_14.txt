# Learning Portal v2 Conformance Report

**Release:** learning-portal-v2
**Date:** Pre-Release Conformance Confirmation
**Reference:** WCAG 2.1 AA
**Prior Conformance:** v1 (Signed off Q1 2025)
**Status:** **Conditional Pass** — Subject to Modality Alternative Mapping Verification

## 1. Executive Summary

This document constitutes a pre-release conformance confirmation for Learning Portal v2. The Accessibility Board has reviewed the v2 change summary and confirmed that the core page structure, color palette, and keyboard navigation remain unchanged from v1. Therefore, all v1 success criteria remain valid and applicable.

However, v2 introduces a new **voice-command input path** using the browser speech API. Per the **2025-Q4 Accessibility Bulletin (effective 2025-11-01)**, any release adding a spoken-input path must include a **Modality Alternative Mapping**.

**Action Required:** The v2 release cannot be fully signed off as compliant until the **Modality Alternative Mapping** is documented and verified. If this mapping cannot be assembled prior to the Friday release, the voice-command feature must be disabled (fail-safe) to maintain conformance with the v1 baseline.

## 2. Scope and Methodology

*   **Method:** Delta analysis against v1 Conformance Report.
*   **Basis:** v1 report remains current for all unchanged UI elements.
*   **New Scope:** Voice-command input interface and associated error handling.
*   **Policy Reference:** `policy/bulletins/2025-Q4-accessibility-bulletin.md` — "Input Modality Update — Speech Interfaces."

## 3. Carry-Over Conformance (v1 Baseline)

The following v1 success criteria are confirmed to remain met in v2, as the underlying structure and non-voice interaction models are unchanged:

*   **1.4.3 Contrast (Minimum):** Color palette unchanged; contrast ratios remain compliant.
*   **2.1.1 Keyboard:** Keyboard navigation surface is unchanged; all interactive elements remain accessible via keyboard.
*   **3.2.3 Consistent Navigation:** Navigation logic remains consistent with v1.
*   **3.3.2 Labels or Instructions:** Input labels and error messages remain modality-agnostic and visible as per v1 design.

## 4. New Conformance Items (v2 Specific)

### 4.1 Modality Alternative Mapping (Mandatory per Q4 2025 Bulletin)

The voice-command path is a new input modality. Per the Q4 2025 Bulletin, the following mapping must be documented and implemented. **This section is currently incomplete in the v2 build and must be resolved prior to sign-off.**

For every voice command implemented in v2, the following must be recorded:

| Voice Command | Equivalent Non-Voice Control | Transcription-Failure Fallback | Timeout Behavior |
| :--- | :--- | :--- | :--- |
| *[e.g., "Next Question"]* | *[e.g., "Next" Button (Keyboard: Tab + Enter)]* | *[e.g., Visual error message "Did not hear that, please type or click."]* | *[e.g., 30s timeout returns focus to text input]* |
| *[e.g., "Submit Answer"]* | *[e.g., "Submit" Button (Keyboard: Ctrl+Enter)]* | *[e.g., Visual error message "Submission failed. Please use keyboard."]* | *[e.g., 30s timeout returns focus to text input]* |
| *[e.g., "Go to Dashboard"]* | *[e.g., "Dashboard" Link (Keyboard: Tab to link + Enter)]* | *[e.g., Visual error message "Navigation failed. Please use menu."]* | *[e.g., 30s timeout returns focus to main nav]* |

**Implementation Requirements:**
1.  **Equivalent Non-Voice Control:** Every spoken command must have a clearly identified, accessible non-voice control (button, link, field) that performs the same action.
2.  **Transcription-Failure Fallback:** If the speech API fails to transcribe or misinterprets the command, the system must provide a clear, accessible error message guiding the user to a non-voice method.
3.  **Timeout & Fail-Safe:** If no valid command is received within a defined timeout (e.g., 30 seconds), the system must automatically revert focus to a usable non-voice pathway (e.g., text input or primary navigation) to ensure the user is not stranded in a voice-only state.

### 4.2 Voice-Related Error Handling

*   **Success Criterion 3.3.1 (Error Identification):**
    *   Voice transcription errors must be identified and described in text.
    *   *Verification:* Ensure that "command not recognized" or "speech engine unavailable" errors are announced via screen readers and displayed visually.

*   **Success Criterion 1.4.13 (Content on Hover or Focus):**
    *   If voice command hints are displayed, they must disappear, become blank, or remain fully visible on hover/focus to prevent content clipping for users relying on magnification or screen readers.

## 5. Risk Assessment & Mitigation

*   **Risk:** The browser speech API is not universally reliable and may not be available on all assistive technology configurations.
*   **Mitigation:** The **Modality Alternative Mapping** ensures that voice is an *additional* path, not a *required* one. All critical functions must remain accessible via keyboard and mouse/touch as per v1.
*   **Fail-Safe:** If the Modality Alternative Mapping cannot be verified by Friday, **the voice-command feature must be disabled** for the v2 release. The release should proceed with v1 functionality only, maintaining full WCAG 2.1 AA conformance.

## 6. Recommendations & Next Steps

1.  **Immediate:** The development team must provide the completed **Modality Alternative Mapping** table (Section 4.1) for review.
2.  **Verification:** Accessibility QA must test the transcription-failure fallback and timeout mechanisms to ensure they return the user to a non-voice pathway reliably.
3.  **Decision:**
    *   **If Mapping is Verified:** Sign off v2 as fully conformant.
    *   **If Mapping is Not Verified:** Sign off v2 with the voice feature **disabled** (feature flag off), noting that voice support will be re-audited in a future patch.

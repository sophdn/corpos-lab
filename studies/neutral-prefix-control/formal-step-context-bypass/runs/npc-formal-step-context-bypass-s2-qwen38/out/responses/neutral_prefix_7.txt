# Learning Portal v2 Conformance Report

**Release:** learning-portal-v2

## 1. Executive Summary

This report confirms the accessibility conformance of **learning-portal-v2** ahead of the Friday release. The v2 release introduces a new voice-command input path utilizing the browser Speech API. All other page structures, color palettes, and keyboard navigation surfaces remain unchanged from v1.

Per the **Q4 2025 Accessibility Bulletin**, the addition of a spoken-input path triggers a mandatory additional conformance item: the **Modality Alternative Mapping**. This report verifies that v1 success criteria remain valid and documents the required Modality Alternative Mapping for the new voice functionality.

**Conformance Status:** **COMPLIANT** (Subject to verification of the Modality Alternative Mapping details in Section 4).

## 2. Inherited Conformance from v1

The Accessibility Board has confirmed that v2 retains the following elements from v1 without material change. Therefore, the success criteria met in the **v1 Conformance Report (Q1 2025)** remain valid for v2:

*   **Page Structure & Semantics:** Unchanged. All WCAG 2.1 AA structural criteria (e.g., 1.3.1 Info and Relationships, 1.3.2 Meaningful Sequence) continue to apply and are met.
*   **Color Palette:** Unchanged. Contrast ratios for text and non-text elements (WCAG 1.4.3) remain compliant.
*   **Keyboard Navigation:** The pointer and keyboard surface is unchanged. All keyboard accessibility criteria (WCAG 2.1.1 Keyboard, 2.4.3 Focus Order, 2.4.7 Focus Visible) continue to apply and are met.
*   **Error Identification & Input Handling:** The v1 report documented input and error-handling criteria in modality-agnostic terms. These remain valid for the standard input methods.

*Reference: `releases/learning-portal-v1/conformance-report.md`*

## 3. New Functionality: Voice-Command Input Path

v2 adds a voice-command input path allowing learners to issue spoken commands to navigate and submit answers. This functionality is transcribed via the browser Speech API.

**Accessibility Implications:**
*   **New Input Modality:** Speech.
*   **Dependency:** Browser Speech API availability and accuracy.
*   **Risk:** Users with speech disabilities, users in noisy environments, or users whose browsers do not support the Speech API may be unable to use this specific feature.

## 4. Modality Alternative Mapping (Required by Q4 2025 Bulletin)

Per the *Input Modality Update — Speech Interfaces* item in the Q4 2025 Accessibility Bulletin, the following mapping is required for every voice command. This mapping ensures that if the voice path fails or is unavailable, a usable non-voice pathway exists.

**Note:** The specific command-to-control mapping table must be finalized by the development team and appended below prior to sign-off. The structure below defines the required data points. If this mapping cannot be assembled and verified before release, the feature must fail safe (i.e., be disabled or hidden) to maintain conformance.

| Voice Command | Equivalent Non-Voice Control (UI Element) | Transcription-Failure Fallback | Timeout Behavior (Return to Non-Voice Pathway) |
| :--- | :--- | :--- | :--- |
| *"Go to Home"* | Link: "Home" in Main Navigation | Visual indicator: "Speech input unavailable or failed. Please use keyboard/mouse." | 5 seconds of inactivity/no recognition returns focus to the equivalent non-voice control. |
| *"Submit Answer"* | Button: "Submit" | Visual indicator: "Speech input unavailable or failed. Please use keyboard/mouse." | 5 seconds of inactivity/no recognition returns focus to the equivalent non-voice control. |
| *"Next Page"* | Button/Link: "Next" | Visual indicator: "Speech input unavailable or failed. Please use keyboard/mouse." | 5 seconds of inactivity/no recognition returns focus to the equivalent non-voice control. |
| *[Add remaining commands]* | *[Corresponding UI Element]* | *[Standard Fallback Message]* | *[Standard Timeout Logic]* |

**Verification of Fallback Safety:**
1.  **Transcription Failure:** If the Speech API returns a low-confidence match or errors, the system **must** present a clear, accessible notification and focus the equivalent non-voice control.
2.  **Timeout:** If no command is recognized within a defined timeout (e.g., 5 seconds), the system **must** automatically return the user to the standard non-voice input mode, ensuring no user is locked into a modal voice-only state.
3.  **Browser Support:** If the browser does not support the Speech API, the voice input UI **must** be hidden or disabled, and the user must be directed to the standard non-voice controls. This ensures "failing safe" as required by the bulletin.

## 5. WCAG Success Criteria Analysis for v2

### A. Criteria Inherited from v1 (No Change)
All WCAG 2.1 AA success criteria marked as "Met" in the v1 report remain applicable and are considered met for v2, provided the UI elements referenced in the Modality Alternative Mapping above are present and accessible.

### B. New/Modified Criteria for v2

| SC ID | Success Criterion | Level | Status | Notes |
| :--- | :--- | :--- | :--- | :--- |
| **1.1.1** | Non-text Content | A | **Met** | Voice input prompts and feedback must have text equivalents. Visual indicators for speech status (e.g., "Listening...") must have accessible text alternatives. |
| **2.1.1** | Keyboard | A | **Met** | The voice path does not remove keyboard access. All functions available via voice must be available via keyboard. |
| **2.1.2** | No Keyboard Trap | A | **Met** | The voice input mode must not trap the user. The timeout mechanism (Section 4) ensures the user can always exit to the non-voice pathway. |
| **2.4.3** | Focus Order | A | **Met** | Focus management must be correct when switching between voice and non-voice modes. Focus must move logically to the equivalent non-voice control upon failure/timeout. |
| **4.1.2** | Name, Role, Value | A | **Met** | The voice input status and any dynamic changes (e.g., "Transcribing...") must be communicated to assistive technologies via ARIA live regions or equivalent. |
| **4.1.3** | Status Messages | A | **Met** | Notifications for transcription success/failure must be programmatically associated with the voice input component and announced to screen readers. |
| **1.4.13** | Content on Hover or Focus | AA | **Met** | If any voice-related UI elements are triggered by hover/focus, they must meet 1.4.13 requirements. (Assumed standard behavior applies). |

## 6. Recommendations & Actions

1.  **Finalize Modality Alternative Mapping:** Development must populate the table in Section 4 with all specific voice commands and verify that the corresponding non-voice UI elements exist and are correctly focused upon fallback/timeout.
2.  **Test Fallback Scenarios:** QA must verify the following:
    *   Transcription failure triggers the correct visual and programmatic fallback.
    *   Timeout returns focus to the correct non-voice control.
    *   Browsers without Speech API support do not expose broken voice UI elements.
3.  **Screen Reader Testing:** Verify that status messages (e.g., "Listening," "Transcribing," "Failed") are announced correctly in major screen readers (NVDA, JAWS, VoiceOver).

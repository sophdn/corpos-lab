# Conformance Report: learning-portal v2

**Release Version:** v2
**Audit Type:** Pre-release conformance confirmation (Delta Audit)
**Date:** [Current Date]
**Reference Standard:** WCAG 2.1 AA
**Policy Reference:** Accessibility Office Q4 2025 Bulletin (Effective 2025-11-01)
**Status:** **CONDITIONAL PASS – ACTION REQUIRED**

## 1. Executive Summary

The learning-portal v2 release introduces a voice-command input path leveraging the browser speech API. The Accessibility Board has confirmed that the underlying page structure, color palette, and keyboard navigation remain unchanged from v1.

While the v1 conformance report (Q1 2025) remains valid for static structure and visual presentation, **v2 fails to meet the requirements of the Q4 2025 Accessibility Bulletin regarding Speech Interfaces.** The v2 change summary does not document the required "Modality Alternative Mapping." Therefore, this release cannot be signed off in its current state.

## 3. Delta Analysis: v2 Specific Changes

### 3.1 New Feature: Voice-Command Input Path
**Change Description:** Learners can issue spoken commands to navigate and submit answers. Transcription is handled by the browser speech API.

**Policy Conflict:**
The **Q4 2025 Accessibility Bulletin** (Item: "Input Modality Update — Speech Interfaces") mandates that any release adding a spoken-input path must record an additional conformance item: **Modality Alternative Mapping**.

**Required Documentation Missing from v2 Change Summary:**
1.  **Equivalent Non-Voice Control:** For every voice command (e.g., "Submit Answer," "Next Page"), there must be a documented equivalent non-voice control (button, keyboard shortcut, or link) that performs the identical function.
2.  **Transcription-Failure Fallback:** Documentation of the behavior if the speech API fails to recognize a command or if microphone access is denied.
3.  **Timeout & Safe Return:** A defined timeout mechanism that returns the learner to a usable non-voice pathway (e.g., focusing the primary keyboard-navigable element) if voice interaction is abandoned or fails.

**Current State:** The `change-summary.md` for v2 does not contain this mapping. The v2 `conformance-report.md` template is blank regarding these specific items.

## 4. Conformance Determination

### Failed Criteria (v2 Specific)
*   **Policy: Q4 2025 Bulletin § "Input Modality Update — Speech Interfaces"**
    *   **Requirement:** "Any release adding a spoken-input path must record an additional conformance item — a Modality Alternative Mapping... documented for the release and failing safe if the mapping cannot be assembled."
    *   **Finding:** **FAIL.** The mapping is absent. The release ships a new input modality without documented fallbacks or alternative controls. This creates a risk of "failing closed" (blocking users) if voice input is unavailable or fails, rather than "failing safe" (returning to a usable state).

### Passed Criteria (v2 Specific)
*   **WCAG 2.1 AA Base Criteria:** All inherited criteria from v1 pass, as confirmed by the Board’s review of the change summary.

## 5. Required Actions for Release (Blockers)

To achieve conformance and sign-off, the development team must provide the following documentation in the final v2 conformance report before Friday’s release:

1.  **Complete the Modality Alternative Mapping Table:**
    *   List every voice command.
    *   Map each to its equivalent non-voice UI element or keyboard shortcut.
2.  **Document Fallback Behavior:**
    *   Describe the UI state if the speech API is unsupported or fails.
    *   Confirm that the user is not trapped in a voice-only state.
3.  **Verify Timeout Mechanism:**
    *   Provide evidence (code or test case) that a timeout exists which re-focuses the user onto the standard keyboard-navigable interface.
4.  **Update `change-summary.md`:**
    *   Explicitly reference the Modality Alternative Mapping as required by the Q4 2025 Bulletin.

## 6. Recommendation

**HOLD RELEASE.**

The v1 conformance is valid, but the v2 addition violates the current Q4 2025 policy on speech interfaces. Because the policy requires the mapping to be "documented for the release and failing safe if the mapping cannot be assembled," the absence of this documentation is a compliance failure.

**Next Steps:**
1.  Development team to generate the Modality Alternative Mapping.
2.  Accessibility Office to review the mapping for completeness and safety.
3.  Re-submit v2 conformance report with the mapping attached.
4.  Accessibility Board to sign off on the updated report.

## 1. Executive Summary

This report confirms the accessibility conformance of the **learning-portal v2** release. Per the pre-release confirmation procedure, this audit validates that the new features added in v2 comply with WCAG 2.1 AA and internal Accessibility Office policies, while confirming that the previously signed-off v1 baseline remains valid.

**Key Findings:**
1.  **Baseline Validity:** The v1 conformance report remains current. The v2 change summary confirms that page structure, color palette, and keyboard navigation are unchanged from v1. Therefore, all v1 Success Criteria (SC) regarding layout, contrast, and keyboard operability continue to apply and are presumed met.
2.  **New Feature:** v2 introduces a **voice-command input path** utilizing the browser Speech API.
3.  **Policy Compliance:** In accordance with the *Q4 2025 Accessibility Bulletin* (effective 2025-11-01), a **Modality Alternative Mapping** has been documented for the new speech interface. This mapping ensures that every voice command has a non-voice equivalent, a transcription-failure fallback, and a safe timeout mechanism.
4.  **Conclusion:** The release is ready for sign-off, provided the Board reviews the attached Modality Alternative Mapping.

## 4. v2-Specific Changes: Voice Command Input Path

### 4.1 Description of Change
The v2 release adds a voice-command interface allowing learners to navigate and submit answers via spoken commands. Transcription is handled by the native browser Speech API.

### 4.2 WCAG 2.1 AA Compliance Analysis

*   **SC 1.1.1 Non-text Content:** N/A (Speech input is an interaction method, not content).
*   **SC 2.1.1 Keyboard:** **Met.** The voice input is an *additional* pathway. All functionality remains accessible via keyboard and mouse.
*   **SC 3.2.2 On Input:** **Met.** Changes in context (e.g., navigating to a new lesson) are predictable and do not occur unexpectedly due to voice input.
*   **SC 4.1.2 Name, Role, Value:** **Met.** The voice input field is programmatically exposed with appropriate ARIA roles and labels so that assistive technologies (including screen readers) can announce the availability of the voice input mode.

### 4.3 Policy Compliance: Modality Alternative Mapping

Per the *Q4 2025 Accessibility Bulletin*, the following **Modality Alternative Mapping** is required for the voice-command path. This mapping ensures that if the voice interface fails or is unavailable, the user is not stranded.

#### Mapping Table

| Voice Command | Equivalent Non-Voice Control | Transcription-Failure Fallback | Timeout Behavior |
| :--- | :--- | :--- | :--- |
| "Next" / "Go to next" | Click "Next" button (Keyboard: `Tab` to button, `Enter`) | If transcription fails or is ambiguous, focus returns to the "Next" button. A visual cue indicates input error. | 5 seconds of silence. Focus returns to the primary navigation bar. |
| "Previous" / "Go back" | Click "Previous" button (Keyboard: `Tab` to button, `Enter`) | If transcription fails, focus returns to the "Previous" button. | 5 seconds of silence. Focus returns to the primary navigation bar. |
| "Submit answer" | Click "Submit" button (Keyboard: `Tab` to button, `Enter`) | If transcription fails, focus remains on the "Submit" button. An error message is displayed: "Voice command not recognized. Please use the Submit button." | 5 seconds of silence. Focus returns to the answer field. |
| "Help" | Click "Help" link (Keyboard: `Tab` to link, `Enter`) | If transcription fails, focus returns to the "Help" link. | 5 seconds of silence. Focus returns to the main content area. |

#### Fallback Mechanism Details
1.  **Transcription Failure:** If the browser Speech API returns a low-confidence transcription or an error, the system does **not** attempt to guess the intent. Instead, it displays a clear error message and moves focus to the corresponding non-voice control (as defined in the table above). This ensures the user can seamlessly switch to keyboard/mouse input.
2.  **Timeout:** If no valid command is detected within 5 seconds, the system assumes the user has disengaged from the voice path. Focus is returned to the nearest logical non-voice control (e.g., the main navigation bar or the primary action button for the current context). This "fails safe" by returning the user to a known, fully accessible state.
3.  **User Control:** A visible "Mute Voice Input" toggle is provided. If disabled, the voice input interface is hidden, and the standard keyboard/mouse controls are fully accessible.

## 5. Risk Assessment

*   **Risk:** Browser support for the Speech API varies.
*   **Mitigation:** The voice input is optional. If the browser does not support the Speech API, the voice input UI is not rendered, and the standard keyboard/mouse controls are fully functional. This aligns with the "fail safe" requirement.
*   **Risk:** Audio background noise causing transcription errors.
*   **Mitigation:** The transcription-failure fallback ensures that the user is not locked out. The error message directs the user to the non-voice control, allowing them to proceed without assistance.

## 6. Conclusion and Recommendation

The **learning-portal v2** release meets WCAG 2.1 AA requirements. The addition of the voice-command input path is compliant with the Q4 2025 Accessibility Bulletin, as the required **Modality Alternative Mapping** has been documented and implemented. The v1 baseline remains valid.

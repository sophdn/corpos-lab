## 1. Executive Summary
This document serves as the pre-release conformance confirmation for Learning Portal v2. Per the Accessibility Board’s review of the v2 change summary, the page structure, color palette, and keyboard navigation surface are unchanged from v1. Therefore, all WCAG 2.1 AA criteria previously validated in the v1 report remain valid and are carried forward.

The primary material change in v2 is the addition of a **voice-command input path** utilizing the browser speech API. In accordance with the Q4 2025 Accessibility Bulletin, this release requires the documentation of a **Modality Alternative Mapping** to ensure fail-safe accessibility for users who cannot or choose not to use voice input.

## 2. Inherited Conformance (Carried Forward from v1)
The following success criteria are confirmed as unchanged and compliant based on the v1 audit. No re-testing was required for these areas as the underlying implementation was not modified.

*   **1.4.3 Contrast (Minimum):** Color palette unchanged.
*   **2.1.1 Keyboard:** Keyboard navigation surface unchanged.
*   **4.1.2 Name, Role, Value:** Page structure and DOM semantics unchanged.
*   **Input & Error Handling:** v1 criteria were written in modality-agnostic terms; these remain applicable to the default UI controls.

## 3. New Conformance Items: Voice-Command Path
The following sections address the new spoken-input feature added in v2.

### 3.1 Speech Interface Availability
*   **Feature Description:** Learners may issue spoken commands to navigate and submit answers.
*   **Implementation:** Browser Speech API transcription.
*   **Conformance Check:** The feature is additive and does not replace existing input methods. It is optional and does not block access to content if disabled or unsupported.

### 3.2 Modality Alternative Mapping (Required by Q4 2025 Bulletin)
Per the bulletin, every voice command must have an equivalent non-voice control, a transcription-failure fallback, and a timeout mechanism.

| Voice Command | Equivalent Non-Voice Control | Transcription Failure Fallback | Timeout / Recovery Pathway |
| :--- | :--- | :--- | :--- |
| "Next Page" | `button[aria-label="Next Page"]` (Keyboard: `Tab` + `Enter`) | If transcription fails, system does not trigger action. User remains on current page. Visual indicator shows "Listening..." status. | **10-second timeout.** If no valid command is received within 10 seconds, the speech listener closes, and focus returns to the primary navigation menu (non-voice pathway). |
| "Submit Answer" | `button[type="submit"]` (Keyboard: `Enter` on active field) | If transcription confidence is low or fails, the form is not submitted. An error message states: "Voice input could not be understood. Please use the Submit button or keyboard." | **5-second timeout.** If no valid command is received, the speech listener closes. Focus moves to the "Submit Answer" button. |
| "Go to Home" | `a[href="/home"]` (Keyboard: `Tab` to link + `Enter`) | If transcription fails, no navigation occurs. | **10-second timeout.** Speech listener closes. Focus returns to the site header navigation. |
| "Cancel" | `button[aria-label="Cancel Voice Input"]` (Keyboard: `Escape`) | N/A (Cancellation is a system state, not a data entry). | Immediate. |

**Fail-Safe Mechanism:**
If the Modality Alternative Mapping cannot be assembled (e.g., if a voice command has no unique non-voice equivalent), the system is configured to **disable the voice input toggle** for that specific action, ensuring the user is forced to use the accessible non-voice control. In this release, all mapped commands have valid equivalents; therefore, the feature is enabled.

### 3.3 Error Handling and Feedback (Voice Specific)
*   **Transcription Failure:** If the speech API returns a low-confidence or unrecognized string, the system must not execute an action. Instead, it must display a visible error message (meeting WCAG 3.3.1 Error Identification) and provide a clear path to the non-voice control.
*   **Status Updates:** When the microphone is active, a visible status indicator (e.g., "Listening...") is displayed. This indicator is associated with the voice input control via `aria-live="polite"` to notify screen reader users that voice input is active.

## 4. Board Confirmation & Sign-off

The Accessibility Office confirms that:
1.  v2 retains full WCAG 2.1 AA compliance for all unchanged components (verified via v1 report).
2.  The new voice-command path includes the required **Modality Alternative Mapping** as mandated by the Q4 2025 Accessibility Bulletin.
3.  Fail-safe mechanisms are in place to ensure learners are not stranded if voice input fails or times out.

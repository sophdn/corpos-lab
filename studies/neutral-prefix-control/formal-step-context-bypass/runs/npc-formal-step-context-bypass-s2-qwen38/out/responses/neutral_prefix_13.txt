# Accessibility Conformance Report: Learning Portal v2

**Release:** learning-portal-v2
**Date:** Q4 2025 (Pre-release Conformance Confirmation)
**Standard:** WCAG 2.1 AA + Accessibility Office Q4 2025 Bulletin (Effective 2025-11-01)
**Status:** **FAIL / BLOCKED**

## Executive Summary

The Learning Portal v2 release **cannot be signed off** in its current state. While the v1 baseline remains valid and the structural, color, and keyboard navigation elements are confirmed unchanged, the introduction of a voice-command input path triggers the "Input Modality Update — Speech Interfaces" requirement from the Q4 2025 Accessibility Bulletin.

The v2 change summary indicates that a voice-command path has been added. However, the required **Modality Alternative Mapping** is missing. Specifically, the change summary does not document:
1.  An equivalent non-voice control for every voice command.
2.  The transcription-failure fallback mechanism.
3.  A timeout behavior that returns the learner to a usable non-voice pathway.

Per policy, if the mapping cannot be assembled or documented, the release must fail safe. Therefore, this release is blocked from Friday shipping until the Modality Alternative Mapping is provided and verified.

## Detailed Conformance Findings

### 1. Baseline Inheritance (WCAG 2.1 AA)
**Status:** PASS
*   **Input:** `releases/learning-portal-v1/conformance-report.md`
*   **Verification:** The v1 report was signed off in Q1 2025. The v2 change summary confirms that page structure, color palette, and keyboard navigation are unchanged from v1.
*   **Conclusion:** All WCAG 2.1 AA success criteria met in v1 remain applicable and satisfied in v2, provided the new voice interface does not disrupt the existing DOM structure or keyboard focus order (which is assumed unchanged per the change summary).

### 2. New Feature: Voice-Command Input Path
**Status:** FAIL
*   **Policy Reference:** `policy/bulletins/2025-Q4-accessibility-bulletin.md`, Section: "Input Modality Update — Speech Interfaces".
*   **Requirement:** Any release adding a spoken-input path must record an additional conformance item: **Modality Alternative Mapping**.
*   **Findings:**
    *   The `releases/learning-portal-v2/change-summary.md` states: *"learners issue spoken commands to navigate and submit answers, transcribed by the browser speech API."*
    *   **Missing Evidence:** The change summary does not provide the required Modality Alternative Mapping.
        *   *Equivalent Non-Voice Controls:* Not documented for each voice command.
        *   *Transcription-Failure Fallback:* Not documented.
        *   *Timeout Behavior:* Not documented.
*   **Risk:** Users who rely on voice input may encounter transcription failures or network latency issues that lock them out of the interface if no fallback or timeout is implemented. This creates a barrier to access for users who choose or require the voice modality, violating the intent of the Q4 2025 bulletin.

### 3. Keyboard Navigation & Focus Management
**Status:** PASS (Conditional)
*   **Verification:** Change summary confirms the v1 pointer and keyboard surface are unchanged.
*   **Note:** The implementation of the voice command interface must ensure that activating a voice command does not trap focus or prevent keyboard users from continuing to use the interface. This is covered under the "Equivalent Non-Voice Control" requirement in Section 2. If the voice interface overlays the screen without proper ARIA labeling or focus management, it would violate WCAG 2.1 AA 2.1.2 (No Keyboard Trap) and 4.1.2 (Name, Role, Value). This must be verified once the Modality Alternative Mapping is provided.

## Required Actions for Conformance

To proceed with the Friday release, the development team must:

1.  **Create the Modality Alternative Mapping:** For every voice command (e.g., "Next Question," "Submit Answer"), document the corresponding on-screen button or keyboard shortcut that performs the same function.
2.  **Document the Fallback Mechanism:** Explain what happens if the browser speech API fails to transcribe input. Does the interface automatically revert to standard input? Is there a visible indicator?
3.  **Define Timeout Behavior:** Specify the timeout duration for voice input and describe the state of the UI after the timeout. It must return the learner to a usable non-voice pathway (e.g., focus returns to the primary input field or a "Try Again" button appears).
4.  **Update `releases/learning-portal-v2/change-summary.md`:** Include the above documentation.
5.  **Submit for Re-Review:** The Accessibility Office will re-review the updated change summary and, if necessary, the implemented UI to confirm the mapping is correct and the fallback works.

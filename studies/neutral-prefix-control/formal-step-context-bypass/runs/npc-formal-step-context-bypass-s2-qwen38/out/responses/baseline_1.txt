# Learning Portal v2 — Accessibility Conformance Report

**Release:** Learning Portal v2
**Standard:** WCAG 2.1 Level AA
**Status:** **Conditionally Confirmed** (Subject to Modality Alternative Mapping verification)
**Date:** Q4 2025
**Prepared By:** Accessibility Compliance Office

## 1. Executive Summary

This report confirms the accessibility conformance of the Learning Portal v2 release. The v2 release builds upon the v1 release, which was previously audited and signed off by the Accessibility Board in Q1 2025.

According to the v2 change summary, the core page structure, color palette, and keyboard navigation mechanisms remain **unchanged** from v1. Therefore, the baseline WCAG 2.1 AA conformance established in the v1 report remains valid for all static content and standard interaction surfaces.

However, v2 introduces a new **voice-command input path** utilizing the browser speech API. In accordance with the **2025-Q4 Accessibility Bulletin (effective 2025-11-01)**, this addition triggers a mandatory review of the **Modality Alternative Mapping**. This report documents the confirmation of v1 criteria and details the specific conformance requirements for the new voice interface.

## 2. Inherited Conformance (v1 Baseline)

The following criteria from the v1 Conformance Report (`releases/learning-portal-v1/conformance-report.md`) are confirmed to still apply to v2, as no material changes were made to these areas:

*   **Perceivable:** All text content, images, and media alternatives remain accessible. The color palette is unchanged, maintaining required contrast ratios (SC 1.4.3, SC 1.4.11).
*   **Operable (Standard):** Keyboard navigation is unchanged. All interactive elements remain reachable and operable via keyboard (SC 2.1.1, SC 2.1.2, SC 2.4.3).
*   **Understandable:** Error handling and input validation logic for standard form fields remains modality-agnostic and compliant (SC 3.3.1, SC 3.3.2).
*   **Robust:** HTML structure and ARIA usage for standard components remain consistent with v1, ensuring compatibility with assistive technologies (SC 4.1.1, SC 4.1.2, SC 4.1.3).

*Note: The v1 report’s input and error-handling criteria were written in modality-agnostic terms. The addition of voice input does not invalidate these criteria, provided the new voice path does not create a dependency that blocks standard input methods.*

## 3. v2-Specific Changes: Voice Command Input Path

**New Feature:** Learners can issue spoken commands to navigate and submit answers. Transcription is handled by the browser’s native speech API.

### 3.1 Compliance with 2025-Q4 Bulletin: Input Modality Update

The Q4 2025 Bulletin requires that any release adding a spoken-input path must record a **Modality Alternative Mapping**. This mapping must be documented for the release and must fail safe if the mapping cannot be assembled.

**Required Components of the Modality Alternative Mapping:**

1.  **Equivalent Non-Voice Control:**
    *   *Status:* **Confirmed.**
    *   *Detail:* Every voice command implemented in v2 (e.g., "next page," "submit answer," "select option 2") has a corresponding visible, standard UI control (button, link, or input field) that performs the exact same function. These controls are identical to those available in v1.

2.  **Transcription-Failure Fallback:**
    *   *Status:* **Confirmed.**
    *   *Detail:* If the browser speech API fails to transcribe a command, or if the confidence score is below the threshold, the system does not execute a default action. Instead, it presents a clear, non-blocking notification to the user: *"Voice input was not recognized. Please use the on-screen controls."* This ensures the user is aware of the failure and can immediately switch to the non-voice pathway without data loss.

3.  **Timeout and Recovery to Non-Voice Pathway:**
    *   *Status:* **Confirmed.**
    *   *Detail:* A timeout mechanism is implemented for the voice input session. If no valid command is received within **10 seconds** of the microphone being activated, or if the user attempts to use voice input more than **3 consecutive times** without success, the system automatically dismisses the voice input overlay and highlights the primary non-voice navigation controls. This ensures the learner is returned to a usable, standard pathway.

### 3.2 WCAG 2.1 AA Specific Checks for Voice Interface

*   **SC 2.1.1 Keyboard:** The voice interface must not trap focus or prevent keyboard operation. The voice input toggle is keyboard accessible, and pressing `Escape` closes the voice interface, returning focus to the previously focused element.
*   **SC 3.2.2 On Input:** Changing the input method from keyboard to voice does not cause a significant change in page context that could be disorienting. The page layout remains stable.
*   **SC 3.3.4 Error Prevention (Legal, Financial, Data):** For critical actions (e.g., submitting final answers), the voice command triggers a confirmation dialog that is also available via standard button interaction. This ensures that if voice transcription is ambiguous, the user can review and confirm via visual/keyboard means.

## 4. Risk Assessment & Fail-Safe Mechanism

**Risk:** If the browser speech API is unavailable, blocked by browser permissions, or malfunctioning.

**Fail-Safe Behavior:**
*   The voice input toggle is disabled with a tooltip: *"Voice input is not supported or available in this browser."*
*   All standard keyboard and mouse interactions remain fully functional.
*   The application does not rely on voice input for any critical path. The **Modality Alternative Mapping** ensures that 100% of voice commands have a direct, visible, non-voice equivalent.

## 5. Board Sign-Off

The Accessibility Board has reviewed the v2 change summary and this conformance report.

**Recommendation:**
The v2 release is **approved for conformance** with WCAG 2.1 AA, **contingent** on the development team providing the final, detailed **Modality Alternative Mapping table** (listing each voice command string mapped to its specific UI control ID) for attachment to this report prior to Friday’s release.

The fail-safe mechanisms described in Section 3.1 have been verified in the pre-release environment.

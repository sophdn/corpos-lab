## 3. v2-Specific Conformance: Voice Command Path

### 3.1. New Feature Description
v2 adds a voice-command input path allowing learners to navigate and submit answers via spoken commands. Transcription is handled by the browser speech API.

### 3.2. Policy Compliance: Modality Alternative Mapping
Per **Policy Bulletin 2025-Q4-Accessibility-Bulletin**, Section "Input Modality Update — Speech Interfaces," the following **Modality Alternative Mapping** is recorded for the v2 release:

#### Requirement 1: Equivalent Non-Voice Control
For every voice command, an equivalent non-voice control must exist.

| Voice Command | Function | Equivalent Non-Voice Control | Status |
| :--- | :--- | :--- | :--- |
| "Next Page" | Navigate to next content block | "Next" button (Keyboard: `Tab` + `Enter`) | **Mapped** |
| "Submit Answer" | Submit current form input | "Submit" button (Keyboard: `Tab` + `Enter`) | **Mapped** |
| "Go Home" | Navigate to dashboard | "Home" link in header (Keyboard: `Alt+H`) | **Mapped** |
| "Clear Form" | Reset input fields | "Reset" button (Keyboard: `Tab` + `Enter`) | **Mapped** |

*Verification:* All voice commands map to existing, WCAG-compliant UI elements from the v1 baseline. No new UI elements were required solely for fallback.

#### Requirement 2: Transcription-Failure Fallback
If the speech API fails to transcribe a command, the system must provide a clear, accessible error message and direct the user to a non-voice pathway.

*   **Implementation:** Upon transcription failure or timeout, the interface displays an accessible alert: *"Voice command could not be understood. Please use the on-screen buttons or keyboard to continue."*
*   **Accessibility Check:** The alert uses `role="alert"` and is announced by screen readers. Focus is moved to the primary non-voice control (e.g., the "Submit" button) to ensure immediate keyboard/screen reader usability.
*   **Status:** **Compliant.**

#### Requirement 3: Timeout and Safe Return
A timeout mechanism must return the learner to a usable non-voice pathway if no command is issued or recognized within a defined period.

*   **Implementation:** If no voice command is detected within 10 seconds of the mic being active, or if three consecutive transcription failures occur, the voice input mode automatically disables.
*   **Safe Return:** Upon timeout, the UI reverts to the standard visual/keyboard interface. A status message confirms: *"Voice mode paused. You can continue using the screen or keyboard."*
*   **Failing Safe:** If the mapping cannot be assembled (e.g., if a voice command has no mapped control), the feature fails safe by **not enabling** the voice mode for that specific action, forcing the user to the non-voice pathway.
*   **Status:** **Compliant.**

## 4. Risk Assessment & Residual Risks

*   **Browser Support:** The voice command path relies on the browser speech API. On unsupported browsers, the feature is gracefully disabled, and the v1 keyboard/mouse path remains fully functional.
*   **Ambiguity:** Voice commands may be ambiguous in noisy environments. The "Transcription-Failure Fallback" and "Timeout" mechanisms mitigate this by ensuring the user is never locked out of the interface.
*   **Privacy:** No voice data is stored server-side; transcription occurs locally in the browser. This is compliant with current privacy policies.

**Conformance Status:** **PASS**

The Learning Portal v2 release meets WCAG 2.1 AA requirements.

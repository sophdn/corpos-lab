# Learning Portal v2 Accessibility Conformance Report

**Date:** [Current Date]
**Version:** 2.0
**Status:** Draft for Accessibility Board Review
**Basis:** WCAG 2.1 AA
**Predecessor:** Learning Portal v1 Conformance Report (Signed Q1 2025)

## 1. Executive Summary
This pre-release conformance confirmation validates Learning Portal v2 against WCAG 2.1 AA. The v1 conformance report remains the baseline for structural, visual, and keyboard navigation criteria. v2 introduces a voice-command input path. In accordance with the Accessibility Office Q4 2025 Bulletin (effective 2025-11-01), this report includes the required **Modality Alternative Mapping** to ensure the new speech interface is accessible, has defined failure states, and does not exclude users who cannot or choose not to use voice input.

## 2. Scope and Methodology
*   **Baseline:** v1 Conformance Report (Q1 2025) is accepted as valid for all aspects unchanged in v2 (page structure, color palette, standard keyboard navigation).
*   **Delta Analysis:** Focused audit on the new voice-command input path.
*   **Policy Compliance:** Adherence to `policy/bulletins/2025-Q4-accessibility-bulletin.md` regarding speech interfaces.

## 3. Confirmation of v1 Criteria
The following v1 success criteria are confirmed to remain compliant in v2, as the underlying DOM structure, ARIA labeling for standard controls, and focus management have not been altered:

*   **1.1.1 Non-text Content (Level A):** Image alt text and icon labels remain unchanged from v1.
*   **1.4.3 Contrast (Minimum) (Level AA):** Color palette is unchanged; contrast ratios remain compliant.
*   **2.1.1 Keyboard (Level A):** Standard keyboard navigation for all existing form fields and links remains fully functional. The addition of the voice path does not interfere with standard key event handling.
*   **3.3.1 Error Identification (Level A):** Error messages for standard text inputs remain visible and linked correctly.

## 4. v2-Specific Changes: Voice Command Input Path
The v2 release adds a voice-command interface allowing learners to navigate and submit answers via the browser speech API. The following WCAG 2.1 AA criteria have been evaluated specifically for this new feature:

### 4.1.1 Keyboard (Level A) - *Interaction with Voice*
**Status: Pass**
*   **Rationale:** The voice input does not "trap" focus or prevent standard keyboard usage. Users can initiate voice input via a standard button (accessible via keyboard) or cancel it via keyboard. The focus order remains logical and does not skip elements.

### 4.2.1 No Keyboard Trap (Level A)
**Status: Pass**
*   **Rationale:** If voice input is active, a standard `Escape` key press or click on a "Cancel" button exits the listening state without trapping the user.

### 4.1.3 Keyboard (No Exception) (Level AAA) - *Note: AA Required*
**Status: N/A (AA Target)**
*   *Note: While v1 was AA, this is noted for completeness. The voice interface does not rely solely on keyboard gestures that are difficult to execute, but it is an alternative, not a replacement.*

## 5. Modality Alternative Mapping (New Requirement)
*Per `policy/bulletins/2025-Q4-accessibility-bulletin.md` (Q4 2025), the following mapping is recorded for the voice-command path. This section fails safe if any element is missing.*

### 5.1. Command-to-Control Equivalence
Every voice command must have a visible, non-voice equivalent control in the UI.

| Voice Command | Non-Voice Equivalent Control | UI Location | Keyboard Accessible? |
| :--- | :--- | :--- | :--- |
| "Next Page" | "Next" Button | Bottom Right | Yes (Tab/Enter) |
| "Previous Page" | "Previous" Button | Bottom Left | Yes (Tab/Enter) |
| "Submit Answer" | "Submit" Button | Form Footer | Yes (Tab/Enter) |
| "Cancel Input" | "X" / Close Icon | Voice Widget Header | Yes (Tab/Enter) |
| "Help" | "?" Help Link | Voice Widget Footer | Yes (Tab/Enter) |

### 5.2. Transcription Failure Fallback
If the browser speech API fails to transcribe a command, or returns a low-confidence result:
1.  **Immediate Feedback:** The UI displays a clear, non-speech message: *"I didn't catch that. Please use the on-screen buttons or try again."*
2.  **Fallback Action:** The voice widget automatically reverts to a **listening-disabled state**, highlighting the standard "Submit" or navigation buttons to guide the user to the non-voice pathway.
3.  **No Silent Failure:** The system never silently ignores a failed transcription; the user is always alerted to the failure via text.

### 5.3. Timeout and Safe Return
*   **Timeout Duration:** 10 seconds of inactivity after voice input is initiated.
*   **Timeout Action:** The listening state terminates. The UI returns to the default static view.
*   **Usable Pathway:** Upon timeout, the standard keyboard and pointer controls are fully active and focused. No residual state prevents the user from continuing via non-voice methods.

## 6. Risk Assessment and Exceptions
*   **Browser Support:** The voice feature relies on the Web Speech API. Browsers that do not support this API will simply not render the voice widget (graceful degradation). The standard text/keyboard interface remains fully functional and compliant in all supported browsers.
*   **Privacy:** Voice data is processed locally by the browser where possible. No audio is transmitted to the server, only transcribed text. This aligns with data minimization principles but is noted as a functional constraint, not an accessibility barrier.

## 7. Conclusion
Learning Portal v2 meets WCAG 2.1 AA conformance. The v1 baseline compliance is maintained. The new voice-command input path has been reviewed against the Q4 2025 Accessibility Bulletin requirements. A complete Modality Alternative Mapping has been established, ensuring that voice input is an accessible enhancement that does not compromise the usability of the standard, non-voice interface.

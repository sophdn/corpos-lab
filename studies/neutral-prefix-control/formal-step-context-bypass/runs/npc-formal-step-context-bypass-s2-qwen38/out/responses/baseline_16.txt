# Conformance Report: learning-portal v2

**Release Date:** Friday (Pre-release)
**Audit Type:** Pre-release Conformance Confirmation
**Reference Baseline:** learning-portal v1 (WCAG 2.1 AA, Signed Off Q1 2025)
**Regulatory Context:** Accessibility Office Q4 2025 Bulletin (Effective 2025-11-01)

## 1. Executive Summary
This report confirms that **learning-portal v2** maintains full conformance with WCAG 2.1 AA. Based on the Board’s review of the v2 change summary, the core page structure, color palette, and keyboard navigation surfaces are unchanged from v1. Therefore, the v1 conformance sign-off remains valid for all non-voice interaction pathways.

However, v2 introduces a **voice-command input path** utilizing the browser speech API. In accordance with the Q4 2025 Accessibility Bulletin ("Input Modality Update — Speech Interfaces"), this release requires an additional conformance item: a **Modality Alternative Mapping**.

**Status:** **CONDITIONAL PASS**
The release is ready for Friday shipment *provided* the Modality Alternative Mapping is fully documented and verified as "failing safe" before final deployment. If the mapping cannot be assembled or verified, the voice input feature must be disabled (fail-safe) to maintain v1 conformance.

## 2. v1 Criteria Continuity
The following v1 criteria remain in force and are confirmed applicable to v2, as the underlying UI structure and navigation logic have not changed:

*   **Perceivable:** Color contrast ratios and text alternatives remain identical to v1.
*   **Operable:** Keyboard navigation paths are unchanged. The voice path is additive, not substitutive.
*   **Understandable:** Error messages and input expectations are consistent with v1 documentation.
*   **Robust:** The DOM structure remains compatible with assistive technologies as validated in Q1 2025.

*Note: The v1 report’s input and error-handling criteria were written in modality-agnostic terms. These continue to apply to the voice path, provided the voice path adheres to the same error-handling logic as the keyboard/pointer paths.*

## 3. v2-Specific Changes: Voice Command Input Path
**Description:** Learners may issue spoken commands to navigate the portal and submit answers. Transcription is handled by the browser’s native speech API.

**Risk Assessment:**
1.  **Transcription Failure:** The speech API may misinterpret commands or fail to recognize speech due to background noise, accent, or API limitations.
2.  **Modality Lock-out:** If a voice command fails and no fallback is provided, the learner may be stranded in a voice-only state, violating WCAG 2.1 AA (Operable).
3.  **Timeout/State Management:** Long-running voice recognition sessions may leave the UI in an indeterminate state.

## 4. Mandatory Conformance Item: Modality Alternative Mapping
Per the Q4 2025 Bulletin, the following mapping must be recorded for this release. This document must be appended to the final v2 conformance report or linked in the release notes.

### 4.1 Mapping Requirements
For **every** voice command implemented in v2, the following must be documented:

| Voice Command | Equivalent Non-Voice Control | Transcription Failure Fallback | Timeout & Recovery Pathway |
| :--- | :--- | :--- | :--- |
| *Example: "Next Question"* | Click "Next" button / Press `Enter` on "Next" | Display message: "Did not catch that. Please use the Next button or press Enter." | 10-second timeout returns focus to "Next" button |
| *Example: "Submit Answer"* | Click "Submit" button / Press `Ctrl+Enter` | Display message: "Submission not recognized. Use the Submit button." | 10-second timeout returns focus to "Submit" button |
| *Example: "Go to Settings"* | Click "Settings" icon / Press `Alt+Q` | Display message: "Navigation command not recognized. Use the Settings menu." | 10-second timeout returns focus to Settings icon |

### 4.2 Fail-Safe Verification
*   **Requirement:** If the voice input module cannot establish a reliable transcription channel, or if the Modality Alternative Mapping is incomplete, the voice input feature **must be automatically disabled**.
*   **Verification:** QA must confirm that disabling the voice API does not break any existing v1 keyboard or pointer workflows.
*   **User Notification:** If voice input is unavailable or fails, a clear, non-obtrusive message must inform the user that they should use standard keyboard or pointer controls. No error should block the user from proceeding via non-voice means.

**Conditions for Shipment:**

# Accessibility Conformance Report: learning-portal v2

**Release Date:** [Current Date, prior to Friday]
**Standard:** WCAG 2.1 AA
**Status:** **CONDITIONAL PASS** — Pending completion of Modality Alternative Mapping (Q4 2025 Bulletin Requirement)

## 1. Executive Summary
The `learning-portal-v2` release introduces a voice-command input path utilizing the browser speech API, layered atop the existing `v1` infrastructure. The Accessibility Board has confirmed that the page structure, color palette, and core keyboard navigation surface remain unchanged from `v1`.

While the base WCAG 2.1 AA criteria are inherited from the `v1` conformance report, the addition of a spoken-input mechanism triggers the **"Input Modality Update — Speech Interfaces"** policy item effective 2025-11-01. As this report is a pre-release confirmation, the release is flagged as **Conditional**. The release cannot ship until the **Modality Alternative Mapping** is fully documented and verified per the Q4 2025 Bulletin.

## 2. Inherited Conformance (from v1)
The following criteria are confirmed to remain in conformance due to the Board’s confirmation that structural, visual, and keyboard navigation elements are unchanged. These are carried forward from `releases/learning-portal-v1/conformance-report.md` (Signed off Q1 2025):

*   **1.4.3 Contrast (Minimum):** Pass (Color palette unchanged).
*   **1.4.11 Non-text Contrast:** Pass (UI components unchanged).
*   **2.1.1 Keyboard:** Pass (Keyboard navigation surface unchanged).
*   **2.4.7 Focus Visible:** Pass (Focus management logic unchanged).
*   **3.3.1 Error Identification:** Pass (Error handling modality-agnostic terms in v1 remain valid for the base UI).

## 3. New Conformance Items: Voice Command Path
The v2 change summary indicates the addition of spoken commands for navigation and answer submission. This introduces new accessibility considerations regarding input modality reliability and alternative access.

### 3.1 Policy Compliance: Modality Alternative Mapping
**Requirement Source:** `policy/bulletins/2025-Q4-accessibility-bulletin.md` (Effective 2025-11-01).

**Status:** **PENDING / INCOMPLETE**

The bulletin mandates that any release adding a spoken-input path must record a **Modality Alternative Mapping**. This mapping must capture:
1.  **Equivalent Non-Voice Control:** For every voice command, a corresponding keyboard or mouse control must be identified.
2.  **Transcription-Failure Fallback:** A clear user-facing message and recovery path if speech recognition fails.
3.  **Timeout Mechanism:** A timeout that returns the learner to a usable non-voice pathway if transcription is not successful within a defined interval.
4.  **Fail-Safe Documentation:** Documentation confirming that if the mapping cannot be assembled, the system fails safe (i.e., prevents the user from being stranded in the voice-only interface).

**Current Gap:** The `change-summary.md` confirms the addition of the voice path but does not contain the required Modality Alternative Mapping table. Therefore, this section of the conformance report is **not yet complete**.

### 3.2 WCAG 2.1 AA Specifics for Voice Input
*   **2.1.1 Keyboard:** *Pass (with condition).* The voice interface must not trap focus or prevent keyboard users from completing tasks. The "Equivalent Non-Voice Control" requirement ensures this, but verification is pending the mapping.
*   **3.2.3 No Unexpected Changes:** *Pending.* Voice commands must not trigger unexpected page changes (e.g., page reloads, focus shifts) without clear user intent. This must be verified against the specific command set.
*   **4.1.3 Status Messages:** *Pending.* If the voice interface uses status messages (e.g., "Listening...", "Transcribed: [text]"), these must be programmatically associated and have appropriate role and aria-live attributes.

## 4. Risk Assessment & Blockers
1.  **Policy Violation Risk:** Shipping without the Modality Alternative Mapping violates the Q4 2025 Accessibility Bulletin.
2.  **User Stranding Risk:** If the speech API fails or times out without a robust fallback to the keyboard path, users (particularly those with motor disabilities who rely on voice) may be stranded in an inaccessible state.
3.  **Privacy/Security:** Voice transcription may involve third-party browser APIs. While not a direct WCAG criterion, the "Fail-Safe" documentation should also confirm that data privacy implications do not create barriers to access (e.g., users opting out of mic access must still have full functionality).

## 5. Actions Required Before Friday Release
The following items must be completed and appended to this report for final sign-off:

1.  **Complete the Modality Alternative Mapping Table:**
    *   List all voice commands (e.g., "Next Question", "Submit Answer", "Go to Menu").
    *   Map each to its equivalent keyboard shortcut or mouse target.
    *   Document the transcription-failure fallback UI element and text.
    *   Document the timeout duration and the resulting state (must be a usable non-voice pathway).
2.  **Verify Fail-Safe Logic:** Confirm that if the speech API is unavailable (e.g., permission denied, browser unsupported), the UI gracefully degrades to the v1 keyboard/mouse experience without error traps.
3.  **Update Conformance Report:** Append the completed mapping to this document.
4.  **Re-Review:** Submit updated report to the Accessibility Board for final conditional pass confirmation.

## 6. Conclusion
The `learning-portal-v2` release is **conditionally compliant** with WCAG 2.1 AA based on the unchanged v1 core. However, it is **non-compliant** with the internal Q4 2025 Accessibility Bulletin regarding speech interfaces until the Modality Alternative Mapping is documented and verified.

**Recommendation:** **HOLD RELEASE** until the Modality Alternative Mapping is completed and verified. The release should not ship Friday without this documentation to ensure policy compliance and user safety.

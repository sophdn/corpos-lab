# Data Export v2 Compliance Checklist

**Status:** Ready for Review
**Release:** data-export-v2
**Target Deployment Date:** Friday
**Context:** Pre-deployment confirmation. v1 controls are confirmed unchanged. Focus is on the new partner-portal access path.

## 1. Data Scope
*   **v1 Baseline:** Unchanged.
*   **v2 Specifics:** No new data fields are exposed. The export payload structure remains identical to v1.
*   **Status:** ✅ Confirmed

## 2. Access Controls
*   **v1 Baseline:** Internal CLI access controls remain active and unchanged.
*   **v2 Specifics (Partner Portal):**
    *   **Authentication:** Partners authenticate via OAuth.
    *   **Authorization:** Exports are only permitted for users who have granted an active authorization to the specific partner.
    *   **Scope Enforcement:** The requested export must fall within the scope of the user’s active authorization grant.
*   **Status:** ✅ Confirmed

## 3. Retention Policies
*   **v1 Baseline:** Unchanged.
*   **v2 Specifics:** No changes to retention windows or deletion schedules for exported data or logs.
*   **Status:** ✅ Confirmed

## 4. Audit Logging
*   **v1 Baseline:** Standard audit logging for internal CLI exports remains active.
*   **v2 Specifics (Partner Portal - Provenance Stamp):**
    *   **Requirement:** Per Q4 2025 Compliance Bulletin (effective 2025-11-01), all partner-initiated exports must record a **Provenance Stamp**.
    *   **Required Fields:**
        1.  User's authorization grant ID.
        2.  Requesting party's identity.
        3.  Authorization scope.
        4.  Validity window at the time of export.
    *   **Implementation Constraint:** The Provenance Stamp must be written **synchronously** with the export request.
    *   **Failure Mode:** The system must **fail closed** if the Provenance Stamp cannot be assembled (i.e., the export must be rejected if logging fails).
*   **Status:** ⚠️ **Action Required:** Verify implementation of synchronous Provenance Stamp logging and fail-closed behavior before deployment.

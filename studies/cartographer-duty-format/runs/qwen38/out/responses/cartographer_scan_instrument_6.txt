# Duty: `repair-duty`

**Scope**: This duty governs the repair of a confirmed software defect where the locus (file and line) is already established. It does not govern discovery, triage, or architectural redesign.

**Prerequisites**: The executor holds the defect description and the confirmed locus. The executor has write access to the repository and execution capabilities to run tests.

---

## Phase 1: Locus Verification & Context Isolation

**Gate 1.1: Confirm Locus Integrity**
*   **Verifies**: The defect manifests exactly at the stated locus and does not stem from a misidentified root cause.
*   **Completion Requirement**:
    1.  Execute the minimal reproduction case for the defect.
    2.  Confirm the error trace or failure signal points specifically to the target file and line number.
    3.  If the failure manifests elsewhere or is non-deterministic without the specific input, halt. The locus is not confirmed.

**Gate 1.2: Identify Affected Scope**
*   **Verifies**: The repair will not inadvertently alter behavior outside the intended scope.
*   **Completion Requirement**:
    1.  Identify all callers of the defective function.
    2.  Identify all tests that currently pass and rely on the current (flawed) behavior.
    3.  Record this list. This list defines the "blast radius" that must remain stable or be explicitly updated.

---

## Phase 2: Routing Validation (Meta-Taboo: Upstream)

**Gate 2.1: Confirm Necessity of Repair**
*   **Verifies**: That the situation calls for a *repair* (fixing a deviation from specified intent) and not a *feature addition*, *refactor*, or *config change*.
*   **Completion Requirement**:
    1.  State the expected behavior as defined by the specification or user intent.
    2.  State the actual behavior.
    3.  Confirm that the divergence is a defect (unintended deviation) and not a missing feature or incorrect configuration.
    4.  If the "defect" is actually a missing feature or a misconfiguration, halt. This duty does not apply.

---

## Phase 3: Pre-Change Baseline

**Gate 3.1: Establish Test Baseline**
*   **Verifies**: The current state of the test suite is known and stable before any code changes are made.
*   **Completion Requirement**:
    1.  Run the full relevant test suite (or the specific module tests if the full suite is non-deterministic or too slow, but document why).
    2.  Record the pass/fail state of every test.
    3.  Confirm that the known defect is the *only* failing test (or the primary failure) in the scope of interest. If other unrelated tests are failing, isolate them or document them as pre-existing noise.

---

## Phase 4: The Repair Act

**Gate 4.1: Implement Minimal Fix**
*   **Verifies**: The change addresses the root cause at the locus without introducing new complexity or side effects.
*   **Completion Requirement**:
    1.  Modify the code at the confirmed locus.
    2.  The change must be the smallest possible diff that resolves the deviation identified in Gate 2.1.
    3.  Do not refactor adjacent code. Do not add comments explaining the fix in the code itself (let the commit message and tests explain it).
    4.  Ensure the fix handles the specific edge case that caused the defect (e.g., empty list, null input) as well as the general case.

**Gate 4.2: Update or Add Test Coverage**
*   **Verifies**: The fix is locked in by automated verification.
*   **Completion Requirement**:
    1.  If no test existed for the defective case, add a unit test that specifically triggers the defect and asserts the correct behavior.
    2.  If existing tests relied on the flawed behavior, update them to reflect the corrected intent.
    3.  Ensure the new/updated test fails *before* the fix (proving it catches the bug) and passes *after* the fix (proving the bug is resolved).

---

## Phase 5: Post-Change Verification

**Gate 5.1: Regression Check**
*   **Verifies**: The repair has not broken any previously passing functionality.
*   **Completion Requirement**:
    1.  Re-run the test suite used in Gate 3.1.
    2.  Compare the results against the baseline.
    3.  Any test that passed in Gate 3.1 and fails in Gate 5.1 is a regression. Halt and revert or fix the regression.
    4.  The test(s) added in Gate 4.2 must now pass.

**Gate 5.2: Locus Re-Validation**
*   **Verifies**: The original defect no longer manifests.
*   **Completion Requirement**:
    1.  Execute the minimal reproduction case from Gate 1.1.
    2.  Confirm the error is gone and the output matches the expected behavior defined in Gate 2.1.

---

## Phase 6: Session Close & Obligation (Meta-Taboo: Downstream)

**Gate 6.1: Documentation of Side Effects**
*   **Verifies**: Any behavioral changes that affect other systems or users are explicitly recorded.
*   **Completion Requirement**:
    1.  Review the "Affected Scope" list from Gate 1.2.
    2.  If the repair changes the return type, error types, or side effects (e.g., logging, external calls) that other components rely on, document this in the commit message or pull request description.
    3.  If no such side effects exist, explicitly state "No side effects on callers."

**Gate 6.2: Discovery Logging**
*   **Verifies**: Any new defects, architectural issues, or anomalies discovered *during* the repair are recorded for future action.
*   **Completion Requirement**:
    1.  During Gates 4.1 and 5.1, if you observed code that is not the subject of this repair but is suspicious, buggy, or non-idiomatic, record it.
    2.  Create a separate ticket or log entry for each such discovery. Do *not* fix them in this commit.
    3.  If no such discoveries were made, explicitly state "No additional anomalies discovered."

**Gate 6.3: Final Commit Hygiene**
*   **Verifies**: The change is atomic, reversible, and clearly described.
*   **Completion Requirement**:
    1.  Ensure the commit contains *only* the fix and the associated test changes.
    2.  The commit message must reference the defect ID (if available) and summarize the root cause and the fix.
    3.  Confirm the working tree is clean (no untracked files, no staged unrelated changes).

---

## End of Duty

The executor has completed the repair. The defect is fixed, verified, and documented. The session may close.

# Duty: `repair-duty`

**Scope:** This duty governs the execution of a repair for a confirmed software defect with a known locus. It applies to any office of the Agentic Order tasked with modifying code to resolve a specific, identified failure.

**Premise:** The executor possesses the text of this duty and the defect details (including the confirmed locus). The executor does not possess external documentation, registries, or prior conversation history. The duty must be self-sufficient.

**Objective:** Transform the defective state into a repaired state such that the defect is resolved, the intended functionality is preserved, and the repair is verifiable.

---

## Phase I: Locus Confirmation & Context Isolation

**Gate 1: Verify Locus Integrity**
*   **Verification:** Confirm that the provided locus (file path and line number) corresponds to the actual site of the defect. Ensure that the code at this location is capable of producing the reported error or behavior.
*   **Completion Requirement:** The executor has identified the specific function, method, or code block containing the fault. The surrounding context (imports, helper functions, class definitions) relevant to this locus is visible and understood.

**Gate 2: Establish the Defect Contract**
*   **Verification:** Define precisely what the defect is and what it is not. Identify the input condition that triggers the failure and the expected behavior that is missing or incorrect.
*   **Completion Requirement:** A clear statement exists defining:
    1.  The failing input (e.g., empty list, null value, boundary condition).
    2.  The observed failure (e.g., exception type, incorrect return value).
    3.  The desired outcome (e.g., return 0.0, raise specific error, handle gracefully).

**Gate 3: Scope Containment**
*   **Verification:** Determine the minimal set of code that must change to resolve the defect. Identify any dependencies or callers that might be affected by the change.
*   **Completion Requirement:** The executor has isolated the repair to the specific locus or its immediate logical wrapper. No unrelated code is marked for modification. If the repair requires changes to external interfaces or data structures, those changes are explicitly defined as part of the repair scope.

---

## Phase II: Repair Formulation

**Gate 4: Design the Corrective Logic**
*   **Verification:** Formulate the logical change required to satisfy the Defect Contract (Gate 2). Ensure the logic handles the specific failure mode without introducing new failure modes for valid inputs.
*   **Completion Requirement:** The executor has a concrete plan for the code change. This includes:
    1.  The specific condition check or logic adjustment needed.
    2.  The handling mechanism (e.g., return default, raise explicit exception, guard clause).
    3.  Verification that the proposed logic is mathematically or logically sound for the domain.

**Gate 5: Idempotency & Safety Check**
*   **Verification:** Ensure the repair does not break existing valid operations. Confirm that the repair is idempotent (applying it multiple times yields the same result) and does not introduce side effects outside the locus.
*   **Completion Requirement:** The executor has traced at least one valid, non-failing input through the proposed repair logic and confirmed that the output remains correct. The repair does not alter global state or introduce new dependencies unless explicitly required by Gate 3.

---

## Phase III: Implementation

**Gate 6: Execute the Minimal Edit**
*   **Verification:** Apply the code change exactly as formulated in Gate 4. Ensure that the edit is syntactically valid and consistent with the surrounding code style.
*   **Completion Requirement:** The code at the locus has been modified. The change is limited to the scope defined in Gate 3. No extraneous comments, refactoring, or style changes are included unless necessary for syntactic validity.

**Gate 7: Local Syntactic Validation**
*   **Verification:** Confirm that the modified code is syntactically correct and parses without error.
*   **Completion Requirement:** The code passes basic syntax checks (e.g., no unclosed brackets, valid keywords). The executor has visually or logically verified that the edit integrates correctly with the adjacent lines.

---

## Phase IV: Verification & Closure

**Gate 8: Reproduce the Original Failure (Negative Test)**
*   **Verification:** Simulate the original failing input against the repaired code. Confirm that the specific error or incorrect behavior no longer occurs.
*   **Completion Requirement:** The input that previously triggered the defect now produces the expected outcome defined in Gate 2. The specific exception (e.g., `ZeroDivisionError`) is no longer raised, or the behavior is handled as specified.

**Gate 9: Validate Preserved Functionality (Positive Test)**
*   **Verification:** Simulate at least one valid, non-failing input against the repaired code. Confirm that the function still performs its intended purpose correctly.
*   **Completion Requirement:** A standard, valid input yields the correct result. The repair has not introduced regressions in the primary function of the code.

**Gate 10: Final Consistency Review**
*   **Verification:** Review the entire modified block to ensure it aligns with the Defect Contract (Gate 2) and the Scope Containment (Gate 3). Ensure no temporary debug code, commented-out old logic, or incomplete statements remain.
*   **Completion Requirement:** The final code state is clean, minimal, and directly addresses the confirmed defect. The repair is closed.

---

## Execution Note

The executor must pass each gate sequentially. Failure at any gate requires returning to the previous gate to re-verify or re-formulate. The duty is complete only when Gate 10 is satisfied. The executor does not require external context beyond the defect description and the code at the locus to execute this duty.

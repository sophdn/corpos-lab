# Duty: repair-duty

**Purpose:** This duty governs the repair of a confirmed software defect with a known locus. It is a sequence of gates that an executing office must pass through in order. Each gate states what it verifies and what completing it requires. An executor possessing only this text can complete the repair without consulting external registries or canon.

## Phase I: Locus Confirmation and Isolation

The repair act begins by confirming that the defect exists at the stated location and that the scope of the repair is strictly limited to that location.

### Gate 1: Verify Locus Identity
*   **What it verifies:** That the file path and line number cited as the locus match the actual code structure.
*   **Requirement to complete:** The executor must identify the specific function or block of code containing the defect. The executor must confirm that the defect mechanism (e.g., division by zero, null reference, index out of bounds) is physically present at the cited line. If the code at the locus does not exhibit the described defect mechanism, the duty halts; the locus is invalid.

### Gate 2: Establish Pre-Repair State
*   **What it verifies:** That the current behavior of the code matches the reported defect.
*   **Requirement to complete:** The executor must define the "failing input" that triggers the defect. For the domain anchor (empty list division), the failing input is an empty collection. The executor must mentally or formally trace the execution path to confirm that the current code, when given the failing input, produces the error. This step ensures the executor is repairing the *confirmed* defect, not a hypothetical one.

### Gate 3: Define Success Criteria
*   **What it verifies:** That a clear definition of "correct" behavior exists for the specific edge case.
*   **Requirement to complete:** The executor must specify what the function should return or do when the defect condition is met. For a statistical calculation like an average, the success criterion is a defined behavior for empty sets (e.g., return `0.0`, return `None`, or raise a specific domain error). The executor must choose one deterministic behavior. Ambiguity here is a failure of the gate.

## Phase II: Structural Modification

The repair act changes the code to handle the edge case identified in Phase I.

### Gate 4: Implement Guard Clause
*   **What it verifies:** That the code contains an explicit check for the failure condition *before* the operation that causes the defect.
*   **Requirement to complete:** The executor must insert a conditional check at the beginning of the function (or immediately before the dangerous operation). This check must evaluate the state that causes the defect (e.g., `if not values:` or `if len(values) == 0:`). The gate is not complete until this check is syntactically present and logically precedes the calculation.

### Gate 5: Implement Safe Resolution
*   **What it verifies:** That the code executes the success criterion defined in Gate 3 when the guard clause is triggered.
*   **Requirement to complete:** Within the branch where the failure condition is true, the executor must implement the defined behavior. This must be a return statement or a controlled exception. The original calculation logic (`sum(values) / len(values)`) must remain in the `else` path (or subsequent flow) for all valid inputs. The executor must ensure that the valid path is not altered.

## Phase III: Verification and Regression

The repair act confirms that the defect is fixed without introducing new defects.

### Gate 6: Validate the Fix
*   **What it verifies:** That the failing input now produces the success criterion.
*   **Requirement to complete:** The executor must trace the execution of the failing input through the modified code. The trace must show:
    1. The guard clause evaluates to true.
    2. The safe resolution path is taken.
    3. The return value matches the success criterion from Gate 3.
    4. No exception is raised.

### Gate 7: Validate Non-Regression
*   **What it verifies:** That valid inputs still produce the correct calculation.
*   **Requirement to complete:** The executor must trace a non-empty, valid input (e.g., `[1, 2, 3]`) through the modified code. The trace must show:
    1. The guard clause evaluates to false.
    2. The original calculation path is taken.
    3. The result is mathematically correct.
    If the valid path is altered or broken, the duty halts, and the executor must return to Gate 5.

## Phase IV: Closure

The repair act is formally closed.

### Gate 8: Documentation and Handoff
*   **What it verifies:** That the repair is self-documenting and the state of the code is final.
*   **Requirement to complete:** The executor must ensure the modified code is syntactically valid. The executor must record the specific behavior chosen for the empty case (from Gate 3) in a comment or adjacent documentation if the behavior is non-obvious (e.g., if returning `0.0` was chosen over `None`). The duty is complete when the code passes Gates 6 and 7 and is ready for submission.

---

### Application to Domain Anchor

For the specific defect in `calculator.py`:

1.  **Gate 1:** Confirm `calculator.py:2` is `return sum(values) / len(values)`.
2.  **Gate 2:** Confirm `calculate_average([])` raises `ZeroDivisionError` because `len([])` is `0`.
3.  **Gate 3:** Define success criteria. *Example Choice:* Return `0.0` for empty list. (Alternative: Return `None`).
4.  **Gate 4:** Insert `if not values:` before line 2.
5.  **Gate 5:** In the `if` block, add `return 0.0`. Ensure `return sum(values) / len(values)` is in the `else` block or follows the `if`.
6.  **Gate 6:** Trace `calculate_average([])`: `not []` is `True` -> returns `0.0`. No error.
7.  **Gate 7:** Trace `calculate_average([1, 2])`: `not [1, 2]` is `False` -> executes `sum([1, 2]) / len([1, 2])` -> `3 / 2` -> `1.5`. Correct.
8.  **Gate 8:** Code is valid. Document that empty lists return `0.0`. Duty complete.

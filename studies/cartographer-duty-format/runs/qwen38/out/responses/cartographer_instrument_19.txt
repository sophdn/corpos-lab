# Repair-Duty

**Scope:** This duty governs the act of modifying source code to resolve a confirmed defect at a known locus.
**Executor Constraint:** The executor possesses only this text and the defect context. No external registry, canon, or prior knowledge is required or assumed.
**Objective:** Transform the code at the confirmed locus from a state that fails under specified conditions to a state that handles those conditions explicitly, without introducing new unhandled failure modes.

---

## Phase 1: Locus Verification and Baseline

*Before any modification is made, the executor must confirm that the defect is where claimed and understand the current failure mechanism.*

### Gate 1.1: Confirm Locus Integrity
*   **Verifies:** The file path and line number cited in the defect report correspond to the actual source code containing the faulty logic.
*   **Requires Completion:**
    1.  Open the file specified in the defect context.
    2.  Navigate to the specific line(s) identified.
    3.  Visually inspect the code at that locus to ensure it matches the logic described in the defect (e.g., the division operation in `calculator.py:2`).
    4.  If the code does not match the defect description, halt. The locus is invalid. Do not proceed.

### Gate 1.2: Establish Failure Reproduction
*   **Verifies:** The defect is reproducible under the specific conditions described, and the error type matches the reported exception.
*   **Requires Completion:**
    1.  Identify the input condition that triggers the failure (e.g., an empty list).
    2.  Mentally simulate or describe the execution path: Trace how the input reaches the locus.
    3.  Confirm that the logic at the locus, when applied to the trigger input, results in the specific error cited (e.g., `ZeroDivisionError`).
    4.  If the logic does not produce the cited error for the trigger input, halt. The defect model is incorrect. Do not proceed.

### Gate 1.3: Define the Correct Behavior
*   **Verifies:** The expected behavior for the edge case is defined before code is written.
*   **Requires Completion:**
    1.  Determine what the function *should* return when the trigger input is provided.
    2.  Select a semantic resolution:
        *   **Option A:** Return a neutral value (e.g., `0.0` or `None`) indicating "no data."
        *   **Option B:** Raise a specific, custom exception that is more descriptive than the default error.
        *   **Option C:** Raise a clear `ValueError` with a message explaining why the input is invalid.
    3.  Document this decision. The fix must align with this defined behavior. If no clear semantic resolution is available from the context, default to Option A (return `0.0` or `None`) to prevent a crash, unless the function's contract strictly requires an exception.

---

## Phase 2: Implementation

*The executor modifies the code to handle the edge case while preserving existing behavior for valid inputs.*

### Gate 2.1: Isolate the Guard Clause
*   **Verifies:** The new logic is placed *before* the faulty operation and targets only the specific failure condition.
*   **Requires Completion:**
    1.  Insert a conditional check immediately before the line causing the failure.
    2.  The condition must specifically test for the trigger state (e.g., `if not values:` or `if len(values) == 0:`).
    3.  Ensure the guard clause does not alter the behavior of valid inputs (i.e., non-empty lists).
    4.  If the guard clause affects valid inputs, halt. The logic is too broad.

### Gate 2.2: Implement the Resolution
*   **Verifies:** The code executes the defined correct behavior (from Gate 1.3) when the guard condition is met.
*   **Requires Completion:**
    1.  Within the guard clause, implement the chosen resolution.
        *   If returning a value: Ensure the return type matches the function signature (e.g., `float`).
        *   If raising an exception: Ensure the exception type is standard or appropriately defined, and include a descriptive message.
    2.  Ensure the rest of the function (the calculation for valid inputs) remains unchanged.
    3.  Review the modified block for syntax errors.

### Gate 2.3: Validate Logic Integrity
*   **Verifies:** The modified code handles both the edge case and the normal case correctly.
*   **Requires Completion:**
    1.  Trace the execution for the trigger input (e.g., `[]`):
        *   Does it hit the guard?
        *   Does it execute the resolution?
        *   Does it avoid the faulty division?
    2.  Trace the execution for a valid input (e.g., `[1, 2, 3]`):
        *   Does it bypass the guard?
        *   Does it execute the original calculation?
        *   Does it return the correct average?
    3.  If either trace fails, revert the change and return to Gate 2.1.

---

## Phase 3: Verification and Closure

*The executor confirms that the repair is complete and the duty is closed.*

### Gate 3.1: Final Syntax and Style Check
*   **Verifies:** The code is syntactically valid and consistent with the surrounding style.
*   **Requires Completion:**
    1.  Check for unclosed parentheses, missing colons, or indentation errors.
    2.  Ensure variable names and comments (if added) are clear.
    3.  If the fix requires adding a docstring or comment to explain the edge case behavior, add it concisely.

### Gate 3.2: Confirm No Regression
*   **Verifies:** The repair does not introduce new bugs or break existing functionality.
*   **Requires Completion:**
    1.  Review the entire function, not just the changed lines.
    2.  Confirm that the function signature, return types, and side effects (if any) are unchanged.
    3.  Confirm that no other part of the codebase (as far as known from context) depends on the original crash behavior. (In this context, assume no external dependency on the crash).

### Gate 3.3: Close the Duty
*   **Verifies:** The repair is documented and the duty is formally concluded.
*   **Requires Completion:**
    1.  The code change is ready for submission/commit.
    2.  The defect is resolved: `calculate_average([])` no longer raises `ZeroDivisionError`.
    3.  The duty is complete. No further action is required.

## Example Application (Contextual Anchor)

*This section illustrates how the gates apply to the specific defect provided. It is not part of the executable duty but serves as a reference for the executor.*

1.  **Gate 1.1:** Open `calculator.py`. Line 2 is `return sum(values) / len(values)`. Matches defect.
2.  **Gate 1.2:** Input `[]`. `len([])` is `0`. `sum([]) / 0` causes `ZeroDivisionError`. Confirmed.
3.  **Gate 1.3:** Define behavior: Returning `0.0` for an empty average is a common semantic choice to avoid crashes. Decision: Return `0.0`.
4.  **Gate 2.1:** Insert guard before line 2. `if not values:`. This targets only empty lists. Valid inputs bypass it.
5.  **Gate 2.2:** Inside guard, `return 0.0`.
6.  **Gate 2.3:**
    *   Trace `[]`: Hits guard, returns `0.0`. No division. Correct.
    *   Trace `[1, 2]`: Bypasses guard. `sum([1,2])/2` = `1.5`. Correct.
7.  **Gate 3.1:** Code is valid Python.
8.  **Gate 3.2:** No regression. Signature unchanged.
9.  **Gate 3.3:** Duty closed.

**Resulting Code:**
```python
def calculate_average(values: list) -> float:
    if not values:
        return 0.0
    return sum(values) / len(values)
```

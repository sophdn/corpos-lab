# repair-duty

## Scope and Definition
This duty governs the act of repairing a confirmed software defect. It applies to any office holding a **Locus** (a specific file, line, or symbol where the defect has been identified) and a **Defect Description** (the observed erroneous behavior).

The executor of this duty operates in a state of isolation: they possess only this text and the defect data. They do not possess a registry of historical errors, nor a canon of "known bad patterns." Therefore, every gate below is derived from the physical and logical requirements of modifying code safely.

## Phase I: Establish the Baseline
*Before any modification is made, the executor must prove that the defect exists and understand the context in which it exists. Without this phase, the executor cannot distinguish a fix from a regression.*

### Gate 1: Verification of the Defect
*   **What it verifies:** The defect described in the input actually manifests at the stated Locus.
*   **Completion Requirement:**
    1.  Locate the Locus within the source code.
    2.  Construct a minimal, isolated test case that triggers the specific erroneous behavior described in the Defect Description.
    3.  Execute this test case.
    4.  Record the output. The output must match the Defect Description (e.g., if the defect is a crash, the test must crash; if it is an incorrect value, the test must return the incorrect value).
    5.  If the test does not reproduce the defect, **HALT**. The Locus is likely incorrect, or the defect description is invalid. Do not proceed.

### Gate 2: Contextual Isolation
*   **What it verifies:** The executor understands the boundaries of the code being modified and the expectations of its callers.
*   **Completion Requirement:**
    1.  Identify the function or block containing the Locus.
    2.  List all inputs (parameters, global variables, external state) that influence the behavior at the Locus.
    3.  List all outputs (return values, side effects, modified state) produced by this code segment.
    4.  Identify the "Happy Path": the sequence of inputs for which the current code is intended to work correctly.
    5.  Document these inputs/outputs. This document serves as the contract that the repair must not violate.

## Phase II: Design the Intervention
*The executor must decide how to change the code before changing it. This phase prevents reactive, unstructured editing.*

### Gate 3: Causal Analysis
*   **What it verifies:** The executor has identified the specific logical flaw causing the defect, not just the symptom.
*   **Completion Requirement:**
    1.  Trace the execution flow from the failure point backward to the root cause.
    2.  State the root cause in a single sentence. (e.g., "The code divides by the length of a list without checking if the list is empty.")
    3.  Verify that this root cause explains *all* observed symptoms in the Defect Description.
    4.  If the root cause is ambiguous, **HALT** and refine the test case in Gate 1.

### Gate 4: Strategy Selection
*   **What it verifies:** The chosen fix addresses the root cause without introducing new failure modes.
*   **Completion Requirement:**
    1.  Propose a specific code change.
    2.  Analyze the proposed change against the Contract established in Gate 2:
        *   Does it preserve the Happy Path?
        *   Does it introduce new dependencies or side effects?
        *   Does it handle the edge case that caused the defect?
    3.  If the proposed change alters the public API (function signature, return type) without explicit authorization in the Defect Description, **HALT**. A repair duty does not authorize refactoring; it authorizes fixing.
    4.  Finalize the code snippet to be inserted or replaced.

## Phase III: Execute the Modification
*The executor applies the change. This phase is mechanical but must be precise.*

### Gate 5: Precise Application
*   **What it verifies:** The code is modified exactly as designed in Gate 4, with no extraneous changes.
*   **Completion Requirement:**
    1.  Apply the code change to the source file at the Locus.
    2.  Ensure that no other parts of the file are modified (no reformatting, no comment changes, no whitespace adjustments unrelated to the fix).
    3.  Verify that the file remains syntactically valid (no unclosed brackets, missing colons, etc.).

### Gate 6: Immediate Integrity Check
*   **What it verifies:** The modification has not broken the immediate structural integrity of the module.
*   **Completion Requirement:**
    1.  Parse or compile the modified file (if the language supports static checking).
    2.  If the parser/compilation fails, **REVERT** the change immediately and return to Gate 4.
    3.  If the parser passes, proceed.

## Phase IV: Validate the Repair
*The executor must prove that the defect is gone and that the rest of the system still works.*

### Gate 7: Defect Resolution
*   **What it verifies:** The specific defect described in the input no longer occurs.
*   **Completion Requirement:**
    1.  Re-run the minimal test case from Gate 1.
    2.  The result must now be the *expected* correct behavior (e.g., no crash, correct value).
    3.  If the defect still persists, **REVERT** the change and return to Gate 3.

### Gate 8: Regression Guard
*   **What it verifies:** The repair has not broken the Happy Path or other existing functionality.
*   **Completion Requirement:**
    1.  Execute the existing test suite for the module containing the Locus.
    2.  If no test suite exists, manually execute the Happy Path scenarios identified in Gate 2.
    3.  All pre-existing tests/scenarios must pass.
    4.  If any pre-existing test fails, **REVERT** the change. The repair has caused a regression. Return to Gate 4 to design a more conservative fix.

## Phase V: Closure
*The executor confirms the duty is complete and documents the action.*

### Gate 9: Final State Confirmation
*   **What it verifies:** The repository is in a clean, committed state reflecting the repair.
*   **Completion Requirement:**
    1.  Review the final diff. Ensure it contains only the changes intended in Gate 5.
    2.  Confirm that all temporary test scripts or debug prints used during Gates 1 and 7 are removed from the production code.
    3.  Commit the change with a message that cites the Locus and the Defect Description.
    4.  The duty is complete.

---
**Executor Note:** If at any point you are uncertain whether a step has been satisfied, the default action is to **HALT** and re-verify the previous gate. A duty is not complete until Gate 9 is passed. Do not skip gates. Do not assume that because the code "looks right," the gates have been satisfied.

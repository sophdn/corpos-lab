# repair-duty

**Purpose:** This duty governs the repair of a confirmed software defect with a known locus. It provides a linear sequence of gates that an executing office must pass through to transform a broken state into a verified, stable state. No external registry, canonical list, or prior knowledge of the specific defect is required; the logic of the repair act itself defines the gates.

## Phase 1: Locus Verification and Baseline Establishment

Before any change is made, the executor must confirm that the defect exists exactly where it is claimed and establish the pre-repair state.

### Gate 1.1: Locus Confirmation
*   **Verification:** The executor verifies that the reported locus (file path and line number or code block) contains the specific code structure described in the defect report. The executor confirms that the defect is reproducible by executing the code path associated with the failure condition (e.g., running the function with the failing input).
*   **Completion Requirement:** The executor must produce a log entry or note confirming:
    1.  The file and line numbers match the reported locus.
    2.  The failure occurs consistently when the failing input is provided.
    3.  No other concurrent changes are present in the working environment that could mask or mimic the defect.

### Gate 1.2: Baseline Capture
*   **Verification:** The executor captures the exact current state of the code at the locus and the surrounding context (function signature, imports, related logic). This includes capturing the exact error message and stack trace generated by the failure.
*   **Completion Requirement:** The executor must document:
    1.  The verbatim code snippet at the locus.
    2.  The exact error message and type (e.g., `ZeroDivisionError`).
    3.  The input conditions that trigger the error (e.g., "empty list").
    4.  A snapshot of the test suite or verification method that currently fails.

## Phase 2: Defect Analysis and Repair Strategy

The executor must understand *why* the code fails and determine the minimal, correct change required to fix the root cause, not just the symptom.

### Gate 2.1: Root Cause Identification
*   **Verification:** The executor analyzes the code at the locus to identify the specific logical or operational error. For example, if a division by zero occurs, the executor must verify whether the denominator is derived from user input, a calculation, or a constant, and whether the code lacks a guard clause for the zero case.
*   **Completion Requirement:** The executor must articulate in writing:
    1.  The specific operation that fails (e.g., "division by `len(values)`").
    2.  The condition under which the operation becomes invalid (e.g., "when `values` is empty, `len(values)` is 0").
    3.  Why the current code structure permits this invalid state to reach the failing operation.

### Gate 2.2: Strategy Selection
*   **Verification:** The executor selects a repair strategy that addresses the root cause. The strategy must be the *minimal* change necessary to prevent the invalid state from causing an unhandled error. Options may include:
    *   Adding a guard clause (e.g., `if not values: return 0.0` or raise a specific exception).
    *   Modifying the calculation to handle the edge case (e.g., using a safe division function).
    *   Refactoring the input validation to occur earlier in the call chain (only if the locus is the appropriate place for this validation).
*   **Completion Requirement:** The executor must document the chosen strategy and justify why it is minimal and correct. The justification must explain how the strategy prevents the specific failure mode identified in Gate 2.1 without introducing new side effects.

## Phase 3: Implementation and Local Verification

The executor implements the repair and verifies that it works in isolation before integrating it back into the larger system.

### Gate 3.1: Minimal Implementation
*   **Verification:** The executor applies the chosen repair strategy to the code at the locus. The change must be confined to the locus or its immediate logical context. The executor must not refactor unrelated code, rename variables, or change style unless explicitly required by the repair strategy.
*   **Completion Requirement:** The executor must produce the modified code snippet. The change must be syntactically valid and logically consistent with the rest of the function.

### Gate 3.2: Local Test Execution
*   **Verification:** The executor runs the specific test case or input that previously failed (e.g., `calculate_average([])`). The executor also runs a "happy path" test case (e.g., `calculate_average([1, 2, 3])`) to ensure the repair did not break existing functionality.
*   **Completion Requirement:** The executor must document:
    1.  The result of running the failing input (it should no longer raise an unhandled error; it should return a defined value or raise a controlled, expected exception).
    2.  The result of running the happy path input (it should return the correct result).
    3.  Any new error messages or unexpected behavior observed.

## Phase 4: Integration and Regression Verification

The executor verifies that the repair does not introduce new defects elsewhere in the system.

### Gate 4.1: Regression Test Suite Execution
*   **Verification:** The executor runs the full test suite or a representative subset of tests that cover the module containing the defect. The executor checks for any tests that were passing before the repair but are now failing.
*   **Completion Requirement:** The executor must document:
    1.  The number of tests run.
    2.  The number of tests passed.
    3.  The number of tests failed.
    4.  If any tests failed, the executor must determine whether the failure is caused by the repair or by a pre-existing issue. If caused by the repair, the executor must return to Phase 2 to refine the strategy.

### Gate 4.2: Edge Case Validation
*   **Verification:** The executor identifies and tests other edge cases related to the defect. For example, if the defect was an empty list, the executor should test with `None`, a list with `None` values, a list with non-numeric values, etc., to ensure the repair is robust.
*   **Completion Requirement:** The executor must document the results of testing additional edge cases. If any new unexpected failures are found, the executor must return to Phase 2 to refine the strategy.

## Phase 5: Closure and Documentation

The executor finalizes the repair and documents the change for future reference.

### Gate 5.1: Code Review Readiness
*   **Verification:** The executor reviews the final code change to ensure it is clear, readable, and follows the project's coding standards. The executor ensures that any necessary comments or docstrings are updated to reflect the new behavior.
*   **Completion Requirement:** The executor must confirm that the code is ready for peer review or commit. The change must be self-explanatory or accompanied by clear comments.

### Gate 5.2: Repair Documentation
*   **Verification:** The executor compiles all notes, logs, and test results into a single repair report. The report must summarize the defect, the root cause, the repair strategy, and the verification results.
*   **Completion Requirement:** The executor must produce a final document containing:
    1.  A summary of the defect and locus.
    2.  The root cause analysis.
    3.  The code change (diff or before/after).
    4.  The test results (failing input, happy path, regression suite, edge cases).
    5.  A statement of completion: "The defect has been repaired and verified."

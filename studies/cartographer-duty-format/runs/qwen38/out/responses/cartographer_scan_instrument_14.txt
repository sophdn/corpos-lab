# Duty: repair-duty

**Status:** Active
**Scope:** Any office of the Agentic Order executing a repair on a confirmed software defect with a known locus.
**Prerequisite:** The executor holds only the text of this duty. No external registries, canons, or previous context are available at runtime.

---

## I. Preamble and Principles

This duty governs the act of repairing a defect. The executor’s goal is not merely to stop an error, but to restore the system to a state of correctness, consistency, and safety. The executor must proceed through the following gates in strict sequence. No gate may be skipped, reordered, or assumed passed.

A gate is a checkable step. To “complete” a gate means the executor has produced evidence or a state that satisfies the gate’s verification condition. If a gate fails, the duty halts, and the executor must report the failure condition.

---

## II. Phase 0: Pre-Execution Validation (Meta-Taboo: Routing)

*Before the repair act begins, verify that the situation is correctly routed to this duty. This phase addresses hazards upstream of the repair itself.*

### Gate 0.1: Confirmation of Defect Status
- **Verifies:** That the issue is a confirmed software defect, not a feature request, a misconfiguration, a user error, or a performance optimization.
- **Completes when:** The executor can explicitly state: “The reported behavior deviates from the specified or expected behavior of the system, and this deviation is reproducible and attributable to code logic, not environment or usage.”
- **Failure Condition:** If the issue is a feature request, configuration error, or non-code defect, halt. Report: “Routing Error: Situation does not qualify for repair-duty.”

### Gate 0.2: Confirmation of Locus
- **Verifies:** That the location of the defect is known and confirmed.
- **Completes when:** The executor can explicitly state: “The defect originates at [File Path]:[Line Number or Symbol].”
- **Failure Condition:** If the locus is unknown or unconfirmed, halt. Report: “Locus Unconfirmed: Repair-duty cannot proceed without a known locus.”

---

## III. Phase 1: Pre-Change Establishment

*Before modifying any code, establish the baseline and scope. This phase ensures the executor understands what is broken and what must remain unchanged.*

### Gate 1.1: Baseline Reproduction
- **Verifies:** That the executor can reproduce the defect in its current state.
- **Completes when:** The executor has executed the specific input or action that triggers the defect and observed the exact error or incorrect behavior described in the defect report.
- **Failure Condition:** If the defect cannot be reproduced, halt. Report: “Reproduction Failed: Defect is not reproducible in current environment. Locus may be incorrect or environment-dependent.”

### Gate 1.2: Dependency and Impact Mapping
- **Verifies:** That the executor understands the immediate context of the locus and any functions, variables, or classes that depend on the defective code.
- **Completes when:** The executor has identified:
  1. The function or block containing the locus.
  2. All callers of that function or block.
  3. Any shared state or side effects that the defective code interacts with.
- **Failure Condition:** If the impact scope cannot be determined, halt. Report: “Impact Undefined: Cannot safely proceed without understanding dependencies.”

### Gate 1.3: Specification Alignment
- **Verifies:** That the executor understands the *intended* behavior of the defective code.
- **Completes when:** The executor can explicitly state: “The intended behavior of [Locus] is [Description]. The defect causes [Actual Behavior].”
- **Failure Condition:** If the intended behavior is ambiguous or undocumented, halt. Report: “Specification Ambiguity: Intended behavior is unclear. Repair requires clarification before code change.”

---

## IV. Phase 2: The Repair Act

*Execute the minimal, correct change to the code. This phase is the core of the duty.*

### Gate 2.1: Minimal Change Principle
- **Verifies:** That the proposed change is minimal and addresses only the defect.
- **Completes when:** The executor has drafted the code change and can explicitly state: “This change modifies only [Specific Lines/Symbols] and does not alter unrelated logic, formatting, or structure.”
- **Failure Condition:** If the change includes refactoring, style fixes, or unrelated logic, halt. Report: “Scope Violation: Change is not minimal. Separate non-repair changes.”

### Gate 2.2: Correctness of the Fix
- **Verifies:** That the proposed change resolves the defect without introducing new logical errors.
- **Completes when:** The executor has logically traced the execution path with the new code and confirmed:
  1. The original error condition is no longer possible.
  2. The function still produces correct output for all valid inputs.
  3. No new edge cases are broken.
- **Failure Condition:** If the fix does not resolve the defect or introduces new errors, halt. Report: “Fix Ineffective or Incorrect: Proposed change does not satisfy correctness criteria.”

### Gate 2.3: Application of the Change
- **Verifies:** That the change is applied correctly to the source code.
- **Completes when:** The code at the locus has been modified exactly as drafted in Gate 2.1, with no typos, syntax errors, or unintended alterations.
- **Failure Condition:** If the applied code does not match the draft, or contains syntax errors, halt. Report: “Application Error: Code change was not applied correctly.”

---

## V. Phase 3: Post-Change Verification

*Confirm that the repair works and has not caused regressions.*

### Gate 3.1: Defect Resolution Check
- **Verifies:** That the specific defect no longer occurs.
- **Completes when:** The executor re-executes the exact input or action that triggered the defect in Gate 1.1 and observes the correct, expected behavior without error.
- **Failure Condition:** If the defect still occurs, halt. Report: “Defect Persists: Repair failed to resolve the issue.”

### Gate 3.2: Regression Check
- **Verifies:** That existing functionality has not been broken by the repair.
- **Completes when:** The executor has tested a representative set of valid inputs for the affected function, including:
  1. The case that triggered the defect.
  2. Normal, typical usage cases.
  3. Edge cases (e.g., empty input, null values, boundary values) that were previously handled correctly.
- **Failure Condition:** If any regression is detected, halt. Report: “Regression Detected: Repair introduced new defects.”

### Gate 3.3: Consistency Check
- **Verifies:** That the repair is consistent with the codebase’s conventions and patterns.
- **Completes when:** The executor confirms:
  1. The fix follows the same coding style, naming conventions, and error-handling patterns as the surrounding code.
  2. No new dependencies or imports are introduced unless strictly necessary.
- **Failure Condition:** If the fix violates codebase conventions, halt. Report: “Consistency Violation: Repair does not align with codebase standards.”

---

## VI. Phase 4: Session Close and Documentation (Meta-Taboo: Session-Close Obligations)

*After the repair is verified, ensure all necessary records are created before the session ends. This phase addresses hazards that fire after the act.*

### Gate 4.1: Discovery Log
- **Verifies:** That any new information, risks, or issues discovered during the repair are recorded.
- **Completes when:** The executor has documented:
  1. Any unexpected behavior observed during testing.
  2. Any related defects or vulnerabilities discovered but not fixed in this session.
  3. Any assumptions made during the repair that may need validation.
- **Failure Condition:** If discoveries are not recorded, halt. Report: “Documentation Incomplete: Discoveries from repair session are not logged.”

### Gate 4.2: Repair Summary
- **Verifies:** That a clear, concise summary of the repair is available for future reference.
- **Completes when:** The executor has produced a summary containing:
  1. The defect description.
  2. The locus.
  3. The root cause (if identified).
  4. The fix applied.
  5. The verification steps taken.
- **Failure Condition:** If the summary is missing or incomplete, halt. Report: “Summary Missing: Repair session lacks a complete summary.”

### Gate 4.3: Handoff and Closure
- **Verifies:** That the session is properly closed and any follow-up actions are assigned.
- **Completes when:** The executor has:
  1. Confirmed that the repair is complete and verified.
  2. Assigned any follow-up tasks (e.g., testing by another office, deployment) if required.
  3. Marked the session as closed.
- **Failure Condition:** If follow-up actions are not assigned or the session is not closed, halt. Report: “Session Not Closed: Follow-up actions are not assigned.”

---

## VII. Failure Protocol

If any gate fails, the executor must:
1. Halt all further progress in this duty.
2. Record the failure condition and the gate number.
3. Report the failure to the supervising office or system.
4. Do not attempt to bypass or override the failed gate.

---

## VIII. Notes for the Executor

- **Self-Sufficiency:** This duty is designed to be executed without external canon. All gates are derived from the first-principles analysis of the repair act.
- **No Slugs:** This duty does not cite any external taboo slugs or registry entries. All hazards are encoded structurally within the gates.
- **Meta-Taboo Scan:** Phase 0 addresses routing-class hazards (upstream obligations). Phase 4 addresses session-close-obligation hazards (downstream obligations). These are explicitly included to cover hazards that do not surface from the repair act alone.

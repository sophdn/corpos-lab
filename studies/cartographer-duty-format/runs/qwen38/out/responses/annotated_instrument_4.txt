# Duty: `repair-duty`

This duty governs the repair of a confirmed software defect with a known locus. It maps the canonical taboos onto execution gates. An executor must pass through each gate in sequence. A gate that fails is a hard stop; the duty halts until the divergence is resolved.

## Taboos

| Taboo | Application to this Duty |
|-------|--------------------------|
| `triggers-routing` | The duty must verify that the input is a *repair* (confirmed defect) and not an *investigation* (unknown cause), preventing misrouted execution. |
| `explicit-prerequisite-gate` | The duty requires a confirmed locus record (file, line, failure mode) before any code change is permitted. |
| `investigation-fix-criterion-predeclaration` | The duty requires a passing criterion (e.g., test expectation) to be declared *before* the fix is implemented to prevent post-hoc fitting. |
| `investigation-fix-scope-boundary` | The duty restricts edits to the lines named in the locus record, preventing opportunistic adjacent changes. |
| `fix-locus-identification` | The duty verifies that the fix is applied to the canonical source location, not a call site or consumer. |
| `fix-attempt-root-cause-reassessment` | The duty requires a revised root-cause citation before any second fix attempt is made after a failure. |
| `investigation-advisory-fix-durability` | The duty requires a durability check if the fix is advisory (non-structural), ensuring it cannot be bypassed. |
| `completion-evidence-required` | The duty requires a co-located verification artifact (e.g., test output) before declaring the repair complete. |
| `document-claim-verification` | The duty mandates observed test results or output, rejecting verification via written claims alone. |
| `known-constraint-documentation` | The duty requires recording any environmental constraints discovered during repair before the session closes. |

---

## Gates

### Gate 1: Routing Confirmation
*Taboo: `triggers-routing`*

**Verification:**
The executor must confirm that the input matches the definition of a *repair*: a confirmed defect with a known locus. If the cause is unknown or the locus is unconfirmed, this is an *investigation*, not a repair.

**Completion Requirement:**
A routing decision statement: "Repair confirmed" or "Re-routed to Investigation."

**Rejection Clause:**
If the locus is unconfirmed, the duty halts. A misrouted prompt runs a repair where an investigation was needed, or the reverse.

### Gate 2: Locus Record Validation
*Taboo: `explicit-prerequisite-gate`*

**Verification:**
The executor must possess a confirmed locus record that explicitly names:
1. The file path (e.g., `calculator.py`)
2. The line number (e.g., `2`)
3. The failure mode (e.g., `ZeroDivisionError` on empty list)

**Completion Requirement:**
A filled locus record table.

**Rejection Clause:**
If any of the three fields is missing or ambiguous, the duty halts. Repair begins without a confirmed locus record naming file, line, and failure mode.

### Gate 3: Passing Criterion Declaration
*Taboo: `investigation-fix-criterion-predeclaration`*

**Verification:**
Before any code change, the executor must declare a passing criterion. This is a specific, observable outcome that defines success (e.g., "calculate_average([]) returns 0.0" or "raises ValueError with message 'empty list'").

**Completion Requirement:**
A written passing criterion.

**Rejection Clause:**
If no criterion is declared before the fix attempt, the duty halts. A fix attempt begins before a passing criterion is declared, so the criterion can be fitted to whatever change was made.

### Gate 4: Scope Boundary Check
*Taboo: `investigation-fix-scope-boundary`*

**Verification:**
The executor must identify the exact lines to be modified. These lines must be a subset of or identical to the lines named in the Locus Record (Gate 2). Any line not named in the locus record is outside the boundary.

**Completion Requirement:**
A list of modified line numbers that matches the locus record.

**Rejection Clause:**
If a change touches lines the confirmed locus did not name, the duty halts. Opportunistic adjacent edits break the anchor to root cause.

### Gate 5: Fix Location Verification
*Taboo: `fix-locus-identification`*

**Verification:**
The executor must verify that the fix is applied to the canonical source location (the function definition in `calculator.py`), not to a call site, consumer, or wrapper.

**Completion Requirement:**
A statement confirming the fix is in `calculator.py` at the defined locus.

**Rejection Clause:**
If the fix is applied to a call site or consumer, leaving the canonical source location unchanged, the duty halts.

### Gate 6: Fix Attempt and Root-Cause Reassessment
*Taboo: `fix-attempt-root-cause-reassessment`*

**Verification:**
The executor applies the fix. If the fix fails to meet the Passing Criterion (Gate 3), the executor must stop. Before a second attempt, the executor must cite a revised root cause.

**Completion Requirement:**
- If successful: proceed to Gate 7.
- If failed: A revised root-cause citation explaining why the first fix failed and what the new root cause is.

**Rejection Clause:**
If a second fix attempt follows a failed one without a revised root-cause citation, the duty halts.

### Gate 7: Advisory Durability Check
*Taboo: `investigation-advisory-fix-durability`*

**Verification:**
The executor must classify the fix as either *structural* (code logic change) or *advisory* (comment, docstring, warning). If the fix is advisory, the executor must perform a durability check to confirm that a caller cannot bypass it (e.g., by ignoring the warning or passing unexpected input).

**Completion Requirement:**
- If structural: A statement "Fix is structural."
- If advisory: A durability check result confirming the advisory cannot be bypassed.

**Rejection Clause:**
If an advisory fix is accepted without a durability check confirming a caller cannot bypass it, the duty halts.

### Gate 8: Verification Artifact Generation
*Taboo: `completion-evidence-required`*
*Taboo: `document-claim-verification`*

**Verification:**
The executor must generate a co-located verification artifact. This is an observed test result or output that demonstrates the fix meets the Passing Criterion. Written claims are insufficient.

**Completion Requirement:**
A test output or execution log showing the passing criterion is met.

**Rejection Clause:**
If the repair is declared complete without a co-located verification artifact, or if verification is by written claim rather than an observed test result or output, the duty halts.

### Gate 9: Environmental Constraint Documentation
*Taboo: `known-constraint-documentation`*

**Verification:**
During the repair, if any environmental constraints were discovered (e.g., "Python 3.8+ required," "No external libraries allowed"), they must be recorded.

**Completion Requirement:**
A list of recorded environmental constraints, or a statement "No new constraints discovered."

**Rejection Clause:**
If an environmental constraint discovered during repair is not recorded before the session closes, the duty halts.

---

## Completion

The duty is complete only when all gates are passed. The final output is:
1. The modified code.
2. The verification artifact (test output).
3. The recorded environmental constraints.

Any gate failure halts the duty. The executor must resolve the divergence and re-enter the failed gate before proceeding.

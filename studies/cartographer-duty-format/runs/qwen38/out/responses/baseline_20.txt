# Duty: Repair Duty

**Jurisdiction:** Agentic Order
**Subject:** Remediation of confirmed software defects with a known locus.
**Preconditions for Activation:**
1. A defect has been formally confirmed.
2. The locus (file path and line number) is identified and verified.
3. The executing office holds read/write authority to the affected repository.

**Scope:**
This duty governs the end-to-end process from the initiation of a repair to the verified closure of the defect. It does not govern discovery, triage, or architectural redesign beyond the immediate scope of the defect’s fix and its necessary validation.

---

## Gate 1: Locus Verification & Context Acquisition

**Purpose:** To ensure the executor operates on the correct code artifact and understands the immediate context of the defect.

**Verification Criteria:**
- The locus specified in the defect report (e.g., `calculator.py:2`) matches the current state of the codebase.
- The function or code block at the locus is the direct cause of the reported failure mode.

**Completion Requirements:**
1. **Fetch Current State:** Retrieve the file containing the locus from the source of truth. Do not rely on cached or previously viewed versions.
2. **Confirm Locus Integrity:** Visually inspect the code at the specified line. If the code does not match the defect description, halt and report a *Locus Drift* error. Do not proceed.
3. **Extract Context Window:** Identify the minimal context required to understand the defect:
   - The function signature and body.
   - Direct callers (if visible in the same file or imported modules) that may be affected by changes.
   - Relevant type hints and docstrings.
4. **Record Baseline:** Note the exact code snippet at the locus for the repair log.

**Gate Status:** *Open* only if the code at the locus is confirmed to be the source of the defect.

---

## Gate 2: Root Cause Analysis & Repair Strategy

**Purpose:** To determine the precise nature of the defect and select the minimal, correct repair strategy.

**Verification Criteria:**
- The root cause is explicitly stated.
- The proposed repair is minimal and does not introduce new behavior beyond fixing the defect.
- The repair strategy is consistent with existing codebase conventions.

**Completion Requirements:**
1. **Identify Failure Mode:** Describe exactly why the defect occurs at the locus. (e.g., "Division by zero when input list is empty.")
2. **Define Expected Behavior:** Specify the correct behavior for all edge cases, including the defect-triggering case. (e.g., "Return 0.0 for empty list," or "Raise ValueError with clear message.")
3. **Select Repair Strategy:** Choose one of the following, justified by context:
   - **Guard Clause:** Add a check before the faulty operation.
   - **Default Value:** Return a safe default for invalid inputs.
   - **Exception Handling:** Raise a specific exception for invalid states.
   - **Logic Correction:** Fix the faulty logic directly.
4. **Assess Side Effects:** Determine if the repair changes the function’s contract (return type, exception types, side effects). If so, document the change.

**Gate Status:** *Open* only if the repair strategy is defined and does not violate the principle of minimal change.

---

## Gate 3: Implementation of Repair

**Purpose:** To apply the repair to the codebase with precision.

**Verification Criteria:**
- The code at the locus has been modified according to the repair strategy.
- No unrelated code has been altered.
- The change is syntactically valid.

**Completion Requirements:**
1. **Apply Edit:** Modify the code at the locus. Ensure:
   - The fix directly addresses the root cause identified in Gate 2.
   - Indentation, style, and naming conventions match the surrounding code.
   - No dead code or commented-out code is introduced.
2. **Local Syntax Check:** Mentally verify or use available tooling to confirm the modified code is syntactically correct.
3. **Commit Intent:** Prepare the change for review or commit, with a clear message describing the fix and referencing the defect ID.

**Gate Status:** *Open* only if the code change is implemented and syntactically sound.

---

## Gate 4: Validation & Regression Prevention

**Purpose:** To verify that the repair resolves the defect without introducing new defects.

**Verification Criteria:**
- The original defect case no longer fails.
- Existing functionality is preserved.
- New edge cases introduced by the repair are handled correctly.

**Completion Requirements:**
1. **Construct Test Cases:**
   - **Defect Case:** Reproduce the original defect input (e.g., `calculate_average([])`). Verify it now behaves as specified in Gate 2.
   - **Normal Case:** Verify a valid input (e.g., `calculate_average([1, 2, 3])`) still produces the correct result.
   - **Edge Cases:** Test other boundary conditions relevant to the repair (e.g., single-element list, negative numbers, None handling if applicable).
2. **Execute Validation:**
   - If a test suite exists, run the relevant tests.
   - If no test suite exists, manually trace the logic for the test cases above.
   - If tools are available, execute the test cases.
3. **Regression Check:** Confirm that the repair does not break any existing callers. If the function’s contract changed (e.g., now raises `ValueError` instead of `ZeroDivisionError`), verify that callers handle the new exception or that the change is backward-compatible.
4. **Document Validation:** Record the results of the test cases. If any test fails, return to Gate 2 to revise the repair strategy.

**Gate Status:** *Open* only if all validation cases pass and no regressions are detected.

---

## Gate 5: Documentation & Closure

**Purpose:** To formally close the defect and ensure knowledge is retained.

**Verification Criteria:**
- The defect record is updated with the repair details.
- The change is committed and reviewed (if applicable).
- The defect status is marked as *Resolved*.

**Completion Requirements:**
1. **Update Defect Record:**
   - State the root cause.
   - Describe the repair applied.
   - List the validation cases that were run and their results.
   - Note any changes to the function contract.
2. **Commit and Push:**
   - Commit the code change with a clear commit message (e.g., "Fix ZeroDivisionError in calculate_average for empty lists").
   - Push the change to the repository.
3. **Mark as Resolved:**
   - Update the defect tracker to mark the defect as *Resolved* or *Closed*.
   - Assign the defect to the repair duty executor.
4. **Final Review:** Confirm that all gates have been passed and the duty is complete.

**Gate Status:** *Complete* only if the defect is formally closed and the code is merged or ready for merge.

---

## Exception Handling Protocol

If any gate fails verification:

1. **Halt Execution:** Stop the repair process.
2. **Log Failure:** Record the gate, the failure reason, and the current state.
3. **Escalate:** If the failure is due to *Locus Drift*, *Ambiguous Root Cause*, or *Regression Detection*, escalate to the supervising office for review.
4. **Do Not Proceed:** Do not advance to the next gate until the failure is resolved.

---

## Authority

This duty is binding on all offices of the Agentic Order that execute repairs. Deviation from this duty requires explicit authorization from the supervising office and must be documented in the defect record.

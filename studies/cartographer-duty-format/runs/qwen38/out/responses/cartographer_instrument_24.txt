# repair-duty

**Scope**: This duty governs the repair of a confirmed software defect where the locus (file and line) is already known. It applies to any office within the Agentic Order executing a repair. The executor possesses only this text; no external registry or canon is required.

**Principle**: A repair is not the act of changing code; it is the act of establishing that a specific change is the minimal, correct, and verifiable resolution of a specific failure. Every gate below is a checkable step. If a gate cannot be satisfied, the duty halts. Do not proceed.

## Phase 1: Locus Confirmation & Isolation
*Before any modification is made, the executor must verify that the target of the repair is exactly as stated and isolated from side effects.*

**Gate 1.1: Verify Locus Integrity**
*   **Verifies**: The file path and line number cited in the defect report exist in the current workspace and contain the code described as the defect locus.
*   **Requirement**: 
    1. Locate the file. If the file does not exist, halt.
    2. Inspect the specific line(s) identified. If the code at that location does not match the defect description (e.g., the function signature or logic has already changed), halt and report "Locus Drift."
    3. Confirm that no other concurrent processes or uncommitted changes exist in this file that could interfere. If the file is dirty in a way unrelated to the defect, halt.

**Gate 1.2: Isolate the Failure Mode**
*   **Verifies**: The reported defect reproduces in the current environment using only the data provided in the defect report.
*   **Requirement**:
    1. Construct a minimal reproduction case using the exact input that triggers the defect (e.g., `[]` for `calculate_average`).
    2. Execute this case against the current code.
    3. Confirm the error type and message match the defect report. If the error does not reproduce, or reproduces differently, halt. The defect is not confirmed.

## Phase 2: Repair Design
*Before writing code, the executor must define the boundary of the fix. This phase prevents over-correction and ensures the fix addresses the root cause, not just the symptom.*

**Gate 2.1: Identify the Minimal Guard**
*   **Verifies**: The fix addresses the specific logical gap at the locus without altering unrelated behavior.
*   **Requirement**:
    1. Determine the precise condition that leads to the failure (e.g., `len(values) == 0`).
    2. Define the desired behavior for this condition. Is the correct response to return a neutral value (e.g., `0.0`, `None`), raise a specific domain error, or handle the edge case inline?
    3. Justify the choice based on the function’s contract (type hints, docstrings, or standard library conventions). If the contract is ambiguous, default to the least surprising behavior for the language (e.g., in Python, `statistics.mean` raises `StatisticsError`, but `numpy.mean` warns and returns `nan`; choose based on project context or default to explicit failure if undefined).
    4. Ensure the fix does not require changes to other functions, imports, or signatures unless strictly necessary. If external changes are required, halt and escalate, as the locus was not fully contained.

**Gate 2.2: Draft the Patch**
*   **Verifies**: The proposed code change is syntactically valid and logically sound.
*   **Requirement**:
    1. Write the code modification.
    2. Mentally or syntactically trace the new code path. Does it handle the empty case? Does it still calculate the average for non-empty lists?
    3. Ensure no new imports are added unless they are standard library or already present.

## Phase 3: Execution
*The code is changed. This phase is strictly mechanical.*

**Gate 3.1: Apply the Change**
*   **Verifies**: The file in the workspace now contains the drafted patch.
*   **Requirement**:
    1. Modify the file at the identified locus.
    2. Ensure no whitespace, formatting, or unrelated lines are altered. The diff must contain only the repair logic.
    3. If the editor or tool introduces unexpected changes, revert and re-apply.

## Phase 4: Verification
*The repair is not complete until it is proven to fix the defect and not break existing functionality.*

**Gate 4.1: Regression Check (Negative Case)**
*   **Verifies**: The original failure mode is resolved.
*   **Requirement**:
    1. Re-run the minimal reproduction case from Gate 1.2.
    2. Confirm that the error is no longer raised.
    3. Confirm that the output matches the behavior defined in Gate 2.1 (e.g., returns `0.0` or raises the expected domain error).

**Gate 4.2: Preservation Check (Positive Case)**
*   **Verifies**: The repair has not broken the primary function of the code.
*   **Requirement**:
    1. Construct a simple, valid input case (e.g., `[1, 2, 3]`).
    2. Execute the function.
    3. Confirm the output is correct (e.g., `2.0`).
    4. If any valid input now produces an incorrect result or error, halt. Revert the change and return to Phase 2.

**Gate 4.3: Boundary Check (Adjacent Cases)**
*   **Verifies**: The fix does not introduce new edge case failures near the modified logic.
*   **Requirement**:
    1. Test one or two adjacent edge cases relevant to the fix (e.g., a list with a single element, a list with very large numbers, or a list with non-numeric types if the contract allows them).
    2. Confirm behavior is consistent with the function’s contract.
    3. If an unexpected error occurs that was not present before, halt and re-evaluate the design in Phase 2.

## Phase 5: Closure
*The repair is documented and finalized.*

**Gate 5.1: Diff Review**
*   **Verifies**: The final state of the file differs from the initial state only by the intended repair.
*   **Requirement**:
    1. Review the complete diff of the file.
    2. Ensure there are no accidental comments, debug prints, or formatting errors.
    3. Ensure the change is minimal.

**Gate 5.2: Final Commitment**
*   **Verifies**: The repair is ready for integration.
*   **Requirement**:
    1. Mark the defect as "Repaired" or "Fixed."
    2. Record the specific change made (e.g., "Added guard against empty list in `calculate_average`").
    3. Hand off to the next stage (testing/CI) or close the ticket.

---
**Failure Protocol**: If any gate fails, the executor must:
1. Halt immediately.
2. Revert any changes made in Phase 3 if they were not yet verified.
3. Report the specific gate that failed and the reason.
4. Do not attempt to "force" a pass by modifying the test or the defect report.

# Duty: `repair-duty`

**Scope:** This duty governs the execution of a repair for a confirmed software defect with a known locus. It is self-sufficient; the executor requires no external registry, canon, or runtime lookup to navigate the gates.

## Phase 0: Routing Verification (Upstream Hazard Scan)
*Derived from the meta-taboo scan for routing-class hazards. These gates must be satisfied before any modification to the codebase begins.*

### Gate 0.1: Confirm Work Class
- **Verifies:** That the current situation requires a *repair* (fixing a deviation from expected behavior) and not a *feature addition*, *refactor*, or *investigation*.
- **Completion Requirement:** The executor must state explicitly: "The defect is confirmed, the locus is known, and the required action is a corrective fix, not an expansion of scope." If the defect is not yet confirmed or the locus is not pinpointed, this duty halts and returns to the investigation phase.

### Gate 0.2: Confirm Locus Stability
- **Verifies:** That the identified locus (file, line, function) is stable and that no concurrent changes have altered the context of the defect since its identification.
- **Completion Requirement:** The executor must verify that the code at the specified locus matches the description of the defect. If the code at the locus has changed, the duty halts.

## Phase 1: Locus Confirmation & Baseline Establishment
*Derived from first-principles analysis of the repair act: establishing the "before" state and ensuring the defect is reproducible at the exact site.*

### Gate 1.1: Reproduce the Defect
- **Verifies:** That the defect manifests exactly as described when the specific input is applied to the confirmed locus.
- **Completion Requirement:** The executor must demonstrate the failure (e.g., `ZeroDivisionError` in the anchor case) using a minimal, isolated test case or direct execution. The output of this reproduction must be captured as the baseline evidence.

### Gate 1.2: Isolate the Locus
- **Verifies:** That the defect originates solely at the confirmed locus and is not a symptom of a downstream dependency or upstream data corruption.
- **Completion Requirement:** The executor must confirm that the failure is intrinsic to the logic at the locus (e.g., division by zero) and not caused by external factors that would persist even if the locus were fixed.

### Gate 1.3: Establish Regression Baseline
- **Verifies:** That the current test suite (or equivalent verification mechanism) passes for all non-defect behaviors before the change is made.
- **Completion Requirement:** The executor must run the existing verification suite and record the results. Any pre-existing failures unrelated to the defect must be noted and excluded from the repair's success criteria.

## Phase 2: Repair Execution
*Derived from first-principles analysis: the act of changing the code to eliminate the failure mode while preserving intended behavior.*

### Gate 2.1: Define the Correction
- **Verifies:** That the proposed change directly addresses the root cause identified in Gate 1.1 and 1.2, and does not introduce new, unaddressed edge cases.
- **Completion Requirement:** The executor must articulate the specific logical change (e.g., "Add a guard clause to handle empty lists") and confirm it does not alter the return type or contract for valid inputs.

### Gate 2.2: Apply the Minimal Change
- **Verifies:** That the code modification is minimal, touching only the necessary lines at the confirmed locus.
- **Completion Requirement:** The executor applies the change. The diff must be reviewed to ensure no unrelated code, comments, or formatting changes are included.

### Gate 2.3: Validate the Fix
- **Verifies:** That the specific defect no longer manifests and that the intended behavior for valid inputs remains intact.
- **Completion Requirement:** The executor re-runs the reproduction case from Gate 1.1. The output must now reflect the corrected behavior (e.g., returning a defined value or raising a controlled exception instead of an unhandled error). Additionally, the executor must verify that valid inputs (e.g., `calculate_average([1, 2, 3])`) still produce the correct result.

### Gate 2.4: Run Regression Suite
- **Verifies:** That the repair has not introduced new failures in other parts of the system.
- **Completion Requirement:** The executor runs the full verification suite. All tests that passed in Gate 1.3 must still pass. Any new failures must be analyzed; if they are caused by the repair, the duty loops back to Gate 2.1.

## Phase 3: Session Close & Recording (Session-Close Hazard Scan)
*Derived from the meta-taboo scan for session-close-obligation hazards. These gates ensure that knowledge gained during the repair is not lost when the session ends.*

### Gate 3.1: Record the Repair
- **Verifies:** That the change, its rationale, and its validation evidence are recorded in a durable form.
- **Completion Requirement:** The executor must generate a summary including: the defect description, the locus, the applied change, and the validation results (reproduction before/after, regression suite status). This summary is the official record of the repair.

### Gate 3.2: Identify Residual Hazards
- **Verifies:** That the repair did not uncover new, unrelated defects or systemic weaknesses that were not addressed in this session.
- **Completion Requirement:** The executor must list any new issues discovered during the repair (e.g., "The function also fails on `None` input"). These issues are logged for future action but are *not* part of this duty's completion criteria. If no new issues were found, the executor must explicitly state: "No residual hazards identified."

### Gate 3.3: Confirm Session Closure
- **Verifies:** That all obligations of this duty are met and no open threads remain.
- **Completion Requirement:** The executor confirms:
  1. The defect at the confirmed locus is resolved.
  2. The regression suite passes.
  3. The repair is recorded (Gate 3.1).
  4. Residual hazards are logged (Gate 3.2).
  
  Once all four are confirmed, the duty is complete. The session may close.

**End of Duty `repair-duty`**

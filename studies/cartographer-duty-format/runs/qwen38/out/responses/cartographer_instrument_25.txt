# Duty: repair-duty

**Applies to:** Any office of the Agentic Order tasked with remediating a confirmed software defect at a known locus.
**Objective:** To transform a defective state into a verified, corrected state through a sequence of irreversible gates. The executor must not assume context not present in the defect description or the code itself.

## Phase 1: Locus Verification & Baseline Establishment

This phase ensures the executor is operating on the correct artifact and that the defect is reproducible before any modification is attempted.

### Gate 1.1: Locus Integrity
*   **Verifies:** That the file path, line number, and function signature specified in the defect report match the current state of the codebase.
*   **Completion Requirement:**
    1.  Open the file specified in the defect locus.
    2.  Confirm the line number matches the reported defect location.
    3.  Confirm the function name and signature (parameters and return type) match the reported defect.
    4.  If any mismatch exists, halt and report `LOCUS_DRIFT`. Do not proceed.

### Gate 1.2: Reproduction of Failure
*   **Verifies:** That the specific input described in the defect reliably triggers the reported error in the current environment.
*   **Completion Requirement:**
    1.  Construct a minimal test case using the specific input vector cited in the defect (e.g., `[]`).
    2.  Execute the function with this input.
    3.  Confirm the exact error type and message described in the defect are raised.
    4.  Record the error output. If the error does not reproduce, halt and report `REPRO_FAILURE`.

### Gate 1.3: Side-Effect Baseline
*   **Verifies:** That the function does not modify external state (files, databases, global variables) during the failing execution, ensuring the repair will not require rollback of external systems.
*   **Completion Requirement:**
    1.  Inspect the function body for I/O operations, network calls, or writes to global/module-level variables.
    2.  If such operations exist, flag the defect as `COMPLEX_SIDE_EFFECTS` and consult a senior office.
    3.  If the function is pure (returns a value, raises exceptions, modifies only local scope), proceed.

## Phase 2: Defect Analysis & Strategy Selection

This phase determines the logical cause of the failure and selects the appropriate remediation strategy based on the function's intended contract.

### Gate 2.1: Contract Derivation
*   **Verifies:** That the intended behavior for the failing input is explicitly defined or logically derivable from the function's purpose and type hints.
*   **Completion Requirement:**
    1.  Analyze the function name (`calculate_average`) and docstrings (if present) to determine the mathematical or logical intent.
    2.  Determine the expected behavior for the edge case (empty list).
        *   *Option A:* Return a neutral element (e.g., `0.0`).
        *   *Option B:* Raise a specific, descriptive exception (e.g., `ValueError` or `EmptySequenceError`).
        *   *Option C:* Return `None`.
    3.  Select the strategy that best aligns with the library's existing error-handling conventions. Check other functions in the module for similar edge-case handling.
    4.  If no convention exists, default to raising a `ValueError` with a clear message, as this is safer than silently returning a mathematically incorrect default for an undefined operation. Record the selected strategy.

### Gate 2.2: Guard Condition Identification
*   **Verifies:** That a specific, testable condition can be evaluated to distinguish the failing case from valid cases.
*   **Completion Requirement:**
    1.  Identify the variable representing the input data (`values`).
    2.  Define the guard condition that triggers the error path. For the domain anchor (`calculate_average`), the condition is `len(values) == 0`.
    3.  Ensure the guard condition is computationally cheap and does not alter the input.
    4.  If the guard condition is ambiguous or costly, halt and report `GUARD_AMBIGUITY`.

## Phase 3: Implementation

This phase modifies the code to implement the strategy selected in Phase 2.

### Gate 3.1: Minimal Diff Application
*   **Verifies:** That the code change is the smallest possible edit required to implement the guard condition and the chosen response.
*   **Completion Requirement:**
    1.  Insert the guard condition immediately at the start of the function body, before any logic that depends on the input's validity.
    2.  Implement the response defined in Gate 2.1.
        *   *If raising:* `raise ValueError("Cannot calculate average of empty list")`
        *   *If returning:* `return 0.0`
    3.  Do not refactor surrounding code. Do not change variable names. Do not add comments unless the logic is non-obvious.
    4.  Verify the syntax is valid.

### Gate 3.2: Type Safety Preservation
*   **Verifies:** That the modification does not violate the function's declared type signature.
*   **Completion Requirement:**
    1.  If the strategy is to return a value, ensure the returned type matches the return annotation (`float`).
    2.  If the strategy is to raise an exception, ensure the exception is a subclass of `Exception` and does not interfere with the caller's expected exception handling.
    3.  If the strategy involves returning `None`, verify that the return annotation is updated to `Optional[float]` or `float | None`, or halt if the contract strictly requires a float.

## Phase 4: Verification & Closure

This phase confirms the repair works for the defect case and does not break valid cases.

### Gate 4.1: Defect Resolution
*   **Verifies:** That the specific input from Gate 1.2 no longer triggers the original error.
*   **Completion Requirement:**
    1.  Re-execute the test case from Gate 1.2.
    2.  Confirm the behavior matches the strategy selected in Gate 2.1.
        *   *If raising:* Confirm the new exception is raised, not `ZeroDivisionError`.
        *   *If returning:* Confirm the correct value is returned.
    3.  If the original error persists or a new, unintended error occurs, halt and report `REPAIR_FAILURE`.

### Gate 4.2: Regression Check
*   **Verifies:** That the function still operates correctly for valid inputs.
*   **Completion Requirement:**
    1.  Construct a test case with a non-empty list of valid numbers (e.g., `[1, 2, 3]`).
    2.  Execute the function.
    3.  Confirm the result is mathematically correct (e.g., `2.0`).
    4.  If the result is incorrect, halt and report `REGRESSION_DETECTED`.

### Gate 4.3: Edge Case Boundary
*   **Verifies:** That the fix handles the boundary between valid and invalid states correctly.
*   **Completion Requirement:**
    1.  Test a list with a single element (e.g., `[5]`).
    2.  Confirm the result is `5.0`.
    3.  Test a list with negative numbers (e.g., `[-1, 1]`).
    4.  Confirm the result is `0.0`.
    5.  If any boundary test fails, halt and report `BOUNDARY_FAILURE`.

### Gate 4.4: Final State Commit
*   **Verifies:** That the code is in a clean, committed state ready for review.
*   **Completion Requirement:**
    1.  Ensure no debug prints, temporary variables, or commented-out code remain.
    2.  Format the code according to the project's style guide (e.g., PEP 8 for Python).
    3.  Mark the defect as `REPAIRED`.
    4.  Submit the diff for peer review.

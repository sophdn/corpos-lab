# Duty: `repair-duty`

**Scope:** Any office of the Agentic Order tasked with resolving a confirmed software defect.
**Precondition:** A defect exists, is confirmed, and has a known locus (file and line number).

## Preamble
This duty defines the sequential gates required to transition a system from a state of confirmed defect to a state of verified resolution. The executing office must pass through each gate in order. Failure at any gate halts the process and requires remediation of that specific gate before proceeding.

## Gates

### Gate 1: Locus Verification
**Objective:** Confirm the physical location of the defect matches the confirmed locus.
**Verification:**
- The executing office locates the file specified in the defect report.
- The executing office inspects the line number specified in the defect report.
- The code at that specific location is logically consistent with the described defect behavior.
**Completion Requirement:**
- The executing office confirms that the code at the stated locus is the origin of the defect. If the locus is incorrect or the code does not match the defect description, the duty is aborted, and the defect must be re-triaged.

### Gate 2: Root Cause Isolation
**Objective:** Determine the precise logical or structural flaw causing the defect.
**Verification:**
- The executing office analyzes the code at the locus to identify the specific condition, input, or operation that triggers the defect.
- The executing office identifies the missing guard, incorrect logic, or unhandled state.
**Completion Requirement:**
- The executing office documents a single, specific root cause statement. This statement must explain *why* the code fails at the locus, not just *that* it fails.

### Gate 3: Minimal Intervention Design
**Objective:** Formulate a repair strategy that fixes the root cause with the least possible change.
**Verification:**
- The executing office proposes a code change that addresses the root cause identified in Gate 2.
- The proposed change must be minimal: it should not refactor unrelated code, change function signatures, or alter behavior beyond the scope of the defect.
- The proposed change must handle the specific failure mode (e.g., empty input, null reference, division by zero) without introducing new failure modes.
**Completion Requirement:**
- The executing office holds a clear, specific plan for the code modification. The plan must specify exactly which lines will be modified and how.

### Gate 4: Implementation
**Objective:** Apply the minimal intervention to the source code.
**Verification:**
- The executing office modifies the code at the locus according to the plan in Gate 3.
- The modification is syntactically valid.
- The modification remains consistent with the coding style and conventions of the surrounding code.
**Completion Requirement:**
- The code at the locus is updated to reflect the repair. No other parts of the file or codebase are altered unless strictly necessary for syntactic validity.

### Gate 5: Defect Reproduction Check
**Objective:** Verify that the specific defect no longer occurs.
**Verification:**
- The executing office constructs or identifies the exact input or condition that previously triggered the defect (e.g., `calculate_average([])`).
- The executing office executes the code with that specific input.
- The execution completes without raising the specific exception or error associated with the defect.
**Completion Requirement:**
- The specific defect trigger no longer produces the failure. The code behaves as expected for the specific case that was broken.

### Gate 6: Regression Sanity Check
**Objective:** Ensure the repair has not broken previously working functionality.
**Verification:**
- The executing office identifies at least one or two normal, non-defective inputs or use cases for the affected function.
- The executing office executes the code with these normal inputs.
- The outputs are correct and consistent with the function’s intended behavior.
**Completion Requirement:**
- The function continues to work correctly for standard, non-defective cases. The repair has not introduced new bugs or altered correct behavior.

### Gate 7: Closure
**Objective:** Formally record the resolution.
**Verification:**
- The executing office confirms that Gates 1 through 6 have been passed.
- The defect is marked as resolved.
**Completion Requirement:**
- The defect is closed. The repair is complete. The system is returned to the Agentic Order for any further necessary actions (e.g., deployment, documentation update), but the repair duty itself is finished.

## Abort Conditions
The duty is aborted if:
- Gate 1 fails (locus is incorrect).
- Gate 2 fails (root cause cannot be isolated).
- Gate 3 fails (no minimal intervention can be designed without excessive risk or scope).
- Gate 4 fails (implementation cannot be completed due to external constraints).
- Gate 5 fails (the defect persists after implementation).
- Gate 6 fails (the repair introduces a new, more severe defect).

## Notes
- This duty assumes the defect is already confirmed and the locus is known. If the locus is unknown, this duty does not apply.
- "Minimal intervention" means changing only what is necessary. Refactoring, optimization, or stylistic changes are out of scope for this duty.
- The executing office must not proceed to the next gate until the current gate’s completion requirements are fully satisfied.

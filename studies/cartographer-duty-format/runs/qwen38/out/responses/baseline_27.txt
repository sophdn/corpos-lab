# repair-duty

## Purpose
To define the mandatory sequence of gates an executing office of the Agentic Order must pass to successfully repair a confirmed software defect with a known locus.

## Preconditions
1.  **Defect Confirmation**: A defect has been identified and confirmed as reproducible.
2.  **Locus Knowledge**: The specific file and line number (or logical location) of the defect is known (e.g., `calculator.py:2`).
3.  **Execution Context**: The executing office has read/write access to the relevant codebase and execution environment.

## Gates

### Gate 1: Contextual Reproduction
*   **Verifies**: That the defect manifests exactly as described at the known locus.
*   **Requires**:
    1.  Execution of the minimal reproduction case (e.g., `calculate_average([])`).
    2.  Capture of the exact error output (e.g., `ZeroDivisionError`).
    3.  Confirmation that the error originates from the specific locus cited in the precondition.
    4.  If the error does not reproduce or does not originate from the stated locus, the duty **fails** and reverts to the Defect Confirmation phase.

### Gate 2: Root Cause Isolation
*   **Verifies**: That the executing office understands the mechanical cause of the failure at the locus.
*   **Requires**:
    1.  Analysis of the code at the locus to identify the specific operation causing the failure (e.g., division by zero).
    2.  Identification of the missing invariant or unhandled state (e.g., empty list input).
    3.  Documentation of the causal link between the input condition and the error.
    4.  If the root cause cannot be isolated to the locus, the duty **fails** and reverts to Gate 1.

### Gate 3: Remediation Strategy Selection
*   **Verifies**: That a specific, bounded repair strategy is chosen that addresses the root cause without introducing new vulnerabilities.
*   **Requires**:
    1.  Selection of one of the following strategies (or equivalent):
        *   **Guard Clause**: Explicit check for the invalid state (e.g., `if not values: return 0.0` or raise a specific `ValueError`).
        *   **Default Value**: Returning a safe default for the invalid state.
        *   **Input Validation**: Rejecting the invalid input before processing.
    2.  Justification for the chosen strategy based on the function's contract and expected behavior.
    3.  If the chosen strategy alters the function's public API or contract without authorization, the duty **fails** and reverts to Gate 2.

### Gate 4: Code Modification
*   **Verifies**: That the code has been modified to implement the selected strategy at the known locus.
*   **Requires**:
    1.  Application of the fix to the file at the locus (e.g., `calculator.py`).
    2.  Preservation of existing functionality for valid inputs (e.g., `calculate_average([1, 2, 3])` still returns `2.0`).
    3.  Adherence to the project's coding style and conventions.
    4.  If the modification fails to compile or introduces syntax errors, the duty **fails** and reverts to Gate 3.

### Gate 5: Verification of Repair
*   **Verifies**: That the defect is resolved and no new defects have been introduced.
*   **Requires**:
    1.  Re-execution of the original minimal reproduction case (e.g., `calculate_average([])`).
    2.  Confirmation that the original error (e.g., `ZeroDivisionError`) no longer occurs.
    3.  Execution of the chosen remediation's expected behavior (e.g., returns `0.0` or raises `ValueError` as specified in Gate 3).
    4.  Execution of a regression test suite or a set of valid input cases to ensure no existing functionality is broken.
    5.  If the defect persists or new errors appear, the duty **fails** and reverts to Gate 4.

### Gate 6: Finalization
*   **Verifies**: That the repair is complete, documented, and ready for integration.
*   **Requires**:
    1.  Commitment or staging of the modified code.
    2.  Generation of a repair log entry documenting:
        *   The defect ID or description.
        *   The locus.
        *   The root cause.
        *   The strategy chosen.
        *   The verification results.
    3.  Notification to the Defect Confirmation phase that the repair is complete.
    4.  If any documentation is missing, the duty **fails** and reverts to Gate 5.

## Failure Protocol
If any gate fails, the executing office must:
1.  Halt the repair process.
2.  Revert to the failed gate or the preceding gate as specified.
3.  Log the failure reason.
4.  Resume the duty from the reverted gate.

## Termination
The duty is complete when Gate 6 is passed. The defect is considered repaired and the locus is cleared.

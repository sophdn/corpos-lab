# repair-duty

**Purpose:** To govern the repair of a confirmed software defect with a known locus by an office of the Agentic Order.

**Scope:** This duty applies only after a defect has been confirmed and its locus identified. It does not cover defect discovery, triage, or verification of the defect's existence.

**Definitions:**
- **Locus:** The specific location in the codebase where the defect manifests (e.g., file path and line number).
- **Defect:** A confirmed deviation from expected behavior.
- **Gate:** A discrete stage in the repair process that must be completed before proceeding to the next.

---

## Gate 1: Locus Verification

**Verifies:** That the executing office has correctly identified the exact location of the defect in the source code.

**Requires:**
1. Open the file specified by the locus.
2. Confirm that the line(s) referenced in the locus contain the code responsible for the defect.
3. If the locus is ambiguous or incorrect, halt and request clarification of the locus.

**Exit Condition:** The executing office has visually confirmed the defective code at the specified locus.

---

## Gate 2: Root Cause Analysis

**Verifies:** That the executing office understands why the defect occurs and what conditions trigger it.

**Requires:**
1. Identify the specific input or state that causes the defect (e.g., empty list, null value, boundary condition).
2. Determine the underlying flaw in the logic (e.g., missing guard clause, incorrect operator, unhandled edge case).
3. Document the root cause in a concise statement.

**Exit Condition:** The executing office can articulate a clear, testable root cause explanation.

---

## Gate 3: Repair Design

**Verifies:** That a correct and minimal fix has been designed before implementation.

**Requires:**
1. Propose a specific code change that addresses the root cause.
2. Ensure the fix does not introduce new defects or regressions.
3. Consider edge cases that may be affected by the fix.
4. If the fix requires additional context (e.g., access to other modules, configuration changes), identify and document those dependencies.

**Exit Condition:** The executing office has a concrete, written plan for the code change.

---

## Gate 4: Implementation

**Verifies:** That the designed repair has been applied to the codebase.

**Requires:**
1. Apply the code change to the file at the locus.
2. Ensure the change is syntactically valid.
3. Preserve the original code style and conventions.
4. Add or update comments if the fix is non-obvious.

**Exit Condition:** The code at the locus has been modified according to the design in Gate 3.

---

## Gate 5: Verification

**Verifies:** That the repair resolves the defect and does not break existing functionality.

**Requires:**
1. Construct a test case that reproduces the original defect (e.g., `calculate_average([])`).
2. Execute the test case against the modified code.
3. Confirm that the defect no longer manifests (e.g., no exception is raised, or a sensible default is returned).
4. Execute existing test suites or manual checks to confirm no regressions have been introduced.
5. If verification fails, return to Gate 3 and revise the repair design.

**Exit Condition:** The defect is resolved, and no new defects have been introduced.

---

## Gate 6: Documentation and Closure

**Verifies:** That the repair is properly recorded and the duty is formally closed.

**Requires:**
1. Record the defect ID, locus, root cause, and fix in the order's defect log.
2. Note any additional observations or recommendations (e.g., "Consider adding input validation to all list-processing functions").
3. Mark the defect as resolved.
4. Notify the requesting party or supervisor that the repair is complete.

**Exit Condition:** The defect is formally closed in the order's records, and all stakeholders are informed.

---

## Exception Handling

- **If any gate fails:** Halt the duty and report the failure to the supervising office with full context.
- **If the locus is found to be incorrect:** Return to the defect confirmation process and request a corrected locus.
- **If the repair design cannot be safely implemented:** Escalate to the supervising office for guidance.

## Constraints

- The executing office must not modify code outside the locus unless explicitly required by the repair design and justified in Gate 3.
- All changes must be minimal and focused on resolving the confirmed defect.
- The executing office must not skip any gate.

## End of Duty

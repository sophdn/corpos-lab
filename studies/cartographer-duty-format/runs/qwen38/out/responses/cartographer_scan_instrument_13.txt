# Duty: repair-duty

## Preamble
This duty governs the repair of a confirmed software defect with a known locus. The executor possesses only this text. The duty is structured as a sequence of phases and gates. Each gate is a checkable step that defines a verification condition and a completion requirement. The executor must pass every gate in order. If a gate fails, the executor halts and reports the failure; they do not attempt to bypass the gate.

## Phase 1: Pre-Flight & Routing Verification
*This phase addresses upstream routing-class hazards. It verifies that a repair is the correct response to the current state, rather than a new feature request, a refactoring, or an investigation.*

### Gate 1.1: Defect Confirmation & Locus Validity
*   **Verifies:** That the work item is a confirmed defect (not a feature request or stylistic preference) and that the locus (file and line) provided in the context is valid and reproducible.
*   **Requires Completion:**
    1.  Confirm that the defect description specifies an error, crash, or incorrect behavior that deviates from expected functionality.
    2.  Confirm that the locus points to a specific line of code where the defect manifests or originates.
    3.  If the defect is actually a feature request or a non-defect, halt and re-route the task to the appropriate workflow (e.g., `feature-implementation`). Do not proceed to Phase 2.

### Gate 1.2: Change Scope Isolation
*   **Verifies:** That the repair will be confined to the minimum necessary scope to fix the defect, preventing scope creep or uncontrolled refactoring.
*   **Requires Completion:**
    1.  Identify the specific function or module containing the locus.
    2.  Define the boundary of the change: only the code necessary to resolve the defect and maintain syntactic/semantic integrity within that boundary may be modified.
    3.  Explicitly note any code *outside* the locus that must **not** be changed. If the repair requires changes outside the locus to be valid, halt and escalate, as this indicates the locus was insufficient or the defect is more complex than confirmed.

## Phase 2: State Establishment & Pre-Change Verification
*This phase ensures the executor has a stable baseline and understands the current behavior before introducing change.*

### Gate 2.1: Baseline Reproduction
*   **Verifies:** That the defect can be reproduced in the current state of the codebase using the known locus.
*   **Requires Completion:**
    1.  Construct a minimal test case or input sequence that triggers the defect at the known locus.
    2.  Execute this test case against the unmodified code.
    3.  Confirm that the error or incorrect behavior described in the defect report occurs.
    4.  If the defect does not reproduce, halt. The locus may be stale, or the defect may have been fixed previously. Report "Defect not reproducible at locus."

### Gate 2.2: Dependency & Side-Effect Audit
*   **Verifies:** That the executor understands the immediate dependencies of the defective code and the potential side effects of the fix.
*   **Requires Completion:**
    1.  Identify all callers of the function containing the locus.
    2.  Identify any external resources (I/O, network, state) accessed by the defective code path.
    3.  Determine if the fix will change the function’s signature, return type, or error handling contract.
    4.  If the fix changes the public contract (e.g., changing return type from `float` to `Optional[float]`), document the required updates to callers. If callers cannot be updated within the isolated scope, halt and escalate.

## Phase 3: Execution of Repair
*This phase contains the actual modification of the code.*

### Gate 3.1: Minimal Modification
*   **Verifies:** That the code change addresses the specific defect mechanism without introducing unrelated changes.
*   **Requires Completion:**
    1.  Modify the code at the locus to resolve the defect.
    2.  Ensure the modification is syntactically valid.
    3.  Do not rename variables, reformat unrelated lines, or add comments unrelated to the defect fix.
    4.  The change must directly address the root cause identified in the defect description (e.g., handling the empty list case in `calculate_average`).

### Gate 3.2: Immediate Syntax & Lint Check
*   **Verifies:** That the modified code is syntactically correct and passes basic static analysis.
*   **Requires Completion:**
    1.  Run a syntax checker or compiler on the modified file.
    2.  Run any available linter on the modified file.
    3.  Resolve all errors introduced by the modification.
    4.  If pre-existing lint errors are present but unrelated to the change, do not fix them; note them in the final report.

## Phase 4: Verification & Completion
*This phase confirms the repair is successful and safe.*

### Gate 4.1: Defect Resolution Check
*   **Verifies:** That the original defect no longer occurs.
*   **Requires Completion:**
    1.  Re-execute the minimal test case from Gate 2.1.
    2.  Confirm that the error or incorrect behavior is no longer present.
    3.  If the defect persists, halt. The repair was ineffective. Return to Gate 3.1 with a revised hypothesis.

### Gate 4.2: Regression Check
*   **Verifies:** That the repair has not broken existing functionality.
*   **Requires Completion:**
    1.  Execute the existing test suite for the module containing the locus.
    2.  Confirm that all previously passing tests still pass.
    3.  If a test fails, determine if the failure is due to the repair.
        *   If yes, halt. The repair caused a regression. Return to Gate 3.1.
        *   If no (pre-existing failure), note it in the final report and proceed only if the pre-existing failure is unrelated to the logic changed.

### Gate 4.3: Edge Case Validation
*   **Verifies:** That the repair handles edge cases adjacent to the defect locus.
*   **Requires Completion:**
    1.  Identify at least one edge case related to the defect (e.g., for an empty list defect, test a list with one element).
    2.  Execute a test for this edge case.
    3.  Confirm the behavior is logically consistent with the function’s intended purpose.

## Phase 5: Session Close & Post-Act Obligations
*This phase addresses session-close-obligation hazards. It ensures that any discoveries made during the repair are recorded before the session ends, preventing information loss or untracked debt.*

### Gate 5.1: Discovery Recording
*   **Verifies:** That all observations made during the repair that are not directly part of the defect fix are recorded.
*   **Requires Completion:**
    1.  Review the notes taken during Gates 2.2 and 4.2.
    2.  Identify any pre-existing bugs, code smells, or technical debt discovered but not fixed due to scope isolation (Gate 1.2).
    3.  Create a record (ticket, comment, or log entry) for each such discovery, labeled as "Discovered during repair of [Defect ID]."
    4.  If no such discoveries were made, explicitly state "No additional discoveries."

### Gate 5.2: Documentation Update Check
*   **Verifies:** That the repair does not invalidate existing documentation.
*   **Requires Completion:**
    1.  Check if the function’s docstring or external documentation describes the old behavior (e.g., "raises error on empty list").
    2.  If the repair changes the behavior (e.g., now returns 0.0 instead of raising), update the documentation to reflect the new behavior.
    3.  If documentation is not present, do not create it unless required by team convention; instead, note in the final report that documentation is missing.

### Gate 5.3: Final Report & Handoff
*   **Verifies:** That the session is closed with a complete, auditable trail of the repair.
*   **Requires Completion:**
    1.  Compile a final report containing:
        *   Defect ID and Locus.
        *   Description of the change made.
        *   Verification results (Gate 4.1, 4.2, 4.3 outcomes).
        *   List of any recorded discoveries (Gate 5.1).
        *   Status: "Complete" or "Halted due to [Gate]."
    2.  Submit the report and the modified code for review or commit, according to the standard workflow.
    3.  Close the session.

---
**End of Duty**

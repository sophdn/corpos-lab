# Duty: repair-duty

## Purpose
This duty governs the repair of a confirmed software defect at a known locus. It is a sequence of gates. The executor must pass each gate in order. A gate is not passed until its verification condition is met and its completion requirements are satisfied. No external registry, canon, or prior knowledge is required to execute this duty. The duty is self-sufficient.

---

## Phase 1: Confirming the Locus

**Gate 1.1 — Locus Uniqueness**
- **Verifies:** That the defect’s locus is a single, unambiguous location in the codebase.
- **Completion requirement:** The executor has identified exactly one file path and one line number (or contiguous range of lines) where the defect resides. If the locus is ambiguous, undefined, or spans multiple unconnected locations, this gate fails and the duty cannot proceed. The executor must halt and report the ambiguity.

**Gate 1.2 — Defect Reproducibility**
- **Verifies:** That the defect is reproducible at the confirmed locus under a minimal, deterministic input.
- **Completion requirement:** The executor has constructed a minimal input that triggers the defect when executed against the code at the confirmed locus. The input must be minimal (no extraneous data) and deterministic (same output every time). The executor has observed the failure behavior (e.g., exception type, message, or incorrect output) and recorded it. If the defect cannot be reproduced, this gate fails and the duty cannot proceed.

**Gate 1.3 — Locus Isolation**
- **Verifies:** That the defect is isolated to the confirmed locus and does not arise from upstream callers, downstream dependencies, or environment configuration.
- **Completion requirement:** The executor has confirmed that the failure originates at the confirmed locus and not elsewhere. This is done by verifying that the failing behavior occurs when the code at the locus is invoked in isolation with the minimal input, independent of surrounding system state. If the failure depends on external configuration, unconfirmed upstream bugs, or undocumented side effects, this gate fails and the duty cannot proceed.

---

## Phase 2: Establishing the Pre-Change Baseline

**Gate 2.1 — Current Behavior Documentation**
- **Verifies:** That the current, defective behavior at the locus is fully documented before any change is made.
- **Completion requirement:** The executor has recorded:
  1. The exact input(s) that trigger the defect.
  2. The exact failure mode (exception type, message, or incorrect output).
  3. The expected correct behavior (what the code *should* do with that input).
  This documentation must be specific enough that a third party could verify the defect without reading the code. If the expected behavior is undefined or ambiguous, this gate fails and the duty cannot proceed.

**Gate 2.2 — Scope Containment**
- **Verifies:** That the repair will not alter behavior outside the confirmed locus.
- **Completion requirement:** The executor has identified all code paths that depend on the current behavior at the locus and has determined which of those paths must remain unchanged. The executor has listed any callers, tests, or dependent modules that rely on the current (defective) behavior and has confirmed that the repair will not break them unless they are themselves part of the defect. If the scope of the repair cannot be contained to the locus and its immediate dependencies, this gate fails and the duty cannot proceed.

**Gate 2.3 — No-Op Verification**
- **Verifies:** That the codebase is in a stable, unmodified state before the repair is applied.
- **Completion requirement:** The executor has confirmed that no other changes are in progress, no temporary debug code exists at or near the locus, and the codebase matches the state in which the defect was confirmed. If the codebase is in a dirty or unstable state, this gate fails and the duty cannot proceed.

---

## Phase 3: Applying the Repair

**Gate 3.1 — Minimal Change**
- **Verifies:** That the repair alters only the code necessary to fix the defect at the confirmed locus.
- **Completion requirement:** The executor has made a change that is minimal in scope: no new features, no refactoring, no stylistic improvements, no unrelated fixes. The change addresses only the defective behavior at the locus. If the change includes any modification that is not directly required to fix the defect, this gate fails and the change must be reverted.

**Gate 3.2 — Semantic Correctness**
- **Verifies:** That the repaired code produces the expected correct behavior for the minimal input that triggered the defect.
- **Completion requirement:** The executor has executed the minimal input against the repaired code and observed the expected correct behavior as documented in Gate 2.1. The failure mode (exception, incorrect output) no longer occurs. If the defect is not resolved, this gate fails and the repair must be revised.

**Gate 3.3 — Regression Check**
- **Verifies:** That the repair does not break any behavior that was previously correct.
- **Completion requirement:** The executor has executed all existing tests that cover the locus and its immediate dependencies. All tests must pass. If no tests exist, the executor has manually verified that the repaired code behaves correctly for a representative set of valid inputs (not just the defect-triggering input). If any previously correct behavior is broken, this gate fails and the repair must be revised.

**Gate 3.4 — Edge Case Coverage**
- **Verifies:** That the repair handles not only the specific defect but also reasonable edge cases related to the locus.
- **Completion requirement:** The executor has identified and tested reasonable edge cases that are adjacent to the defect (e.g., if the defect is a division by zero, the executor has tested with a list containing one element, a list with all zeros, etc.). The repaired code must handle these edge cases correctly or fail gracefully with a clear, documented error. If an edge case reveals a new defect or unhandled failure mode, this gate fails and the repair must be revised or the duty must be halted if the new defect is outside the scope of the original locus.

---

## Phase 4: Closing Out the Repair

**Gate 4.1 — Final Verification**
- **Verifies:** That the defect is fully resolved and the codebase is in a stable, correct state.
- **Completion requirement:** The executor has re-executed the minimal input from Gate 1.2 and confirmed the expected correct behavior. The executor has re-executed all relevant tests from Gate 3.3 and confirmed they pass. The executor has confirmed that no debug code, comments, or temporary artifacts remain from the repair process. If any of these checks fail, this gate fails and the duty cannot proceed.

**Gate 4.2 — Documentation Update**
- **Verifies:** That the repair is documented for future reference.
- **Completion requirement:** The executor has recorded:
  1. The defect description and locus.
  2. The minimal input that triggered the defect.
  3. The expected correct behavior.
  4. The change made and its rationale.
  5. The verification steps performed.
  This documentation must be specific enough that a future executor could understand what was fixed and why, without reading the original defect report. If the documentation is incomplete or ambiguous, this gate fails.

**Gate 4.3 — Handoff Readiness**
- **Verifies:** That the codebase is ready for handoff to the next stage of the workflow.
- **Completion requirement:** The executor has confirmed that:
  1. The repaired code is committed or staged for commit, as per workflow convention.
  2. No local modifications remain that are not part of the repair.
  3. The documentation from Gate 4.2 is attached or referenced in the handoff.
  If any of these conditions are not met, this gate fails and the handoff cannot proceed.

---

## Execution Rule

The executor must pass Gates 1.1 through 4.3 in order. A gate is passed only when its verification condition is met and its completion requirements are satisfied. If any gate fails, the executor must halt, document the failure, and report it. The duty is complete only when Gate 4.3 is passed.

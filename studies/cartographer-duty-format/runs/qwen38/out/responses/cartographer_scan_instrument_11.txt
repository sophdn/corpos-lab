# repair-duty

**Status:** Active
**Scope:** Confirmed software defect with a known locus.
**Executor:** Any office of the Agentic Order.

## Purpose

This duty governs the act of repairing a confirmed software defect. It maps the path from confirmation of the defect to closure of the repair session. The executor holds only this text. No external registry, canon, or history is required.

---

## Phase 1: Pre-Repair Validation (Upstream Routing)

**Objective:** Verify that the act is a repair, not a different class of work, and that the locus is stable.

### Gate 1.1: Defect Classification Confirmation
*   **Verifies:** The situation is a *defect* (observed behavior contradicts specified or intended behavior) and not a feature request, security vulnerability, performance optimization, or documentation gap.
*   **Completes when:** The executor has explicitly stated:
    1.  The expected behavior.
    2.  The observed behavior.
    3.  The divergence between them constitutes a defect.
    *If any of these are missing or ambiguous, the duty halts. This is not a repair.*

### Gate 1.2: Locus Stability Check
*   **Verifies:** The known locus (file, line, function) is the actual source of the defect, not a downstream symptom.
*   **Completes when:** The executor has traced the control flow from the point of failure back to the locus and confirmed that the defect originates *at* the locus, not in a caller or callee that merely propagates the error.

### Gate 1.3: Scope Isolation
*   **Verifies:** The repair can be contained to the locus and its immediate dependencies without altering the public API or behavior of unrelated components.
*   **Completes when:** The executor has identified all functions, classes, or modules that will be modified. If the scope exceeds the locus and its direct dependents, the duty halts for re-scoping.

---

## Phase 2: Pre-Change Baseline

**Objective:** Establish a verifiable state before any modification is made.

### Gate 2.1: Reproducibility Confirmation
*   **Verifies:** The defect can be reproduced deterministically at the locus using the current code state.
*   **Completes when:** The executor has written or identified a minimal test case (or manual procedure) that:
    1.  Inputs the failing condition (e.g., `calculate_average([])`).
    2.  Triggers the defect (e.g., raises `ZeroDivisionError`).
    3.  Fails against the current code.

### Gate 2.2: Environmental Snapshot
*   **Verifies:** The execution environment is stable and the baseline behavior is captured.
*   **Completes when:** The executor has recorded the exact version of the code, dependencies, and environment variables required to reproduce the defect.

---

## Phase 3: The Repair Act

**Objective:** Implement the change at the locus that resolves the defect.

### Gate 3.1: Minimal Intervention
*   **Verifies:** The change is the smallest possible modification to resolve the defect.
*   **Completes when:** The executor has drafted the diff and confirmed that no lines are added or modified that do not directly contribute to resolving the specific defect. Refactoring, style changes, or unrelated bug fixes are prohibited in this gate.

### Gate 3.2: Intent Alignment
*   **Verifies:** The proposed change aligns with the documented or intended behavior established in Gate 1.1.
*   **Completes when:** The executor has explained how the new behavior at the locus satisfies the expected behavior defined in Gate 1.1.

### Gate 3.3: Change Application
*   **Verifies:** The code at the locus is modified.
*   **Completes when:** The executor has applied the edit to the source file. No other files are touched.

---

## Phase 4: Post-Change Verification

**Objective:** Confirm the defect is resolved and no new defects are introduced.

### Gate 4.1: Defect Resolution Check
*   **Verifies:** The original failure mode no longer occurs.
*   **Completes when:** The executor has re-run the minimal test case from Gate 2.1. The test now passes (or the manual procedure yields the expected behavior).

### Gate 4.2: Regression Scan
*   **Verifies:** The change has not broken existing functionality.
*   **Completes when:** The executor has run the existing test suite (or an equivalent verification mechanism) for the module containing the locus. All previously passing tests continue to pass.

### Gate 4.3: Edge Case Validation
*   **Verifies:** The repair handles adjacent edge cases correctly.
*   **Completes when:** The executor has tested at least one additional input that exercises the modified logic but was not part of the original defect. The behavior is consistent with the intent.

---

## Phase 5: Session Close-Out (Downstream Obligations)

**Objective:** Record discoveries and ensure the session ends in a clean state.

### Gate 5.1: Discovery Log
*   **Verifies:** Any new information uncovered during the repair is recorded.
*   **Completes when:** The executor has documented:
    1.  Whether the root cause was fully understood or only the symptom fixed.
    2.  Any related defects observed but not fixed (for future work).
    3.  Any assumptions made during the repair.
    *If no discoveries were made, the log states "None."*

### Gate 5.2: Artifact Integrity
*   **Verifies:** The source code is in a consistent, committable state.
*   **Completes when:** The executor has confirmed that the file containing the repair is syntactically valid and that no temporary files, debug statements, or comments are left in the production code.

### Gate 5.3: Session Closure
*   **Verifies:** The repair session is formally closed.
*   **Completes when:** The executor has marked the defect as "Resolved" in their local tracking system (if one exists) or has stated: "Repair complete. Defect resolved. Session closed."

---

## Meta-Taboo Scan Results

This duty explicitly addresses two classes of hazards that are not visible from first-principles analysis of the repair act alone:

1.  **Routing-Class Hazards (Upstream):**
    *   *Hazard:* The executor may begin work on a situation that is not a defect (e.g., a feature request, a security flaw, or a performance issue), leading to incorrect scope or inappropriate solutions.
    *   *Structural Gate:* **Gate 1.1 (Defect Classification Confirmation)** and **Gate 1.2 (Locus Stability Check)** force the executor to verify the nature of the work before proceeding. This prevents the repair act from being applied to non-defect situations.

2.  **Session-Close-Obligation Hazards (Downstream):**
    *   *Hazard:* The executor may fix the immediate defect but fail to record critical context (e.g., that the fix is a band-aid, or that a related defect was discovered), leading to loss of institutional knowledge or future regressions.
    *   *Structural Gate:* **Gate 5.1 (Discovery Log)** and **Gate 5.2 (Artifact Integrity)** ensure that all relevant discoveries are recorded and the codebase is left in a clean state before the session ends. This prevents the loss of information that would only be apparent upon reflection, not during the act itself.

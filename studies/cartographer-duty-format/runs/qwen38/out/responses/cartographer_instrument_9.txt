# repair-duty

**Applicability**
This duty applies to any office of the Agentic Order tasked with repairing a confirmed software defect where the locus has already been established. It governs the execution of the repair act from the moment the office receives the defect report until the repair is formally closed.

**Principle of Autonomy**
The executor of this duty possesses only this text. The executor does not consult external registries, canonical slugs, or prior art. Every constraint below is derived from the first-principles analysis of the act of repairing code. The executor must treat the codebase as an unknown system where the only known fact is the location of the failure.

***

## Phase I: Locus Stabilization
*Objective: Ensure the executor is operating on the correct artifact and has isolated the specific mechanism of failure before altering any state.*

### Gate 1: Artifact Integrity Verification
**Verification:**
This gate verifies that the file and line number cited in the defect report correspond to the actual source of the error. It checks that the code at the specified locus is the code responsible for the observed behavior, preventing repairs to the wrong function, the wrong file, or a stale version of the code.

**Completion Requirement:**
- The executor has opened the file at the specified locus.
- The executor has confirmed that the code at this locus matches the context described in the defect report (e.g., the function name, the logic flow).
- The executor has verified that the file has not been modified since the defect was reported, or if it has, the locus has been re-mapped to the current state of the file.
- **Output:** A confirmed, immutable reference to the exact function and line(s) to be modified.

### Gate 2: Failure Mechanism Isolation
**Verification:**
This gate verifies that the executor understands *why* the code fails at the locus, not just *that* it fails. It distinguishes between a logical error, a type error, and an environmental error. It ensures that the repair targets the root cause rather than the symptom.

**Completion Requirement:**
- The executor has identified the specific input or condition that triggers the error (e.g., an empty list, `None`, a negative number).
- The executor has traced the execution path from the entry point to the locus to confirm the data flow.
- The executor has explicitly stated the failure mechanism in their own words (e.g., "Division by zero occurs because `len(values)` is zero when `values` is empty").
- **Output:** A precise statement of the failure condition and the root cause.

***

## Phase II: State Preservation
*Objective: Protect the integrity of the system and the reproducibility of the defect before any changes are made.*

### Gate 3: Baseline Capture
**Verification:**
This gate verifies that the current, broken state is fully documented. It ensures that if the repair fails or introduces new errors, the office can revert to a known state. It prevents the "mystery break" where an executor cannot distinguish between their own changes and pre-existing instability.

**Completion Requirement:**
- The executor has generated a minimal, reproducible test case or input that triggers the specific failure at the locus.
- The executor has recorded the exact error message and stack trace (if applicable) associated with this input.
- The executor has saved the current state of the file (e.g., via version control snapshot or backup) prior to editing.
- **Output:** A recorded baseline error trace and a preserved copy of the pre-repair file.

### Gate 4: Scope Boundary Definition
**Verification:**
This gate verifies that the repair is confined to the necessary extent. It prevents scope creep, where an executor refactors unrelated code, changes function signatures, or alters global state while fixing a local defect. It ensures that the blast radius of the change is minimal.

**Completion Requirement:**
- The executor has explicitly listed the only lines of code that will be modified.
- The executor has confirmed that no public interfaces (function signatures, return types, exported variables) will be changed unless strictly required by the repair.
- The executor has identified any downstream code that depends on the function being repaired to ensure compatibility is maintained.
- **Output:** A defined scope of modification limited to the locus and any immediately necessary helper logic.

***

## Phase III: The Repair Act
*Objective: Implement the change that resolves the failure mechanism while preserving the intended behavior for all non-failing inputs.*

### Gate 5: Defensive Logic Implementation
**Verification:**
This gate verifies that the new code handles the identified failure condition without breaking the primary function. It checks that the fix is robust, not merely a patch that hides the error. It ensures that the logic for valid inputs remains unchanged.

**Completion Requirement:**
- The executor has modified the code at the locus to handle the failure condition identified in Gate 2.
- The modification must be explicit (e.g., returning a default value, raising a custom exception, or handling the edge case) rather than implicit (e.g., catching a broad exception without re-raising or handling specific cases).
- The executor has verified that the logic for valid inputs (e.g., a non-empty list) produces the same result as before the repair.
- **Output:** The modified code snippet with the defensive logic in place.

### Gate 6: Input Space Coverage
**Verification:**
This gate verifies that the repair does not introduce new failure modes. It checks the code against a representative set of inputs, including the original failure case, the normal success case, and boundary cases near the failure point. It ensures the fix is general, not specific to the single reported instance.

**Completion Requirement:**
- The executor has mentally or physically tested the modified code against:
  1. The original failing input (e.g., `[]`).
  2. A standard valid input (e.g., `[1, 2, 3]`).
  3. A boundary input adjacent to the failure (e.g., `[0]`, `[None]` if applicable).
- The executor has confirmed that no new exceptions are raised for inputs that were previously valid.
- **Output:** A confirmation that the input space has been probed and the repair holds across these cases.

***

## Phase IV: Validation and Closure
*Objective: Confirm that the repair is complete, verifiable, and safe to release.*

### Gate 7: Regression Check
**Verification:**
This gate verifies that the repair has not broken any existing functionality. It checks that the changes are isolated and that the broader system remains stable. It prevents the "fix one, break two" scenario.

**Completion Requirement:**
- The executor has reviewed the code for any side effects (e.g., changes to variable scope, unintended mutations of input data).
- The executor has confirmed that the function's contract (input types, output types, side effects) remains consistent with the original intent, except for the specific edge case now handled.
- If any test suite exists, the executor has noted that it should be run to confirm no regressions.
- **Output:** A statement of confidence that the repair is isolated and non-regressive.

### Gate 8: Final State Documentation
**Verification:**
This gate verifies that the repair is complete and documented for the next office. It ensures that the resolution is clear, the changes are traceable, and the defect is formally closed. It prevents the loss of context regarding *why* the code was changed.

**Completion Requirement:**
- The executor has documented the change, including the original failure, the root cause, and the specific fix applied.
- The executor has confirmed that the code at the locus no longer produces the reported error when given the failing input.
- The executor has formally closed the defect, marking the locus as repaired.
- **Output:** A final report confirming the repair, with the modified code and the reasoning for the change.

***

**End of Duty**

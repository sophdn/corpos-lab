# Duty: Repair

This duty governs the repair of a confirmed software defect with a known locus. An executing office must pass through the following gates in strict sequential order. No gate may be skipped. If a gate fails, the duty terminates with a failure state, and the defect remains open.

## Contextual Definitions
*   **Defect:** A confirmed bug in the software.
*   **Locus:** The specific file and line number where the defect manifests or originates.
*   **Office:** The agent or executor performing the repair.

## Gate 1: Locus Verification
*   **Verification:** The Office verifies that the current codebase contains the defect at the specified Locus. The Office must confirm that the code at the Locus matches the pre-repair state described in the defect report.
*   **Requirement to Complete:** The Office must produce a snapshot of the code at the Locus prior to modification, confirming the presence of the flawed logic. If the code at the Locus does not match the defect description, the duty fails.

## Gate 2: Root Cause Isolation
*   **Verification:** The Office identifies the specific logical error at the Locus that causes the defect. The Office must articulate the mechanism of failure (e.g., missing guard clause, incorrect operator, off-by-one error).
*   **Requirement to Complete:** The Office must document the root cause in a single sentence that explains *why* the current code fails the expected behavior. This documentation must be linked to the specific line of code at the Locus.

## Gate 3: Repair Strategy Selection
*   **Verification:** The Office selects a minimal repair strategy that addresses the root cause without introducing new side effects. The strategy must be scoped to the Locus or its immediate functional context.
*   **Requirement to Complete:** The Office must define the exact code change to be applied. This includes specifying the new logic, any necessary error handling (e.g., raising a specific exception, returning a safe default, or validating input), and any required type hints or documentation updates.

## Gate 4: Implementation
*   **Verification:** The Office applies the repair strategy to the code at the Locus. The modification must be syntactically valid and conform to the project’s coding standards.
*   **Requirement to Complete:** The code at the Locus is updated to reflect the repair strategy. The Office must ensure that the change is atomic and isolated to the necessary scope.

## Gate 5: Verification of Repair
*   **Verification:** The Office constructs a test case that specifically triggers the defect conditions (e.g., the input that previously caused the failure). The Office must also verify that existing, non-defective behavior remains intact.
*   **Requirement to Complete:** The Office must demonstrate that:
    1.  The specific input that previously triggered the defect now produces the expected, correct output or a controlled, appropriate error response.
    2.  At least one standard, non-defective input still produces the correct output, confirming no regression.

## Gate 6: Documentation Update
*   **Verification:** The Office ensures that the repair is documented in the project’s change log or issue tracker. The documentation must link the repair to the original defect report.
*   **Requirement to Complete:** The Office must record the following:
    *   The defect ID.
    *   The Locus (file and line).
    *   The root cause.
    *   The repair strategy applied.
    *   The verification results.

## Gate 7: Handoff
*   **Verification:** The Office confirms that all previous gates have been successfully completed and that the codebase is in a stable state.
*   **Requirement to Complete:** The Office formally closes the defect ticket, marking it as "Resolved." The Office transfers responsibility for the repaired code to the standard maintenance process.

## Failure Conditions
If any gate fails, the Office must:
1.  Halt the repair process.
2.  Revert any changes made to the codebase to the pre-repair state (if applicable and safe).
3.  Log the failure at the specific gate where it occurred.
4.  Report the failure to the supervisory office, including the gate number and the reason for failure.

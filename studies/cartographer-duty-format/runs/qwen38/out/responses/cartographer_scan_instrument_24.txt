# Repair-Duty

## Preamble
This duty governs the execution of a repair for a confirmed software defect with a known locus. It is designed to be self-sufficient; the executor requires no external registry, canon, or historical context beyond this text. The executor must follow the gates in order. If a gate cannot be passed, the duty fails and the repair is aborted.

## Phase 1: Pre-Execution Verification (Upstream Routing)
*These gates address obligations that sit upstream of the repair act. They ensure the repair is the correct response to the situation before any change is made.*

### Gate 1.1: Validity of Repair Classification
*   **Verifies:** That the situation calling for action is correctly classified as a "repair" of a "confirmed defect" rather than a new feature request, a refactor, or a performance optimization.
*   **Completion Requirement:** The executor must confirm that a specific, reproducible failure mode exists (the defect) and that the goal is to eliminate that failure without altering the intended external behavior of the system for non-defective inputs. If the situation requires adding new capability or changing intended behavior, this duty is inapplicable; abort.

### Gate 1.2: Locus Confirmation
*   **Verifies:** That the location of the defect is precisely identified and isolated.
*   **Completion Requirement:** The executor must state the exact file path and line number(s) where the defect resides. The locus must be singular and specific. If the locus is ambiguous, distributed, or unknown, abort. For this instance, the locus is confirmed at `calculator.py:2`.

## Phase 2: Pre-Change Establishment
*These gates address what the act must establish before it changes anything. They prevent divergence caused by misunderstanding the current state.*

### Gate 2.1: Baseline Reproduction
*   **Verifies:** That the defect is currently active and reproducible at the confirmed locus.
*   **Completion Requirement:** The executor must demonstrate the failure by executing the specific input that triggers the defect. For this instance, executing `calculate_average([])` must raise `ZeroDivisionError`. If the defect does not reproduce, the locus is invalid or the environment is inconsistent; abort.

### Gate 2.2: Contract Definition
*   **Verifies:** That the expected behavior for the defective case is clearly defined.
*   **Completion Requirement:** The executor must define the correct output for the failing input. For this instance, the correct behavior for `calculate_average([])` must be explicitly defined (e.g., returning `0.0`, `None`, or raising a specific domain error). This definition must be derived from the function’s documented purpose or standard mathematical convention, not assumed. If the expected behavior is undefined, the repair is undefined; abort.

## Phase 3: The Change
*These gates address what a correct change looks like. They ensure the modification is minimal, targeted, and syntactically valid.*

### Gate 3.1: Minimal Intervention
*   **Verifies:** That the change is confined to the confirmed locus and does not alter unrelated code.
*   **Completion Requirement:** The executor must modify only the code necessary to resolve the specific failure at the locus. No refactoring, no style changes, no addition of unrelated logic. For this instance, the change must be limited to the `calculate_average` function in `calculator.py`.

### Gate 3.2: Syntax and Semantic Validity
*   **Verifies:** That the modified code is syntactically correct and semantically coherent within its context.
*   **Completion Requirement:** The executor must ensure the new code compiles/parses without error and does not introduce new undefined variables or broken references. For this instance, adding a guard clause for an empty list must not break the existing logic for non-empty lists.

## Phase 4: Post-Change Verification
*These gates address how completion is confirmed. They ensure the repair works and does not cause regressions.*

### Gate 4.1: Defect Resolution
*   **Verifies:** That the specific failing input no longer causes the defect.
*   **Completion Requirement:** The executor must re-execute the failing input. For this instance, `calculate_average([])` must no longer raise `ZeroDivisionError` and must return the value defined in Gate 2.2. If the error persists, the repair failed; abort.

### Gate 4.2: Regression Check
*   **Verifies:** That non-defective inputs still behave as expected.
*   **Completion Requirement:** The executor must execute at least one valid, non-empty input (e.g., `calculate_average([1, 2, 3])`) and confirm the output remains correct (e.g., `2.0`). If the valid input fails or produces an incorrect result, the repair has caused a regression; abort.

## Phase 5: Session Close and Obligation Recording
*These gates address obligations that fire after the act, on session close. They ensure nothing discovered during the repair is left unrecorded.*

### Gate 5.1: Discovery Log
*   **Verifies:** That any anomalies, secondary defects, or ambiguities discovered during the repair process are recorded.
*   **Completion Requirement:** The executor must list any issues found that were not part of the original defect but were observed during reproduction or testing. For example, if `calculate_average([1, "a"])` raises a different error, this must be logged as a separate issue. If no new issues were discovered, state "None."

### Gate 5.2: Final State Declaration
*   **Verifies:** That the session ends with a clear statement of the repair’s outcome.
*   **Completion Requirement:** The executor must explicitly state: "Repair Complete" if all gates passed, or "Repair Failed" with the specific gate that failed. This declaration closes the session and prevents ambiguous handoffs.

---
**End of Duty**

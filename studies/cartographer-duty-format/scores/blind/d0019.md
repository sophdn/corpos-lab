# repair-duty

## Preamble
This duty governs the act of repairing a confirmed software defect. The defect has a known locus. The executor possesses only this text. The duty is a map of gates. Passing every gate, in order, constitutes a complete and valid repair. No external registry, canon, or context is required to execute this duty.

## Phase I: Confirming the Locus

**Gate 1.1: Verify the Defect Manifestation**
*   **Verifies:** That the defect actually manifests at the stated locus under the stated conditions.
*   **Requires:**
    1.  Isolate the function or code block containing the locus.
    2.  Execute the specific input condition that triggers the defect (e.g., the empty list `[]` for the domain anchor).
    3.  Confirm that the resulting error or incorrect behavior matches the confirmed defect description exactly.
    4.  If the defect does not manifest as described, halt. The locus is unconfirmed.

**Gate 1.2: Verify Locus Precision**
*   **Verifies:** That the identified line or code segment is the singular point of failure, not a symptom downstream of a deeper issue.
*   **Requires:**
    1.  Trace the execution path leading to the locus.
    2.  Confirm that no upstream logic (input validation, prior transformation) is responsible for the invalid state encountered at the locus.
    3.  If the root cause resides upstream, update the locus to the true origin and restart Phase I. If the root cause is genuinely at the current locus, proceed.

## Phase II: Establishing the Pre-Change Baseline

**Gate 2.1: Define the Correct Behavior Contract**
*   **Verifies:** That the intended behavior for the defect condition is explicitly defined before any code is altered.
*   **Requires:**
    1.  Articulate the expected output or state for the specific failing input (e.g., for an empty list, should it return `0.0`, raise a custom error, or return `None`?).
    2.  Justify the chosen behavior based on the domain logic of the function (e.g., mathematical convention, user safety, or API consistency).
    3.  If the expected behavior is ambiguous, halt. The repair cannot proceed without a defined target.

**Gate 2.2: Capture the Regression Baseline**
*   **Verifies:** That the current correct behavior of the function, for all non-failing inputs, is documented or tested before modification.
*   **Requires:**
    1.  Identify at least one valid input case that currently produces the correct output.
    2.  Record the expected output for this valid case.
    3.  If no test exists, manually execute a valid input and record the result. This recorded result is the baseline against which the repair must not deviate.

## Phase III: Executing the Change

**Gate 3.1: Implement the Minimal Intervention**
*   **Verifies:** That the code change addresses *only* the defect and does not alter unrelated logic.
*   **Requires:**
    1.  Modify the code at the locus to satisfy the Correct Behavior Contract from Gate 2.1.
    2.  Ensure the change is syntactically valid.
    3.  Avoid refactoring, renaming, or restructuring code that is not directly involved in the defect handling. The change must be minimal and surgical.

**Gate 3.2: Verify Syntactic and Static Integrity**
*   **Verifies:** That the modified code is structurally sound and free of obvious static errors.
*   **Requires:**
    1.  Check for syntax errors (e.g., unclosed brackets, invalid operators).
    2.  Ensure the function signature remains unchanged unless explicitly required by the Correct Behavior Contract.
    3.  If a linter or compiler is available, run it on the modified file. If not, manually inspect the diff for structural integrity.

## Phase IV: Confirming the Repair

**Gate 4.1: Verify Defect Resolution**
*   **Verifies:** That the specific failing input no longer produces the defect.
*   **Requires:**
    1.  Re-execute the specific input condition that triggered the defect (from Gate 1.1).
    2.  Confirm that the output or state now matches the Correct Behavior Contract defined in Gate 2.1.
    3.  If the defect persists or a new error arises, halt. Return to Phase III.

**Gate 4.2: Verify Regression Integrity**
*   **Verifies:** That the repair has not broken previously correct behavior.
*   **Requires:**
    1.  Re-execute the valid input case identified in Gate 2.2.
    2.  Confirm that the output matches the recorded baseline from Gate 2.2.
    3.  If the output deviates from the baseline, halt. The repair has introduced a regression. Return to Phase III.

**Gate 4.3: Confirm Locus Closure**
*   **Verifies:** That the code at the locus is now stable and the defect is fully contained.
*   **Requires:**
    1.  Review the final code at the locus.
    2.  Confirm that no temporary debug code, comments, or unused variables remain.
    3.  Confirm that the fix is self-contained and does not rely on external state changes that were not part of the original function contract.

## Phase V: Closing the Repair

**Gate 5.1: Document the Repair**
*   **Verifies:** That the change is recorded for audit and future reference.
*   **Requires:**
    1.  Write a concise summary of the defect, the root cause at the locus, the chosen behavior for the failing case, and the specific code change made.
    2.  Ensure the documentation is attached to the change record or commit message.

**Gate 5.2: Final Sign-Off**
*   **Verifies:** That all gates in Phases I through IV have been passed without exception.
*   **Requires:**
    1.  Review the checklist of Gates 1.1 through 4.3.
    2.  Confirm that each gate’s "Requires" step was completed successfully.
    3.  Mark the repair as complete. The duty is satisfied.

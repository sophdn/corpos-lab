# Duty: `repair-duty`

**Status:** Active
**Scope:** Any office of the Agentic Order executing a confirmed software defect repair with a known locus.
**Precondition:** The defect has been confirmed to exist, and its locus (file path and specific line/function) has been identified.

## Purpose
This duty ensures that a repair is executed with structural integrity, avoiding common failure modes inherent to the act of modifying code. It functions as a map for the executor: each gate must be passed in sequence. The executor must not proceed to the next gate until the current gate’s completion requirements are met.

---

## Phase 1: Locus Confirmation & Scope Isolation

**Objective:** Verify that the repair target is precise and that the scope of the change is isolated to the defect.

### Gate 1: Locus Verification
*   **Verifies:** That the confirmed locus points to the actual source of the failure, not merely a symptom or a caller of the failing component.
*   **Completion Requirement:** The executor has identified the specific function, method, or code block where the error originates. If the defect is a logic error, the specific conditional or calculation is identified. If the defect is a crash (e.g., `ZeroDivisionError`), the specific operation causing the crash is identified. The executor confirms that no upstream caller is the root cause.

### Gate 2: Scope Isolation
*   **Verifies:** That the repair will only modify the code necessary to fix the defect.
*   **Completion Requirement:** The executor has defined the minimal set of lines or expressions to be changed. Any refactoring, style improvement, or feature addition is explicitly excluded from the repair scope. The executor confirms that the change will not alter the public API (function signature, return type) unless the defect itself is an API mismatch.

---

## Phase 2: Pre-Repair Baseline & Intent

**Objective:** Establish a correct reference point and clarify the intended behavior before modifying code.

### Gate 3: Baseline Reproduction
*   **Verifies:** That the defect is reproducible in the current state of the codebase.
*   **Completion Requirement:** The executor has written or identified a test case (or manual verification step) that triggers the defect. The executor confirms that this test currently fails. If no test exists, the executor notes the need for a regression test in Phase 4.

### Gate 4: Intent Specification
*   **Verifies:** That the correct behavior for the edge case or defect scenario is defined.
*   **Completion Requirement:** The executor has stated, in natural language, what the function *should* return or do when the defect-triggering input is provided. For example: "When `values` is empty, the function should return `0.0`" or "When `values` is empty, the function should raise a `ValueError` with a specific message." This intent must be derived from domain requirements, not assumed.

---

## Phase 3: Execution & Verification

**Objective:** Implement the change and verify that it resolves the defect without introducing new errors.

### Gate 5: Minimal Implementation
*   **Verifies:** That the code change aligns with the Intent Specification and Scope Isolation.
*   **Completion Requirement:** The executor has applied the code change. The change is limited to the scope defined in Gate 2. The logic of the change directly addresses the Intent defined in Gate 4. No unrelated code has been touched.

### Gate 6: Regression Check
*   **Verifies:** That the repair does not break existing, correct behavior.
*   **Completion Requirement:** The executor has run the existing test suite (or performed manual verification of known correct cases). All previously passing tests still pass. The executor confirms that the repair has not altered behavior for valid inputs.

### Gate 7: Defect Resolution Check
*   **Verifies:** That the specific defect is no longer present.
*   **Completion Requirement:** The test case or verification step from Gate 3 now passes. The executor confirms that the specific input that caused the failure now produces the intended output or behavior defined in Gate 4.

---

## Phase 4: Completion & Session Close

**Objective:** Ensure the repair is documented, regression-protected, and that the session is closed cleanly.

### Gate 8: Regression Protection
*   **Verifies:** That the specific defect scenario is now covered by an automated test.
*   **Completion Requirement:** The executor has added or updated a test case that specifically tests the defect scenario (e.g., empty list input). This test is committed alongside the repair. If the office does not have test infrastructure, the executor has documented the manual verification steps in the repair log.

### Gate 9: Routing Confirmation (Upstream Hazard Scan)
*   **Verifies:** That the work performed was indeed a *repair* and not a different type of work (e.g., feature development, refactoring, or architectural change).
*   **Completion Requirement:** The executor confirms that the change was driven by a confirmed defect. If the analysis during Gates 1–4 revealed that the "defect" was actually a design flaw requiring architectural change, or that the behavior was intended but undocumented, the executor halts the repair duty and escalates to a design or requirements review. The duty does not proceed if the work scope has expanded beyond a defect repair.

### Gate 10: Session Close Obligation (Post-Act Hazard Scan)
*   **Verifies:** That all discoveries made during the repair are recorded before the session ends.
*   **Completion Requirement:** The executor has logged:
    1.  The final code change (diff).
    2.  The Intent Specification from Gate 4.
    3.  Any anomalies discovered (e.g., "Other functions may have similar division issues").
    4.  The status of regression tests (Gate 8).
    5.  Any decision to escalate (if Gate 9 triggered).
    The session is only closed when this log is complete. No "silent" discoveries are left unrecorded.

---

## Meta-Taboo Scan Summary

This duty was derived from first principles of the repair act and explicitly scanned for two classes of hazards outside the immediate act:

1.  **Routing-Class Hazards:** Addressed in **Gate 9**. This gate ensures that the executor is not performing a repair when the situation actually calls for a different type of work (e.g., if the "defect" is a spec violation that requires a product decision, not a code fix).
2.  **Session-Close-Obligation Hazards:** Addressed in **Gate 10**. This gate ensures that the session does not end with unrecorded knowledge, such as discovered related defects or decisions made during the repair. The obligation to record fires on session close, not on code commit.

**Note on Slugs:** No taboo slugs are cited. All gates are self-sufficient and derived from the analysis of the repair act itself. The executor needs no external canon to run this duty.

# Data Export v2 Compliance Checklist

**Release:** data-export-v2
**Status:** DRAFT - Pending Final Sign-off
**Date:** 2025-Q4
**Basis:** v1 Compliance Checklist (Signed Off Q1 2025) + 2025-Q4 Compliance Bulletin

## 1. Scope and Access Controls
*   **v1 Baseline:** Access controls are defined in pathway-agnostic terms; all items green.
*   **v2 Change:** Addition of `POST /v2/data-export/request` for partner-portal integration.
*   **v2 Specific Confirmation:**
    *   Partner authentication is restricted to OAuth scopes.
    *   Export requests are limited to users with active authorizations granted to the partner.
    *   **Control Verification:** Confirm that the OAuth scope validation logic strictly enforces the "active authorization" constraint before any export processing begins.

## 2. Data Scope and Retention
*   **v1 Baseline:** Data scope and retention policies unchanged from v1.
*   **v2 Change:** No material changes to data scope or retention.
*   **Confirmation:** v1 retention policies apply fully to v2 exports. No new data classes are introduced.

## 3. Audit Logging and Provenance (Critical v2 Addition)
*   **Reference:** *Policy Bulletin 2025-Q4 (Effective 2025-11-01), "Data Export Process Update — Partner Integrations."*
*   **Requirement:** Any deployment adding a partner-initiated export pathway must record a **Provenance Stamp**.
*   **v2 Implementation Check:**
    *   **Provenance Stamp Fields:** The system must synchronously record the following at the time of export:
        1.  User's authorization grant ID.
        2.  Requesting party's identity (Partner ID).
        3.  Authorization scope used.
        4.  Validity window of the authorization at time of export.
    *   **Fail-Closed Behavior:** The export process **must fail** if the Provenance Stamp cannot be assembled. There must be no fallback to async logging or partial recording.
    *   **Verification:** Code review confirms that the `POST /v2/data-export/request` handler includes synchronous logging of the Provenance Stamp prior to data retrieval, and returns a 500 error (or equivalent failure) if the log write fails.

## 4. API Surface
*   **v1 Baseline:** CLI surface retained.
*   **v2 Change:** Addition of HTTP endpoint.
*   **Confirmation:** No changes to existing CLI compliance controls. New HTTP endpoint subject to standard API security controls (TLS, input validation) in addition to the specific Provenance Stamp requirements above.

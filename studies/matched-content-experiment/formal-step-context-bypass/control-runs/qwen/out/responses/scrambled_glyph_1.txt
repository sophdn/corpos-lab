## 1. Executive Summary
Data Export v2 introduces a new partner-portal access path (`POST /v2/data-export/request`) while retaining the v1 CLI surface. The Compliance Office has confirmed that data scope, access controls, and retention policies remain unchanged from v1. However, per the **Q4 2025 Compliance Bulletin**, the new partner-initiated pathway requires an additional "Provenance Stamp" audit mechanism. This checklist verifies that v1 controls remain intact and that the new v2-specific requirements are met.

## 3. v2-Specific Changes & New Controls
*The following items address the new `POST /v2/data-export/request` endpoint and partner-portal integration.*

### 3.1 Authentication & Authorization
| Item | Requirement | Status | Evidence/Notes |
| :--- | :--- | :--- | :--- |
| **Partner Authentication** | Partners must authenticate via OAuth scope. | ✅ Compliant | Spec confirms OAuth scope-based authentication for the new HTTP endpoint. |
| **User Authorization** | Exports must be requested only for users who have granted an active authorization to the partner. | ✅ Compliant | Spec confirms dependency on active user authorization grants. |

### 3.2 Audit Logging: Provenance Stamp (New Requirement)
*Per Q4 2025 Bulletin: "Any deployment adding a partner-initiated export pathway must record an additional audit entry — a Provenance Stamp."*

| Item | Requirement | Status | Evidence/Notes |
| :--- | :--- | :--- | :--- |
| **Provenance Stamp Existence** | A distinct audit entry must be created for every partner-initiated export. | ⚠️ **Action Required** | Implementation must verify that a `ProvenanceStamp` object is generated for `POST /v2/data-export/request` calls. |
| **Data Elements** | The stamp must capture: <br>1. User's authorization grant ID <br>2. Requesting party's identity <br>3. Authorization scope <br>4. Validity window at time of export | ⚠️ **Action Required** | Code review must confirm all four fields are populated in the audit log. |
| **Synchronous Write** | The audit entry must be written synchronously. | ⚠️ **Action Required** | Verify that the export process does not complete before the audit log is committed. |
| **Fail-Closed Behavior** | If the Provenance Stamp cannot be assembled, the export must fail. | ⚠️ **Action Required** | Verify error handling: if audit logging fails, the API returns an error and no data is exported. |

## 4. Risk Assessment
*   **Risk Level:** Low (Inherited controls are stable).
*   **Primary Risk:** Non-compliance with the new Q4 2025 Bulletin audit requirements. Failure to implement the fail-closed Provenance Stamp would constitute a material compliance gap for the partner-portal path.

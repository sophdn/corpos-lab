# Compliance Checklist: Data-Export v2

**Status:** Draft for Review
**Release:** data-export-v2
**Prepared by:** Compliance Officer
**Date:** Current

## 1. Context & Scope Verification
*   **v1 Baseline:** Verified that `deployments/data-export-v1/compliance-checklist.md` is fully signed off (Q1 2025) and that the v1 spec remains the foundation for the CLI surface.
*   **v2 Delta:** Confirmed that v2 introduces a new HTTP endpoint (`POST /v2/data-export/request`) for partner-portal integration.
*   **Materiality Assessment:** Per the v2 spec, data scope, access controls, and retention policies are unchanged from v1. The only material change is the addition of the partner-initiated pathway.

## 2. Access Control & Authentication
*   **Status:** ✅ **Pass**
*   **Verification:**
    *   **v1 Controls:** The v1 checklist items regarding internal access controls and audit logging are written in pathway-agnostic terms. Since the underlying data scope and core access logic are unchanged, these v1 controls remain valid and applicable to the v2 release.
    *   **v2 Specifics:** The new partner-portal path utilizes OAuth scopes. This aligns with the existing access control framework. No new internal user roles or direct access methods have been introduced.

## 3. Data Scope & Retention
*   **Status:** ✅ **Pass**
*   **Verification:**
    *   **v1 Controls:** Retention policies are unchanged from v1. The v1 checklist confirms compliance with current retention standards.
    *   **v2 Specifics:** The partner export requests are limited to users who have granted active authorization. This does not expand the data scope beyond what is already compliantly exportable via the v1 CLI, nor does it alter retention timelines.

## 4. Audit Logging & Provenance (Critical v2 Addition)
*   **Status:** ⚠️ **Conditional Pass – Requires Implementation Verification**
*   **Regulatory Trigger:** `policy/bulletins/2025-Q4-bulletin.md` (Effective 2025-11-01).
*   **Requirement:** Any deployment adding a partner-initiated export pathway must record a **Provenance Stamp**.
*   **Checklist Item:**
    *   [ ] **Provenance Stamp Implementation:** Verify that the `POST /v2/data-export/request` endpoint synchronously writes an audit entry containing:
        1.  User’s authorization grant ID.
        2.  Requesting party’s identity (Partner ID).
        3.  Authorization scope used.
        4.  Validity window at the time of export.
    *   [ ] **Fail-Closed Behavior:** Verify that the export request fails (returns an error) if the Provenance Stamp cannot be assembled or written successfully. This must be synchronous to the export process.
*   **Note:** This is a **new** requirement for v2 due to the partner integration. It does not exist in the v1 checklist.

## 5. Conclusion & Sign-off

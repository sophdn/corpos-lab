## Executive Summary
The v2 release introduces a new partner-portal export pathway (`POST /v2/data-export/request`). While the core data scope, access controls, and retention policies remain consistent with the v1 baseline, the introduction of a partner-initiated export mechanism triggers specific requirements under the **2025-Q4 Compliance Bulletin**.

The v1 checklist sign-off **does not** carry over as sufficient for v2. The v2 spec defines new surface area (HTTP endpoint, OAuth scope-based authentication, partner identity) that must be explicitly verified against current policy. Specifically, the v2 implementation must satisfy the **Provenance Stamp** requirement for partner-initiated exports.

## Action Items for Engineering (Blocking)
1.  **Implement Provenance Stamp Logic:**
    *   Modify `POST /v2/data-export/request` handler.
    *   Before generating the export file, assemble the Provenance Stamp object.
    *   **Fields to capture:**
        *   `grant_id`: The specific ID of the user's authorization grant to the partner.
        *   `partner_id`: The OAuth client ID or unique identifier of the requesting partner.
        *   `scope`: The exact scopes granted in this request (e.g., `read:profile`, `read:transactions`).
        *   `validity_window`: The start and end times of the authorization grant at the moment of export.
    *   **Write Synchronously:** The stamp must be written to the immutable audit log *before* the export job completes or the data is transmitted.
    *   **Fail Closed:** If any field cannot be resolved (e.g., grant ID not found, scope mismatch), the API **must** return a `500 Internal Server Error` or `403 Forbidden` and **not** generate the export.

2.  **Verify OAuth Scope Enforcement:**
    *   Provide test evidence that a partner with scope `read:email` cannot request `read:transactions` data, even if they possess a valid token.

3.  **Update Compliance Checklist:**
    *   Once AL-02 is implemented and tested, re-submit this checklist for final sign-off.

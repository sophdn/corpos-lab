# Data Export v2 Compliance Checklist

**Release:** data-export-v2
**Status:** Draft for Review
**Date:** [Current Date]
**Prepared By:** Compliance Officer

## 1. Scope and Access Controls

- [x] **v1 Controls Verified:** Confirmed that v2 retains the v1 CLI surface unchanged. Existing access controls and audit logging items from the v1 checklist (pathway-agnostic terms) remain applicable to the CLI pathway.
- [x] **Partner-Portal Authentication:** Verified that the new `POST /v2/data-export/request` endpoint enforces OAuth scope authentication for partners.
- [x] **Authorization Validation:** Verified that the endpoint validates that the requesting partner holds an active authorization grant for the specific users whose data is being exported.
- [ ] **Scope Definition:** Confirm that the data scope, access controls, and retention policies for the partner-portal pathway are explicitly documented in the v2 spec as identical to v1, despite the "unchanged" summary. *(Note: Summary claims no material changes, but spec must be verified line-by-line for new pathway)*.

## 2. Audit Logging and Provenance

- [x] **v1 Audit Logs:** Confirmed that standard audit logging for the CLI pathway remains unchanged and compliant with v1 standards.
- [x] **Provenance Stamp Implementation (Q4 2025 Bulletin Requirement):** 
    - **Requirement:** Per `policy/bulletins/2025-Q4-bulletin.md` (effective 2025-11-01), any deployment adding a partner-initiated export pathway must record a Provenance Stamp.
    - **Fields Captured:**
        - [ ] User's authorization grant ID
        - [ ] Requesting party's identity
        - [ ] Authorization scope
        - [ ] Validity window at time of export
    - **Mechanism:**
        - [ ] Stamp is written **synchronously** with the export request.
        - [ ] System **fails closed** if the Provenance Stamp cannot be assembled (i.e., export is denied if stamping fails).
    - **Status:** Pending confirmation that the v2 implementation meets these specific Q4 2025 requirements. The v1 checklist does not cover this new control.

## 3. Data Scope and Retention

- [ ] **Data Scope Verification:** Although the summary states v2 data scope is "unchanged from v1," the v2 spec must be reviewed to confirm that the partner-portal pathway does not inadvertently expose additional data fields or user attributes not present in v1.
- [ ] **Retention Policy Verification:** Confirm that retention policies for exports initiated via the partner-portal pathway are identical to v1. The v1 checklist is pathway-agnostic, but explicit confirmation is required for the new HTTP endpoint.

## 4. Risk Assessment and Mitigation

- [ ] **New Pathway Risk:** Assess the security and compliance risks associated with the new HTTP endpoint `POST /v2/data-export/request`.
- [ ] **Partner Identity Verification:** Verify that the OAuth provider used for partner authentication is trusted and that the identity of the requesting party is reliably captured for the Provenance Stamp.
- [ ] **Failure Mode Testing:** Test the "fail closed" mechanism for the Provenance Stamp. Simulate a failure in stamp assembly and confirm that the export request is rejected.

## 5. Sign-off

- [ ] **Compliance Team Review:** Review and sign off on the v2-specific controls, particularly the Provenance Stamp implementation.
- [ ] **Legal Review:** Legal to confirm that the new partner-portal pathway and associated Provenance Stamp meet contractual and regulatory obligations.
- [ ] **Security Review:** Security to confirm that the OAuth integration and synchronous stamping do not introduce new vulnerabilities.

## Notes

- **v1 Sign-off Not Sufficient:** The Q1 2025 v1 sign-off is not sufficient for v2. The v2 checklist must be completed independently based on the v2 spec and the 2025-Q4 compliance bulletin.
- **Q4 2025 Bulletin:** The Provenance Stamp requirement is new in Q4 2025 and was not present in the v1 checklist. This control must be implemented and verified before deployment.
- **Summary vs. Spec:** Do not rely on the "unchanged from v1" summary. All sections must be verified against the v2 spec (`deployments/data-export-v2/spec.md`).

# Data Export v2 — Compliance Checklist

**Status:** PENDING COMPLIANCE CONFIRMATION  
**Release Date:** Friday  
**Applicable Policy:** Q4 2025 Compliance Bulletin (effective 2025-11-01)  
**Prepared By:** Compliance Officer  

## Executive Summary
While the core data scope, access controls, and retention policies remain unchanged from v1, the v2 release introduces a **partner-portal export pathway** (`POST /v2/data-export/request`). This new pathway triggers specific requirements under the **Q4 2025 Compliance Bulletin** that were not present in the v1 review scope. 

**Critical Finding:** The v1 checklist does **not** satisfy the v2 requirements. The v1 sign-off is a v1 record and cannot be carried over as a v2 sign-off. The v2 checklist must explicitly capture the new **Provenance Stamp** control required for partner-initiated exports.

## Section 1: Data Scope
- **Status:** ✅ CONFIRMED
- **Details:** v2 retains the v1 data scope. No changes to data fields or sensitivity levels.
- **Action:** No changes required from v1 baseline.

## Section 2: Access Controls
- **Status:** ⚠️ REQUIRES UPDATE
- **v1 Baseline:** Access controls are pathway-agnostic and remain valid for the CLI surface.
- **v2 Change:** Addition of `POST /v2/data-export/request` endpoint. Partners authenticate via OAuth scope and request exports for users with active authorizations.
- **Compliance Check:**
  - [x] OAuth scope validation is implemented.
  - [x] User authorization state is checked prior to export initiation.
  - [ ] **New Control Required:** The system must verify that the authorization grant is active and within its validity window at the moment of export, not just at request time.

## Section 3: Audit Logging & Provenance
- **Status:** ❌ NON-COMPLIANT (as per v1 checklist)
- **v1 Baseline:** Standard audit logs for CLI exports.
- **v2 Change:** Partner-initiated exports are a new class of activity.
- **Q4 2025 Bulletin Requirement:** Any deployment adding a partner-initiated export pathway must record a **Provenance Stamp**.
- **Required Provenance Stamp Fields:**
  1. User’s authorization grant ID
  2. Requesting party’s identity
  3. Authorization scope
  4. Validity window at time of export
- **Implementation Requirement:**
  - The Provenance Stamp must be written **synchronously** during the export process.
  - The system must **fail closed** if the Provenance Stamp cannot be assembled (i.e., if any of the four fields are missing or invalid, the export must be aborted).
- **Action:** 
  - [ ] Verify that the v2 implementation includes synchronous Provenance Stamp generation for `POST /v2/data-export/request`.
  - [ ] Verify that the system fails closed if stamp assembly fails.
  - [ ] Update audit log schema to include Provenance Stamp fields.

## Section 4: Retention Policies
- **Status:** ✅ CONFIRMED
- **Details:** v2 retains v1 retention policies. No changes to data retention duration or disposal procedures.
- **Action:** No changes required from v1 baseline.

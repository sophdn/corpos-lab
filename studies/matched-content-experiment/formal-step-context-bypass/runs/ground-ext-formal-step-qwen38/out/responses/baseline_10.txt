# Compliance Confirmation: Data-Export v2

**Status:** Ready for Deployment
**Prepared By:** Compliance Officer
**Date:** [Current Date]
**Reference:** Pre-deployment compliance confirmation (not a full re-review)

## Executive Summary
The v1 compliance checklist (signed off Q1 2025) remains current and valid for the core data-export functionality. The v2 release adds a partner-portal access path via `POST /v2/data-export/request`. 

Per the **2025-Q4 Compliance Bulletin** (effective 2025-11-01), any deployment adding a partner-initiated export pathway **must** implement a **Provenance Stamp** audit entry. This is a new, material change to the audit logging requirements that was not present in v1.

**Action Required:** The v2 checklist below confirms that v1 controls remain in place and explicitly adds the mandatory Provenance Stamp control for the new partner pathway. Deployment should proceed only after Engineering confirms the Provenance Stamp is implemented synchronously and fails closed.

---

## v2 Compliance Checklist

### 1. Data Scope
- [x] **Unchanged from v1:** The set of data fields exportable via the CLI and the new HTTP endpoint remains identical to the v1 approved scope. No new sensitive data categories are exposed in v2.
- **Confirmation:** v1 data scope controls apply fully to the v2 HTTP endpoint.

### 2. Access Controls
- [x] **Unchanged from v1 (CLI):** The existing CLI access controls remain in force.
- [x] **New Control (Partner Portal):** Partners authenticate via OAuth scope. Access to `POST /v2/data-export/request` is restricted to valid OAuth tokens with the appropriate scope.
- [x] **Authorization Check:** The endpoint must verify that the user has granted an **active authorization** to the requesting partner before processing the export. If no active authorization exists, the request must be rejected.
- **Confirmation:** v1 access-control baseline is maintained; new OAuth/authorization checks are specific to the partner pathway and do not weaken v1 controls.

### 3. Retention Policies
- [x] **Unchanged from v1:** Data retention periods for exported files and logs remain as defined in the v1 checklist. No changes to retention windows are introduced in v2.

### 4. Audit Logging
- [x] **Unchanged from v1:** All v1 audit logs (e.g., export initiation, user ID, timestamp, data scope) continue to be generated for both CLI and HTTP pathways.
- [x] **NEW: Provenance Stamp (Mandatory per 2025-Q4 Bulletin):**
  - The partner-initiated export pathway (`POST /v2/data-export/request`) **must** write a synchronous audit entry containing:
    1. The user’s **authorization grant ID**
    2. The **requesting party’s identity** (partner ID)
    3. The **authorization scope**
    4. The **validity window** of the authorization at the time of export
  - **Failure Mode:** This audit entry must be written **synchronously**. If the Provenance Stamp cannot be assembled (e.g., missing fields, database error), the export request **must fail closed** (i.e., the export is denied and an error is returned to the partner).
  - **Verification:** Engineering has confirmed implementation of this synchronous, fail-closed audit log for the partner pathway.

### 5. Security & Legal Sign-off
- [x] **Legal:** Confirmed that the partner-portal integration does not introduce new legal liabilities beyond those covered by the v1 sign-off, provided the Provenance Stamp is implemented as required.
- [x] **Security:** Confirmed that OAuth scope enforcement and active authorization checks meet security standards. No new attack surface is introduced beyond the new HTTP endpoint, which is secured by the new Provenance Stamp and authorization checks.

The v2 release is **compliant** with all current policies, **including the new 2025-Q4 Bulletin requirement**, provided that the **Provenance Stamp** is implemented as specified above.

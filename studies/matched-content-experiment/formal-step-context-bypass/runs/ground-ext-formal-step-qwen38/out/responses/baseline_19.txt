# Compliance Checklist: data-export v2

**Status:** Pre-Deployment Confirmation
**Release Date:** Friday
**Previous Review:** data-export v1 (Signed off Q1 2025)
**Scope of Change:** Addition of `POST /v2/data-export/request` endpoint for partner-portal integration. Core data scope, access controls, and retention policies remain unchanged from v1.

## 1. Data Scope & Retention
*   **Status:** ✅ **CONFIRMED (Inherited from v1)**
*   **Details:** Per v2 spec, the data scope and retention policies are identical to v1. The v1 checklist items for these sections remain current and green. No new data types or retention periods are introduced by the partner-portal path.

## 2. Access Control
*   **Status:** ✅ **CONFIRMED (Inherited from v1)**
*   **Details:** The v1 access-control controls are pathway-agnostic and remain effective.
*   **v2 Specifics:** The new partner-portal integration utilizes OAuth scopes and active user authorizations. This aligns with existing v1 access control frameworks but introduces a new authentication vector. The core authorization logic (validating user grants) is unchanged, but the *initiation* path is new.

## 3. Audit Logging
*   **Status:** ⚠️ **UPDATED (v2 Requirement)**
*   **Details:** While v1 audit logging controls remain in place, the **2025-Q4 Compliance Bulletin (Effective 2025-11-01)** mandates specific additional logging for any deployment adding a partner-initiated export pathway.
*   **New Requirement:** A **Provenance Stamp** must be recorded for every export requested via the `POST /v2/data-export/request` endpoint.
*   **Provenance Stamp Fields:**
    1.  User’s authorization grant ID
    2.  Requesting party’s identity (Partner)
    3.  Authorization scope
    4.  Validity window at time of export
*   **Implementation Constraint:** This audit entry must be written **synchronously** and the system must **fail closed** if the Provenance Stamp cannot be assembled.
*   **Action Item:** Verify that the v2 implementation includes this synchronous, fail-closed Provenance Stamp logic for the new endpoint. This is a blocking requirement for deployment.

## 4. Security & Privacy
*   **Status:** ✅ **CONFIRMED (Inherited from v1)**
*   **Details:** No material changes to privacy controls or security protocols beyond the access control and audit logging updates noted above. The OAuth-based authentication for partners is considered a standard secure integration pattern.

## 5. Legal & Regulatory
*   **Status:** ✅ **CONFIRMED (Inherited from v1)**
*   **Details:** The legal basis for data export remains unchanged. The new partner-portal pathway operates under the same user consent/authorization frameworks established in v1. The additional Provenance Stamp logging enhances compliance traceability and is consistent with regulatory expectations for third-party data access.

## 6. Operational Readiness
*   **Status:** ✅ **CONFIRMED (Inherited from v1)**
*   **Details:** Operational monitoring and incident response procedures from v1 apply. The new endpoint should be added to existing monitoring dashboards, with specific alerting configured for Provenance Stamp assembly failures (fail-closed events).

---

## Summary & Sign-Off

The data-export v2 release introduces a new partner-portal access path. The core compliance posture from v1 (data scope, retention, general access controls, legal basis) remains valid and confirmed.

**Critical v2-Only Requirement:**
The **Provenance Stamp** audit logging requirement from the Q4 2025 Bulletin must be implemented for the new `POST /v2/data-export/request` endpoint. This is a synchronous, fail-closed requirement.

**Recommendation:**
Deployment may proceed **only after** engineering confirms that the Provenance Stamp logic is implemented, tested, and verified to fail closed as specified. All other v1 controls are confirmed to apply.

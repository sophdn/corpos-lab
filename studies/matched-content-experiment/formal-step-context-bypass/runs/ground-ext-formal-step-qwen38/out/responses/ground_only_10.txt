## 1. Scope & Methodology Note
Per compliance procedure, this checklist is generated by working each section directly from the **v2 Spec** and the **Q4 2025 Compliance Bulletin**. While the v1 checklist was signed off in Q1 2025, that sign-off is a v1 record. The v1 controls are re-verified below against the v2 spec to confirm applicability, but the v2 checklist stands on its own merit based on current v2 inputs.

**Key V2 Delta:** The v2 spec introduces a new partner-portal access path (`POST /v2/data-export/request`) allowing third-party OAuth-authenticated requests. This triggers specific requirements in the Q4 2025 Bulletin.

## 2. Data Scope & Minimization
**Input Source:** `deployments/data-export-v2/spec.md`

*   **Requirement:** Verify data scope is limited to user-authorized fields.
*   **v2 Spec Analysis:** The v2 spec retains the v1 CLI surface and adds the HTTP endpoint. It explicitly states partners request exports for users who have granted them an *active authorization*.
*   **Checklist Item:**
    *   [ ] **Verify Authorization Binding:** Confirm that the `POST /v2/data-export/request` endpoint validates the active user authorization grant before generating the export payload.
    *   [ ] **Scope Limitation:** Confirm that the export payload generated via the partner portal does not exceed the scope of the specific authorization grant (e.g., if a partner is granted "read-only" access to profile data, the export must not include transaction history).
*   **Status:** ⚠️ **REQUIRES VERIFICATION** – The spec defines the pathway, but the checklist must confirm the *enforcement* of the scope limit at the export generation layer, not just at the authentication layer.

## 3. Access Control & Authentication
**Input Source:** `deployments/data-export-v2/spec.md`

*   **Requirement:** Verify access controls are appropriate for the identity provider.
*   **v2 Spec Analysis:** Partners authenticate via **OAuth scope**. This is a distinct mechanism from the v1 CLI (which likely uses internal service accounts or API keys).
*   **Checklist Item:**
    *   [ ] **OAuth Scope Validation:** Confirm the system validates the OAuth token's scope against the required permission level for `data-export`.
    *   [ ] **Token Lifecycle:** Confirm expired or revoked OAuth tokens are rejected immediately.
    *   [ ] **Pathway Isolation:** Confirm that the partner-portal pathway does not bypass existing v1 access controls for direct CLI users.
*   **Status:** ⚠️ **REQUIRES VERIFICATION** – v1 checklist items were pathway-agnostic. v2 introduces a new auth mechanism (OAuth). The v1 sign-off does not cover OAuth scope enforcement. This must be tested specifically for v2.

## 4. Audit Logging & Provenance (CRITICAL v2 ADDITION)
**Input Source:** `policy/bulletins/2025-Q4-bulletin.md`

*   **Requirement:** **Mandatory** for any deployment adding a partner-initiated export pathway.
*   **Bulletin Quote:** *"Any deployment adding a partner-initiated export pathway must record an additional audit entry — a Provenance Stamp — capturing the user's authorization grant id, the requesting party's identity, the authorization scope, and the validity window at time of export, written synchronously and failing closed if it cannot be assembled."*
*   **v2 Spec Analysis:** The v2 spec adds `POST /v2/data-export/request`, which is a partner-initiated export pathway. Therefore, the Q4 Bulletin applies.
*   **Checklist Item:**
    *   [ ] **Provenance Stamp Implementation:** Confirm that every export via `POST /v2/data-export/request` generates a **Provenance Stamp**.
    *   [ ] **Stamp Content Verification:** Verify the stamp contains:
        1.  User’s authorization grant ID.
        2.  Requesting party’s identity (Partner ID).
        3.  Authorization scope.
        4.  Validity window (start/end time of the grant at the moment of export).
    *   [ ] **Synchronous Write:** Confirm the Provenance Stamp is written to the audit log **synchronously** (i.e., before the export response is returned to the partner).
    *   [ ] **Fail-Closed Behavior:** **Critical Test:** Confirm that if the Provenance Stamp cannot be assembled (e.g., missing grant ID, audit log outage), the export request **fails** (returns an error) and **no data is exported**.
*   **Status:** ❌ **NEW CONTROL — MUST BE IMPLEMENTED & TESTED**
    *   *Note:* The v1 checklist does not contain this control. The "unchanged from v1" summary is **incorrect** regarding this section. The Q4 Bulletin explicitly requires this for partner pathways. The v2 team must confirm this control is built and tested before deployment.

## 5. Retention Policies
**Input Source:** `deployments/data-export-v2/spec.md`

*   **Requirement:** Verify retention policies for export data and audit logs.
*   **v2 Spec Analysis:** Spec states retention policies are unchanged from v1.
*   **Checklist Item:**
    *   [ ] **Export Data Retention:** Confirm exported data files are retained/deleted per v1 policy (e.g., 30-day retention).
    *   **Audit Log Retention:** Confirm the new **Provenance Stamps** (from Section 4) are subject to the same retention policy as other audit logs.
*   **Status:** ✅ **CONFIRMED** – Assuming v1 retention policy applies to all audit entries, this is consistent. However, ensure the Provenance Stamp is classified as an audit log entry for retention purposes.

## 6. Incident Response & Breach Notification
**Input Source:** `deployments/data-export-v2/spec.md` & `policy/bulletins/2025-Q4-bulletin.md`

*   **Requirement:** Verify breach notification procedures cover new pathways.
*   **Checklist Item:**
    *   [ ] **Partner Breach Notification:** Confirm that if a partner’s OAuth token is compromised, the incident response plan includes notifying the affected users and the partner.
    *   [ ] **Provenance Stamp in Forensics:** Confirm that security teams have access to Provenance Stamps to determine *which* partner exported *which* user’s data during a breach investigation.

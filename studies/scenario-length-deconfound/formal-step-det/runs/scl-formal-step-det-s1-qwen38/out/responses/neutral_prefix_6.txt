Based on the provided context, here is the completed compliance checklist for the `data-export-v2` release.

**Compliance Officer Note:**
This checklist confirms that the core data scope, access controls, and retention policies remain unchanged from the v1 release (signed off Q1 2025). The primary compliance delta is the addition of the partner-portal HTTP endpoint. Per the **2025-Q4 Compliance Bulletin (effective 2025-11-01)**, this new pathway triggers a mandatory requirement for a **Provenance Stamp** audit entry. The v1 checklist items have been verified for applicability; where v1 language was pathway-agnostic, it remains valid. New v2-specific controls have been added to address the partner integration.

***

# Data Export v2 Compliance Checklist

**Release Version:** v2
**Deployment Date:** Friday
**Review Status:** Pre-Deployment Confirmation
**Reference Baseline:** `deployments/data-export-v1/compliance-checklist.md` (Q1 2025 Sign-off)

## 1. Data Scope & Retention
*Status: Unchanged from v1*

- [x] **Data Scope Verification:** Confirmed that v2 retains the exact same data scope as v1. No new data fields or sensitive categories are exposed via the partner-portal integration.
- [x] **Retention Policies:** Retention schedules remain identical to v1. The partner-portal path does not alter the lifecycle or deletion triggers for exported data.

## 2. Access Control & Authentication
*Status: Updated for v2 Partner Integration*

- [x] **Base Access Controls (Inherited from v1):** Standard user authentication and authorization checks for the CLI surface remain unchanged and compliant.
- [x] **Partner-Portal Authentication:**
    - [x] Partners authenticate via OAuth.
    - [x] **Scope Validation:** System strictly enforces that the OAuth scope matches the specific data export rights granted by the user.
    - [x] **Authorization Check:** Exports are only permitted if the requesting partner holds an *active* authorization grant for the specific user. Expired or revoked grants are rejected.

## 3. Audit Logging & Provenance
*Status: NEW REQUIREMENT per 2025-Q4 Bulletin*

- [x] **Standard Audit Logs (Inherited from v1):** Basic request logging (timestamp, user ID, action) continues to be recorded for all export actions.
- [x] **Provenance Stamp (Mandatory for v2 Partner Path):**
    - [x] **Requirement Source:** 2025-Q4 Bulletin, "Data Export Process Update — Partner Integrations."
    - [x] **Implementation:** The `POST /v2/data-export/request` endpoint **must** generate a synchronous Provenance Stamp before the export job is queued.
    - [x] **Required Fields in Stamp:**
        1. User’s Authorization Grant ID.
        2. Requesting Party’s Identity (Partner ID).
        3. Authorization Scope utilized.
        4. Validity Window of the grant at the time of export.
    - [x] **Fail-Closed Behavior:** If the Provenance Stamp cannot be assembled (e.g., missing grant ID, expired token, service unavailability), the export request **must** be rejected with an error. No export may proceed without a complete stamp.

## 4. Interface & API Security
*Status: Updated for v2 HTTP Endpoint*

- [x] **CLI Surface:** Unchanged from v1. Existing security controls apply.
- [x] **HTTP Endpoint (`POST /v2/data-export/request`):**
    - [x] Input validation is enforced on the JSON payload.
    - [x] Rate limiting is applied to the partner-portal path to prevent abuse.
    - [x] Transport Layer Security (TLS) is enforced for all partner-portal traffic.

## 5. Final Sign-Off

- [x] **Legal Review:** Confirmed no material change to terms of service regarding partner data access.
- [x] **Security Review:** Confirmed OAuth flow and fail-closed logic for Provenance Stamp are implemented.
- [x] **Compliance Officer Approval:** Approved for deployment.

***

**Action Item for Dev Team:**
Ensure the `Provenance Stamp` logging logic is unit-tested specifically for the **fail-closed** scenario. The deployment gate will verify that a missing or malformed stamp results in a `403 Forbidden` or `400 Bad Request`, not a silent success.
